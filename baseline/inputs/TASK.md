# Implement a runnable synchronous consensus system

Implement the protocol in `protocol.md` as a runnable Go replicated key/value system, using module `example.com/syncepaxos`. Deliver a reusable consensus Node, separate server processes, real network transport, reusable client interfaces and CLI tooling, tests and documentation. Prefer the standard library for offline builds. Do not substitute another consensus algorithm. Choose your own design, implementation process and testing strategy; implement, test, review and fix the system before delivering it.

## Service requirements

Implement deterministic Put, Get and Delete operations on individual keys. Support configurable node identity, fixed membership, addresses, configuration identity and Delta. Multiple independent clients must be able to issue concurrent operations. The delivered programs must run independently of Codex or its tools. A production deployment platform and general storage engine are unnecessary.

Follow the protocol's conflict classification, dependency execution, deterministic SCC ordering and per-replica execution deduplication. Reads must use a documented consistency path, not arbitrary local state. Describe the service consistency guarantee supported by the protocol and implementation. A complete client-history linearizability guarantee is not established in these materials; execution-before-response and eventual replica agreement alone do not establish it.

Use the single-submission client model in protocol section 14. Each logical operation is submitted at most once to one selected replica, with an immutable complete original value and original coordinator. Allocate `(ClientID, RequestSeq)` exactly as specified, including independent allocation sessions, safe concurrent allocation, sequence gaps and out-of-order arrival. Client retry, resubmission after failover, cross-replica result lookup and recovery of old pending client requests are outside scope. A restarted client may issue new operations in a fresh allocation session.

Distinguish rejection before admission, retained application outcomes and unknown outcomes. Normal fault-free service responses to connected waiting clients must return the actual retained execution outcome; admission or metadata decision is insufficient. Application errors are execution results and do not authorize re-execution. A timeout, disconnect or cancelled client wait means the result is unknown to that caller and does not cancel an admitted command's replica obligations or prove any replica dead. No universal end-to-end completion deadline is specified. If the contacted replica crashes before replying, delivery of that result through another replica is outside scope.

Reject malformed requests before admission and preserve legal commands, their retained results and progress when rejecting contradictory ID reuse, as specified in section 14. Rejected inputs must not become dependencies. Local rejection cannot repair a history in which different replicas already admitted different originals for the same ID; report that model violation and its service impact. Transport retransmission and repeated replica knowledge remain supported even without client retries.

## Runtime and network requirements

Nodes must make progress autonomously after startup using real time, without requiring the application to tick or pump transitions. Support concurrent submissions and replica communication, application execution, cancellation and shutdown. Dependency-ready commands must execute while requests continue, and ready independent work must not be indefinitely displaced by newly ready work. Replica discovery and takeover must not require another client request. Follow the protocol's waits and failure assumptions; its ideal-model aggregate times are not additional wall-clock service deadlines. Choose the runtime mechanisms yourself. The protocol's limitation for an infinite conflicting workload whose closure never becomes ready still applies.

Preserve message identity and payload exactly across the wire. Validate configuration and bind connection/message sources to configured member identities; an unverified payload field is not authentication. A documented trusted-cluster mode is sufficient for the CFT deployment; Byzantine tolerance and production PKI are not required.

Provide real-time operation and controlled time/message delivery using the same implementation. The consensus logic must remain reusable without opening real sockets, with replaceable transport and a documented application interface. Provide control and observation points for actual Node operation, including message and completion events, decisions, execution, local retirement and stopping. Observations must reflect actual implementation events. Choose the interfaces and tests yourself.

## History and failure scope

Implement complete observation collection before choosing Fast or Seal and local retirement after actual application completion, as specified in protocol sections 4 and 12.1. Retain the outcome and remove the command from future local conflict observations consistently with atomic first observation. A running application callback does not count as completed. Retirement requires no remote execution report.

Keep originals, immutable observations, seals, decisions, execution flags and results available for old messages and dependency references. Old observations and recovery snapshots must not be recomputed from the retired view, and partial completion of an SCC must not change its established execution order. Retirement is not permission to delete history; active work and retained history have no uniform size bound. Choose the data structures and optimizations yourself.

Support fixed membership and at most f cumulative crash-stop failures. A crashed replica never resumes or rejoins; completed sends retain their delivery obligations to surviving recipients. WAL, crash-restart recovery, membership change, snapshot installation, safe history deletion and arbitrary partition recovery are outside scope. Retaining history in memory for a surviving process's lifetime is acceptable. Explain resource limits, their observable effects before and after admission, and any unmet requirements. An implementation limit does not silently narrow the supplied guarantees.

Include `README.md` for build, configuration, usage, tests, supported semantics and limits, and `DESIGN.md` describing the implemented architecture, interfaces, concurrency, timing and assumptions. Document genuine specification gaps without changing the supplied materials. Choose document structure and test contents yourself.

You may use them or write your own tools. The time budget includes execution. Finish by reporting actual changes, commands and results, and remaining limitations.
