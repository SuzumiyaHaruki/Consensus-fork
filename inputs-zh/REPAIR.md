# 修复提供的候选实现

完整阅读 `protocol.md` 与 `system.md`，在给定的假设与运行约束下修复本轮分配的问题。不要修改 `protocol.md`、`system.md` 或其他提供的材料，也不要查看其他实验或获取另一份共识实现来替代本次实现。

* 阅读 `.forge/feedback/handoff.json`、其中的 `issues_file`，以及相关的原始报告与复现脚本。概览信息仅用于定位问题和证据，其中的摘要不能替代你自己的核查。
* 只处理 `handoff.repair_issue_ids` 指定的问题，并对每项给出一次明确的处理结论；若旧交接中没有该字段，则处理 `issues_file` 中的全部问题 ID。其他待处理问题仅作为上下文背景。

## 1. 理解与定位证据

### 1.1 核对审计发现与复现

* **审查结论与时间/性能依据**：逐项核对审计者引用的要求，检查触发条件是否符合协议假设、在运行时能否实际出现、审计者提出的原因是否成立，以及是否存在其他合理解释。涉及耗时的结论时，须说明时间假设覆盖了哪些实际工作（不能仅凭函数与协议动作同名或消息已入本地队列就认定时间界满足）。核对性能问题的测量条件、成因与实际影响，不能仅因材料未给出数值指标就否定问题。
* **先复现再修改与极性判读**：可行时，先在修改代码前运行原始复现。结合断言与 `polarity`（预期结果极性，即测试通过或失败分别代表什么含义）判断实际结果：复现测试 `PASS` 有时恰恰说明缺陷已被成功复现。
* **走真实路径与严谨解读观察**：测试应经过实际的 `Node` 或服务处理代码。说明测试控制了哪些事件、替换或绕过了哪些组件；测试适配器不得补发缺失的协议消息、代为推进状态转换，也不得掩盖实现中的失败。区分测试请求的动作与实际观察到的事件，说明断言能支持什么结论。等待一段时间仍未完成，不能单凭这一点认定系统永远无法推进。
* **适配与临时构建**：保留原始证据。若因接口调整或目录差异需要做 API/路径适配并重新构建临时二进制，应明确说明适配细节；注意，测试无法编译或原触发条件无法构造，都不能证明问题已经修复。可选调度工具 `../inputs/schedule.py` 提供 `--help`；在隔离执行中使用捕获的源码副本时，须通过其绝对路径调用，且事件记录或重放成功本身不能证明实现正确。

### 1.2 检索本轮与历史证据

索引中的路径以 `.forge/feedback/` 为起点；原始记录中的路径则以其所属运行目录为起点。

* **`execution_records`**：用于定位历史命令与结果。其中 `restore` 将工作区目标路径映射到保留输入，`outputs` 列出保存的文件，`cwd_relative` 表示相对源码工作目录的路径。复用前应先检查覆盖在实现上的补丁层（`overlay`）。
* **`history_file`**：记录已关闭的问题及复核新增的证据；历史关闭结论仅适用于其对应的记录版本。
* **`evidence_index_file`**：可能包含可复用案例、未决问题以及未完成调查的 `supplemental_turns`。使用补充材料前先评估它支持什么结论，不把未完成的草稿当成已确认的发现或额外修复任务。

## 2. 修复方案、结构维护与影响检查

### 2.1 选择修复方案并维护代码结构

* **对症修复与保持行为**：针对已确认的根因修改代码，同时维持 `protocol.md` 与 `system.md` 规定的服务行为。修复方案由你自行决定，不必照搬审计者的建议，也不要放宽协议要求或依赖材料未承诺的外部条件。
* **论证对明文规则的偏离**：复现问题后，先对照协议，检查代码是否按规定的步骤执行。若要引入或保留一项协议改动，须通过重放或可逐步核对的完整推导，证实在可达场景中遵循原条款会违反保证，或导致两项要求无法同时满足。指出必要的最小改动如何解决同一场景，并论证原有假设下受影响的安全性与活性保证仍然成立。证据不足时按原规则修复代码，记录剩余的设计疑问。
* **不以规避或删声明代替修复**：若证据表明审计结论不成立，应说明理由并保留合规实现；切勿仅为通过某个测试而添加特殊分支、削弱断言或关闭应有功能。若问题仅在于文档作出了无依据的性能声明，可更正文档并明确说明实现行为未变；若证据显示实现本身存在性能问题，则不能仅靠删除声明或增加使用限制宣称已修复。
* **守住组件边界与代码整洁**：修改实现时保持协议处理、运行时调度、传输、存储、应用与客户端之间的职责清晰，维护正确的同步机制、状态归属以及接口在阻塞、重入、完成、取消和关闭时的行为；随手整理重复逻辑与不当耦合，避免补丁堆砌。

### 2.2 追踪受影响行为与性能表现

* **分析改动影响**：对照代码差异，说明某项改动预期解决什么问题、必须保留哪些协议行为，并沿改动追踪受影响的条件、消息义务与后续处理——尤其是原先能成功、现在可能被拒绝、延迟或重复处理的请求与步骤。
* **针对性验证与负载对照**：选取能够验证原问题、关联行为及历史问题的测试，不要求每轮跑全量旧测试。当改动涉及共享状态同步、任务调度、计时与重试、扫描或传输机制时，应在可比的每副本资源与实际负载下对照正常路径与原触发场景。
* **对比工作量与后台进度**：比较资源消耗时，应结合两个版本各自完成了多少工作来评估；适用时报告每条已完成请求的成本，并说明协议要求的后台工作（包括转移到其他副本或推迟执行的步骤）完成了多少、还剩多少。即使原现象消失或请求最终成功，也须分别评估协议符合性与正确性，记录仍待解释的差异。
* **同步更新 `DESIGN.md`**：随修复更新 `DESIGN.md` 中受影响的系统结构、状态归属、关键接口与选择、代码位置、检查依据及局限；区分推理与实测结果，详细调查日志通过引用关联，不要堆放在 `DESIGN.md` 中。

### 2.3 有争议的发现与设计缺口

* **准确使用定性标签**：证据反驳审计发现时使用 `not_substantiated`；调查尚不完整时使用 `unresolved`；只有当要求缺失或互相矛盾导致无法确定合规修复时，才使用 `needs_specification`。
* **明确缺口边界与独立复核**：使用 `needs_specification` 时，指明具体缺失或矛盾的规则以及哪些问题 ID 的修复依赖它；对于材料未规定的实现机制，由你自行选择并继续处理不受该缺口影响的问题。不要改写设计材料；即使未修改代码，结论与实现也同样会接受独立复核。

## 3. 运行环境、执行工具与交付收尾

### 3.1 运行条件、安全边界与测试执行

* **检查资源与进程布局**：开展资源敏感的运行前，先检查可用 CPU、内存、进程布局与运行时配置，按实际资源确定负载规模，并保留真实多进程检查。报告每个副本的 `GOMAXPROCS`，它限制该进程中能同时执行 Go 代码的 goroutine 数量。说明各副本共享哪些逻辑 CPU，或分别绑定到哪些 CPU。
* **遵守沙箱、网络与委派规则**：在给定工作区内开发，本地集群与客户端使用回环地址，在协议模型内模拟故障。保留认证与沙箱保护，不更改凭据、不对外发布代码或软件包、不部署到远程或生产环境、不向第三方发送通信，也不修改无关资源；凭据不得写入代码或配置。可使用相同模型、推理强度、权限和预算的原生 Codex 子智能体，协调共享文件修改与高开销测试，整合其修改与结果，并在交付前结束或停止委派任务；不要启动嵌套 Codex 会话或调用外部模型服务。
* **隔离执行与证据留存**：TCP 或多进程测试使用 `forge_local.isolated_exec`，按工具说明配置；用 `outputs` 指定需保留的文件，并检查 `result.artifacts` 确认留存。默认在 `work` 中测试正在修改的实现；`source="candidate"` 对应本轮修复前的候选版本。引用实际执行记录，说明被测版本，保留前后观察；文件缺失或适配器损坏属于复现限制。针对 `evidence_feedback`，可通过证据、解释或更窄的结论回应，不因此强制新增测试。

### 3.2 收尾条件与 `.forge/repair-result.json`

当每项分配的问题都有基于证据的处理结论，能够完成的修复和相关回归检查已经完成，且 `DESIGN.md` 与交付代码一致时，即可收尾。修复没有固定截止时间：围绕具体修复疑问继续深入，随后将未决事项与下一步有用检查交由独立复核，不扩展成无止境的全系统审计，也不以用完可用时间或排除所有设想问题为目标。

* **环境清理与格式规范**：停止自行启动的进程，清理临时资源，完整保留反馈材料。自动化测试放在 `tests/`，Markdown 段落不要使用段内换行。
* **写入 `.forge/repair-result.json`**：写入 `.forge/repair-result.json`，包含 `input_commit`、`action`（候选文件发生变化时为 `repaired`，否则为 `no_change`）、说明性的 `summary` 和 `issues`。每项问题须包含 `id`、`disposition`（`addressed`、`not_substantiated`、`unresolved`、`needs_specification`）与 `reason`。`summary` 和 `reason` 可为非空文本、列表或对象，控制字段须为字符串。
* **组织说明与最终汇报**：解释围绕**要求与原因、改动或不改的理由、前后证据、受影响行为与剩余问题**组织，合并共同解释并引用证据；无需额外报告或固定子字段。这些条目属于修复声明，而非最终关闭决定。最终说明实际改动、执行的命令与结果，以及检查局限。
