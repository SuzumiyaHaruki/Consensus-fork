# 使用保留的证据修复提供的候选实现

阅读提供的 protocol.md 和 system.md，以及 `.forge/feedback/handoff.json`、其中 `issues_file` 指向的文件，以及相关原始报告和复现。overview 用来导航，不是独立裁定。交接材料标明当前输入提交；较早的发现保留各自的来源提交。必须且只报告 `handoff.repair_issue_ids` 中的 ID，每项一次；对于没有该字段的旧交接，使用 `issues_file` 中的全部 ID。其他待处理问题作为规格背景。可选 `history_file` 保留已关闭问题、原始复现和复核新增证据，供选择相关回归检查。历史关闭结论适用于记录的复核版本，不会自动适用于当前候选。索引中的路径相对于 `.forge/feedback/`；原始记录仍保留相对于各自运行目录的路径。

对每项问题，检查所声称的要求、允许的输入和故障、场景可达性，以及其他可能解释。区分必需行为、理想模型下的结论和候选实现的声明。解释耗时时，将给定的通信、故障和计时假设应用于实际操作与事件；偏好的机制或未声明的性能目标不是要求。如果证据能够反驳发现，就保留符合要求的实现，不要只为迎合审计者的偏好而改代码。可行时，先运行原始复现，再修改代码。保留复现，并解释必要的小规模 API 适配；无法编译不表示问题已修复。阅读断言和 `polarity`：PASS 可能表示成功复现缺陷。

使用 `execution_records` 和 overview 定位保留的输入、命令及输出。`restore` 将工作区目标位置映射到输入文件；`outputs` 包含日志和选定输出文件；有记录时，`cwd_relative` 表示相对于源码的工作目录。可选 `evidence_index_file` 还可定位可复用案例、未解决问题，以及后续未完成调查产生的 `supplemental_turns`。补充材料保留修改文件和原始日志；使用之前先评估相关测试或修订解释，不能把草稿当作完成的报告或额外修复任务。复用前检查原始断言，以及替换实现代码的 overlay。重建临时二进制，解释路径或 API 适配；旧命令不一定可以直接移植。保留原始证据，在现有 reason 或证据引用中关联修改前后的检查。文件缺失或 API 过时属于复现限制，不是修复证据。

修复已确立的根因，同时保持协议和受支持的服务行为。自行选择修复机制并说明理由；审计者提出的方案不是强制要求。不要为测试特判、削弱断言或关闭必需功能。检查原始场景和有价值的相关情况，保留命令、输出及局限。按照 `AGENTS.md` 更新 `DESIGN.md` 中受影响的机制和限制。如果候选实现的性能声明没有依据，可能只需更正文档而不改变运行时行为；应将其说明为文档更正，而不是运行时修复。无论更正还是新增限制，都不能取消已提供的要求。

未规定的机制由你自行选择并继续工作；存在多个有效方案不需要研究者批准。证据支持拒绝该发现时，使用 `not_substantiated`；调查尚未完成时，使用 `unresolved`。只有必需行为缺失或相互矛盾、导致无法判断怎样修复才符合要求时，才使用 `needs_specification`；仅仅不确定自己的实现或计时推导，不属于这种缺口。指出缺失或冲突的规则，以及检查过的材料。不改写提供的材料，继续独立可做的修复，并指出真正依赖该缺口的问题 ID。即使代码未改，独立复核也会评估这些声明。委派工作和工作区边界遵循 `AGENTS.md`。

检查 diff，指出发生变化的机制和假设。除原始触发输入外，还应选择能够检查受影响行为及其交互的测试，包括之前成功、现在可能被拒绝、延迟或重复的操作。查阅相关已关闭历史和复核新增测试；不要求运行全部历史测试。检查每个断言实际说明什么：测试集通过或原始反例消失，可能仍没有检查受影响的要求。在现有 summary/reason 字段中解释，为什么选定检查能覆盖本次改动，以及哪些内容仍未检查。在 `DESIGN.md` 中新增限制，不能取消已提供的要求。

用证据、解释或更窄的结论回应 `evidence_feedback`。这些观察不是裁定，也不要求必须增加测试。对可变工作区中的检查，解释实际运行了哪个源码版本，以及轨迹观察如何支持结论；区分记录行为、准备行为和实现行为。

TCP 或多进程检查使用 `forge_local.isolated_exec`，选项见工具描述。默认 work 包含正在修改的修复版本；`source="candidate"` 选择原始输入。使用 `outputs` 在清理前保留选定的工作区相对路径文件或目录，并检查 `artifacts` 中的排除项。引用实际执行记录。可选调度、重放辅助工具 `../inputs/schedule.py` 提供 `--help`；它不验证协议计时或正确性。在 `isolated_exec` 中运行调度并保留输入；对捕获的源码副本，使用辅助工具的绝对路径。`--replay` 比较同一版本上的精确请求、响应；`--plan` 在不同版本上重复场景。保留原始记录并解释适配。检查适配器是通过公共 Node 接口进入，还是直接调用孤立协议状态转换，指出绕过的运行时行为；适配器不能补上实现缺失的行为。记录一致或原触发条件不可用，都不能说明问题已经修复。

根据本轮分配的问题和改动的影响判断何时完成。每项问题都有基于证据的处理结论，已确立的原因在可行范围内得到修复，已做相关修改前后对照和回归检查，设计说明与修复声明也符合交付代码时，就可以结束。修复已证实会破坏必需行为的回归。如果继续调查能解决具体修复问题，就继续；不要仅因为还能做更多检查，就扩展成新一轮全系统审计。如果一项声明仍缺乏依据、某项修复无法完成，或必需行为确实含糊，就记录适当的处理结论、证据和下一项有价值的检查，然后交付独立复核。修复阶段没有固定截止时间；不要在没有具体问题时不断迭代，也不要为了证明普遍正确而迟迟不交付已有价值的结果。

写入 `.forge/repair-result.json`，包含 `input_commit`、`action`（候选文件发生变化时为 `repaired`，否则为 `no_change`）、说明性的 `summary` 和 `issues`。每项问题需要 `id`、`disposition`（`addressed`、`not_substantiated`、`unresolved`、`needs_specification`）和说明性的 `reason`。Summary/reason 可以使用非空文本、列表或对象；控制字段使用字符串。可以补充解释和证据引用，无需固定标题。以独立复核者能够使用的形式说明相关修改前后检查、改动和剩余风险。这些是修复方的声明，不是关闭问题或暂缓处理的决定。

保持反馈材料完整，回归测试放入 `tests/`。复核者会收到修改前后候选、你的声明、反馈和保留的隔离执行记录。最终回复说明实际改动、命令及结果，以及剩余局限。有限测试不能证明一般性的安全性或活性。
