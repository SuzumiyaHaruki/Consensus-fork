# 系统要求

依据 [protocol.md](protocol.md) 实现一个可运行的 Go 语言复制状态机 KV 系统。在严格满足以下系统与协议约束的前提下，架构设计、数据结构、内部接口、并发模型及调度策略由实现端自行选择。

## 1. 服务与配置

* **模块名称**：`example.com/epaxos`。
* **交付组件**：可复用的共识 `Node` 库、独立服务端进程、真实网络传输层、客户端库与 CLI 工具、自动化测试套件及完整文档。
* **键值操作**：通过共识执行确定性的单键 `Put`、`Get` 和 `Delete`。说明各操作的输入、执行效果、返回值和错误语义。
* **集群配置**：支持配置成员名单、各副本网络地址及协议参数；副本总数 `N` 由成员名单自动确定，所有参数须满足 [protocol.md](protocol.md) 的约束条件。
* **并发接入**：系统须支持多个独立客户端并发发起请求，并允许多个副本同时作为入口接收客户端请求。

## 2. 客户端请求与结果

### 2.1 身份、接纳与跨入口去重

* **唯一请求标识 (`rid`)**：每个客户端会话必须拥有全局唯一身份，并在并发场景下分配互不重复的 `RequestSeq`（组成请求标识 `rid`）；具体分配与编码方式自行选择。
* **接纳前校验**：在请求进入共识接纳阶段前，拒绝格式错误的输入以及已知的矛盾 `rid` 复用（如相同 `rid` 携带不同命令）；合法命令的执行不得依赖任何被拒绝的输入。
* **同入口重试**：客户端重试必须保留原 `rid` 与完整命令。若同一副本入口收到尚未执行完毕的重复请求，应复用已有的实例，不得重复创建共识实例（具体等待与通知方式自行选择）。
* **跨入口重试与执行期去重**：若客户端切换至其他副本入口重试，新入口在本地未见过该 `rid` 时可正常接纳并创建对应的共识实例。这些实例共享同一条去重记录，因此彼此冲突。每个副本都处理这些实例，按 `rid` 至多应用一次命令。

### 2.2 返回结果与状态语义

客户端与服务端接口必须清晰区分以下五种结果状态（具体状态码与类型定义自行选择）：**接纳前拒绝**、**尚未完成**、**实际应用结果**、**`ALREADY_EXECUTED`（已执行重复）**、**结果未知**。“尚未完成”表示该入口确认已接纳请求或已将其关联到在途请求，此次尚无执行结果可返回。调用方无法确定请求结果时（例如回复丢失），报告“结果未知”。

* **首次执行与原结果交付**：请求首次在状态机执行后，向当前正在等待该请求的客户端返回实际应用结果；对已经准备发送的原结果回复，继续向该次请求的等待者发送。
* **已执行重复请求**：对于确认已执行过的重复请求，后续重试一律返回 `ALREADY_EXECUTED`（不包含原结果）。在请求实际执行前，严禁返回该状态。
* **依据执行记录判定**：是否已执行必须依据权威的执行记录判定，绝不能因为结果缓存缺失或被淘汰而重新执行同一请求。

### 2.3 等待、取消与客户端重启

* **超时与退避**：客户端的等待超时与重试退避策略自行选择。一旦请求已被副本接纳，即使客户端超时或停止等待，服务端也应继续推进该实例直至完成；是否提供主动取消等待接口、是否允许撤销已排队但尚未接纳的请求，由实现端自行决定。
* **客户端重启**：客户端重启时若丢失了原有的会话身份与请求记录，应获取新的会话身份以发起新操作；不要求客户端维护持久化的重启日志。

## 3. 真实运行时与可测试性

### 3.1 独立进程与运行资源

* **独立进程模型**：每个副本运行在独立的操作系统进程中，拥有独立的 Go 运行时与独立的资源配置（即使多个副本部署在同一台物理机上也是如此）。
* **资源参数区分**：在文档中明确区分**协议 worker 数量**、**进程级 `GOMAXPROCS`** 以及**实际分配的 CPU 核数/配额**，说明各自控制的资源边界与调度行为。
* **故障模型**：采用 crash-stop 故障模型，存活副本在内存中保存状态与数据，不要求支持磁盘持久化后的崩溃重启。

### 3.2 并发、并行与进度推进

* **多实例并发推进**：`Node` 启动后依靠真实时钟自主运行，同时推进多个共识实例，协调处理协议消息、定时器事件与状态机应用。当某个实例在等待网络回复或缺失数据时，其他就绪实例与后台任务必须能够继续推进，不得被全局阻塞。
* **副本内多核并行**：提供可配置的任务并行度上限。在 CPU 资源充足且协议允许的前提下，同一副本必须能够在多个 CPU 核心上**同时**处理不同共识实例的正常路径工作（包括处于相同共识阶段的协议消息处理）。
* **共享状态串行化与不变量**：对必要的共享状态可以采用串行或细粒度同步处理，但必须严格维护协议要求的原子状态转换、当前权限检查（如 ballot 与副本角色权限）、执行顺序、依赖关系、本地接纳规则以及多实例/请求间的公平进度。队列、协程/线程模型、锁粒度、任务生命周期、重试、缓存及证据获取机制由实现端自行选择。
* **生命周期与过载控制**：支持优雅关闭节点、过载保护以及 [protocol.md](protocol.md) 规定的接纳调度；在文档中说明上述每种操作对**尚未接纳**与**已经接纳**请求的具体影响。

### 3.3 网络、边界与时间假设

* **可替换传输与信任边界**：网络传输层必须抽象可替换，使共识组件能够脱离真实 socket 运行（如内存通道）。明确定义可信集群边界，将配置中的成员身份与底层连接/消息的实际来源绑定；编解码须完整保留身份与载荷信息，严禁仅凭未经核对的消息内身份字段信任发送方。
* **消息完整性**：自行选择编码格式与发送方式，但必须保留每条逻辑消息的发送者、接收者、实例 ID、ballot、阶段及对应处理规则。若省略了部分信息，接收方必须能从匹配上下文中无歧义还原，或在使用前按协议要求重新获取。
* **恢复计时**：说明实现如何识别迟迟未完成的实例，以及何时重试或发起恢复。

### 3.4 受控运行与观测

* **控制与观察接口**：暴露对虚拟/受控时间、消息交付（如延迟、丢弃、重排）及相关运行时事件的调度控制与观测接口，并提供通过真实 `Node` 或服务入口运行的受控测试示例。
* **共用核心实现**：受控运行与普通运行必须共用同一套核心协议实现。在文档中说明受控模式下实际经过的代码路径，以及被替换或绕过的外部机制（如替换时钟源、绕过真实网络 socket）；不要求对每一个内部 goroutine 进行细粒度控制。

## 4. 性能与验证

### 4.1 历史增长与资源治理

* **历史扩展效率**：随着已保留历史记录的增长，普通请求仍须保持高效处理。在严格遵守协议规定的冲突检测、依赖追踪与数据保留语义的前提下，及时清理和释放不再需要的临时状态。
* **排队限制与过载降级**：对排队长度与并发工作量设置上限。当系统处于过载状态时，通过调节新请求的接纳速率进行背压控制，确保已接纳的共识实例与关键后台任务（尤其是缺失数据请求及其回复的处理）仍能持续向前推进。

### 4.2 负载测试与统计口径

系统应在并发负载下争取较高的持续吞吐量和较低的客户端延迟。提供可复现的压测报告，展示随着负载增加，客户端每秒收到的成功执行回复数（吞吐量）、从发出请求到收到回复的端到端延迟，以及各副本的资源占用变化。明确说明**目标并发度**与**实测共识并发度**（按全系统已接纳但尚未决定的实例总数计量）。

验证报告必须包含以下维度的量化数据：

* **发送与完成稳定性**：实际请求发送速率、资源配置参数、所有指标的计量单位、统计样本范围与测量时间窗口。对于持续吞吐测试，说明完成速率是否能够稳定维持，以及运行期间系统内未完成的实例或积压请求是否持续累积。
* **按回复状态分类统计**：按实际收到的回复状态分类统计成功、接纳前拒绝、客户端超时、结果未知等各自的数量，以及观察截止时仍在等待回复的请求数。
* **停止施压后的排空观测**：停止发送新请求后，对系统内已有工作的继续观测结果，包括持续观测时长以及观测结束时仍未完成的工作量。
* **历史规模开销与限流影响**：分析普通请求、依赖展开与缺失数据获取的时间、网络通信及内存开销如何随历史规模增长而变化，以及资源上限/过载控制对已接纳请求的具体影响。

### 4.3 并行度与多进程部署验证

* **并发与串行路径剖析**：说明并展示同一副本在普通请求路径中哪些共识步骤实际在多核上并行运行，以及哪些共享状态操作必须串行处理。
* **多档并行度对比**：在可比负载条件下，对比不同任务并行度配置下的系统吞吐量、客户端延迟与副本 CPU 使用率。
* **真实多进程基准**：所有部署性能结论必须基于真实多进程运行测得，并如实记录测试环境的可用硬件资源。

## 5. 交付与文档

* **离线构建与运行环境**：支持完全离线构建，随交付物提供全部所需的第三方依赖。依据正确性、运行时开销与实现复杂度审慎选择依赖库、网络传输与编解码方案。服务端与客户端须支持通过常规命令行启动，默认绑定本地回环地址。
* **可参数化测试套件**：所有自动化测试统一放置在 `tests/` 目录下，支持通过 `go test ./...` 一键运行。保留实际验证使用的可运行测试与命令；进程与运行时配置、负载规模、压测持续时间及随机种子等参数须支持在另一台机器上灵活调整，无需修改测试源码。
* **文档要求 (`README.md` 与 `DESIGN.md`)**：
  * **`README.md`**：
    * 完整说明配置项、对外接口、KV 与状态码语义、系统正常运行的前提条件，以及本地多进程集群的构建、启动、使用和清理命令。
    * 提供可运行的集群配置示例。性能测量按可用 CPU 选择满足协议参数约束的副本数。提供并发客户端压测示例，并演示同一请求的重试，区分首次执行结果、`ALREADY_EXECUTED` 和结果未知。
  * **`DESIGN.md`**：
    * 阐述实际的系统架构、状态归属与并发边界、核心接口及关键设计权衡，涵盖恢复计时与重试行为、冲突索引结构、依赖展开、缺失数据获取以及历史数据保留机制。
    * 如实记录已执行的验证检查与本机测试覆盖范围、尚未执行的大规模实验、未能满足的需求项以及已知系统限制（记录限制有助于透明评估，但不能免除任何系统要求）。
