# 系统要求

将 `protocol.md` 和 `pseudocode.md` 实现为可运行的 Go 复制键值系统。两份文档定义协议规则和假设；本文定义目标服务、运行时能力和交付物。三份文档共同适用。不要替换成其他共识算法。

## 服务与配置

交付模块 `example.com/mixepaxos`：可复用的共识 Node 组件、独立服务进程、真实网络传输、可复用客户端接口和 CLI、测试及文档。支持多个独立的并发客户端。可配置成员身份和地址、一致的配置身份、符合协议关系的 n/f/s/W/e/K/J，以及实现的调度设置。优先使用标准库，以便离线构建。默认使用回环地址；普通服务端和客户端程序必须能独立于 Codex 或私有测试工具运行。

通过共识实现确定性的单键 Put、Get 和 Delete，按照 protocol.md §4.1 说明结果、错误和冲突分类。客户端与服务接口应一致地体现 §§3、7、9.6 中的请求身份、执行、重试和保留语义。服务保证及其前提以 §10 为准。区分接纳前拒绝、应用执行结果和未知结果。在接纳前拒绝格式错误的输入和已知的矛盾请求复用，不得破坏合法工作或创建对被拒绝输入的依赖。具体编码和客户端等待、退避策略由实现选择。

采用 protocol.md §§2、3、9、11 中的故障、恢复和存储范围。通用存储引擎和部署平台不在范围内。

## 运行时能力

Node 启动后应使用真实时间自行推进后台工作；普通使用时不由应用手动 tick 或推动状态转换。支持并发客户端请求、入站消息、定时器和应用工作。传输应可替换，共识组件应能在不使用 socket 的情况下使用。提供取消和关闭接口，并说明它们以及背压、接纳暂停对排队中、已接纳和已发出工作的影响。其他工作等待期间，后台推进仍须满足给定协议规则。

编解码应保留身份和载荷。在各组件间一致地选择、校验未规定的表示方式和数值范围。在明确的可信集群边界内，将配置中的成员身份绑定到实际消息来源；仅信任未经校验的载荷字段不够。不要求拜占庭容错或生产 PKI。这些选择应符合 protocol.md 的证据与信道模型。

提供有文档说明的时间、消息交付及相关运行时事件控制和观察接口，并给出通过真实 Node 或服务接口进入的可运行示例。受控执行与普通运行必须使用同一协议实现。示例应说明实际经过哪些运行路径、替换或绕过哪些机制。不要求控制每个 goroutine。

## 交付

提供服务端和客户端命令、可用 `go test ./...` 运行的自动化测试，以及本地多进程集群的构建、启动、使用和清理说明。包含协议的七成员参数示例、并发客户端和同请求重试。展示执行结果，并按协议一致地呈现未知结果。

README 应说明配置、应用和客户端接口、命令、服务语义、运行条件和已知限制。`DESIGN.md` 应说明交付实现的架构、状态归属、重要接口和影响行为的实现选择。说明资源限制及其对客户端和已接纳工作的影响，包括 protocol.md §§9、11 中的保留状态和检查点开销。不规定固定基准测试或吞吐量目标。报告实际检查、未满足的要求和剩余限制；不能通过记录限制来取消给定要求。
