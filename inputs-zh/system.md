# 系统要求

将 [protocol.md](protocol.md) 中的协议实现为可运行的 Go 复制键值系统。协议材料定义合法决定、执行和历史替换规则；本文定义服务能力、工程成本与交付目标。实现端自行设计满足这些要求的架构、数据结构、并发机制和接口。

## 1. 服务与配置

交付模块 `example.com/mixepaxos`，包括可复用共识 Node、独立服务进程、真实网络传输、客户端库与 CLI，以及测试和文档。支持多个独立并发客户端。成员身份与地址、共同配置身份和 n/f/s/W/e/K/J 可配置，并满足 protocol.md 的参数关系。

通过共识实现确定性的单键 Put、Get、Delete。说明参数、返回结果、应用错误和冲突分类，访问描述须与真实操作一致。格式错误及已知矛盾 rid 复用在接纳前拒绝，不能让合法命令依赖被拒绝的输入。客户端会话身份必须唯一，RequestSeq 并发分配不重复，具体分配与编码方式由实现选择。

一次运行不设置固定请求总数上限，应能不断完成检查点并进入后续 epoch。J 是每个 origin 的单 epoch 分配上限，不是整个系统的请求总数限制。支持协议中存活落后副本的检查点同步；不要求动态成员、崩溃副本重启或重新加入、任意网络分区恢复。

## 2. 客户端结果与重试

首次执行向当时等待该请求的客户端提供实际应用结果。已经执行的重复请求可以直接返回 ALREADY_EXECUTED，不必永久保存或重新提供原结果。这个状态只确认先前发生过执行，不保证原应用操作成功，也不提供读取结果。回复丢失后，客户端可能无法找回那次操作的结果。

区分接纳前拒绝、处理中、应用结果、ALREADY_EXECUTED 和结果未知。只知道请求已经排队或接纳时，合并等待或报告处理中，并继续推进，不能称其已经执行。入口本地不知道的 rid 可以正常接纳，但状态机执行仍须去重。具体状态码和接口表示由实现选择。

超时或取消不撤销已经接纳的工作。换入口重试保留原 rid 和完整命令；收到 ALREADY_EXECUTED 后不得为了找回结果自动换新 rid 重做。客户端等待和退避策略由实现选择，不承诺固定回复截止时间。客户端重启时若丢失原身份与请求记录，取得新身份开始新操作；不要求实现客户端持久重启日志。

跨 epoch 根据执行记录判断请求是否完成。已经执行的请求可以结束等待并返回 ALREADY_EXECUTED；已经准备交付的原结果回复继续正常交付。尚未执行的请求保留身份和命令，公平进入下一 epoch。结果缓存缺失不构成重做依据。等待者管理、回复缓冲和可选结果缓存由实现设计，与规范检查点状态分开。

## 3. 真实运行时与可测试性

Node 启动后使用真实时间自主推进，普通应用不需要手动 tick 或驱动协议转换。支持并发客户端、协议消息、定时器和应用执行；等待某项工作时，其余必需工作仍能推进。传输可替换，共识组件可在不使用 socket 的情况下运行。

自行选择队列、线程、锁、任务生命周期、重试、缓存及证据获取机制，同时保持协议要求的原子转换、当前权限检查与公平进度。提供取消、关闭和背压接口，说明它们对排队、已接纳及已发出工作的影响。

在明确的可信集群边界内，将配置成员身份与实际消息来源关联，编解码保留身份和载荷；不能只信任未经核对的消息内成员字段。不要求拜占庭容错或生产 PKI。解释实际计时和发送机制如何对应 protocol.md 的窗口及心跳前提；本地队列入队或函数返回的名称本身不建立这些前提。说明运行条件及可检测的局部违例，不把它们当作全局窗口证明。

提供时间、消息交付和相关运行时事件的控制与观察接口，并给出通过真实 Node 或服务入口执行的可运行示例。受控与普通运行使用同一协议实现；说明示例经过哪些真实路径、替换或绕过哪些机制。不要求控制每个 goroutine。

## 4. 历史增长与检查点成本

普通冲突查询应利用相关域的索引和前沿，避免每次扫描全部历史；当前 epoch 内的 Validate 完整义务与必要恢复证据仍必须保留。已有证据的副本之间传递必要新增材料，避免在普通消息中递归打包全部累计证明；缺失材料的获取成本应单独说明。

检查点逻辑上表示完整状态，物理上应增量构造：复用未改变的数据并处理本 epoch 的变化，不能每代重建、复制或重新编码全部累计应用及去重状态。向已有所需基座的副本传输变化部分；缺少基座的副本可能需要完整状态传输，其成本另计。具体快照结构、共享方式、认证材料组织及回收算法由实现设计。

回收不再需要的旧快照数据，避免无限期为每代保留独立完整累计副本。必须保留当前状态、跨 epoch 去重、必要父链验证、落后副本同步和未完成操作所需的材料。永久精确结果档案不属于要求；去重记录、应用数据和协议必需证据仍可能增长，不能把某个局部结构有界解释成总内存有界。

限制重复的物理排队与在途工作，同时保持已接纳义务和公平推进。快照准备可发生在 Store 前，但仍计入检查点总延迟；Store 调用内的工作仍属于其 W。说明资源限制、检查点暂停及冷状态传输对客户端和已接纳工作的实际影响。这里不规定特定吞吐数字、数据结构或通用存储引擎；crash-stop 模型允许存活副本在内存中保存数据，不要求磁盘重启持久性。

## 5. 交付

优先使用标准库，支持离线构建。默认使用回环地址。提供普通命令即可启动的服务端和客户端，不依赖 Codex 或私有测试工具。自动化测试放在 `tests/`，可用 `go test ./...` 运行。

README 包含配置、接口、服务语义、运行条件及本地多进程集群的构建、启动、使用和清理命令。给出七成员参数示例、并发客户端和同请求重试的用法，展示应用结果与重复、未知状态的区别。

`DESIGN.md` 说明交付实现的架构、状态归属、重要接口和影响行为的选择，包括计时、证据保留、增量快照与回收。报告实际检查、未满足要求和已知限制；记录限制不能取消给定要求。生成、审计和修复的工作方法由各自角色提示定义，不在本文件规定固定开发或测试步骤。
