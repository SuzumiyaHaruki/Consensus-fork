# 系统要求

依据 [protocol.md](protocol.md) 实现可运行的 Go 复制 KV 系统。满足以下要求的架构、数据结构、接口、并发和调度机制由实现端选择。

## 1. 服务与配置

- 模块：`example.com/mixepaxos`。
- 组件：可复用共识 Node、独立服务进程、真实网络传输、客户端库与 CLI、测试和文档。
- 操作：通过共识执行确定性的单键 Put、Get、Delete，说明输入、执行效果、返回值和错误含义。
- 配置：成员名单、各副本地址及 f/s/W/e；n 由成员名单确定，参数满足 protocol.md。

支持多个独立客户端并发请求，以及多个副本同时接收请求。

## 2. 客户端请求与结果

### 2.1 身份与接纳

客户端会话身份唯一，并发分配 RequestSeq 不重复；分配和编码方式自行选择。接纳前拒绝格式错误及已知矛盾 rid 复用，合法命令不能依赖被拒绝的输入。

重试保留原 rid 和完整命令。同一入口对未执行请求复用已有工作，不重复创建实例；等待和回复方式自行选择。换入口时，本地未知的 rid 可以接纳，不同入口可创建不同实例，执行时按 rid 去重。

### 2.2 返回结果

接口须区分接纳前拒绝、尚未完成、实际应用结果、ALREADY_EXECUTED 和结果未知，具体状态码与表示自行选择。

- 首次执行后，向当前等待该请求的客户端返回实际应用结果；已准备交付的原结果继续发送。
- 已执行的重复请求返回 ALREADY_EXECUTED，本次不包含原结果；执行前不能返回该状态。
- 根据执行记录判断是否已执行，不能因结果缓存缺失而重做。

### 2.3 等待、取消与重启

客户端等待和退避策略自行选择。超时或停止等待后，已接纳工作继续推进；是否提供主动取消等待接口、是否允许撤销未接纳的排队请求，自行决定。

客户端重启时若丢失原身份与请求记录，取得新身份开始新操作；不要求客户端持久重启日志。

## 3. 真实运行时与可测试性

### 3.1 部署与运行资源

每个副本运行在独立进程中，拥有独立 Go 运行时，并可分别配置运行时参数；多个副本部署在同一机器上时也如此。区分协议 worker 数量、进程级 GOMAXPROCS 和实际 CPU 分配，说明各项配置控制什么。

crash-stop 模型允许存活副本在内存中保存数据，不要求磁盘支持崩溃后重启。

### 3.2 并发、并行与进度

- 多实例推进：Node 启动后使用真实时间自主运行，同时推进多个共识实例，处理协议消息、定时器和应用执行。某实例等待网络回复或缺失数据时，其他可推进实例与后台任务继续处理。
- 副本内并行：提供可配置的任务并行度上限。CPU 资源足够且协议允许时，同一副本能在多个核上同时处理不同实例的正常请求路径共识工作，包括相同阶段的协议消息处理。

必要共享状态可串行处理，须保持协议要求的原子转换、当前权限检查、顺序、依赖关系、本地接纳规则和公平进度。队列、线程、锁、任务划分与生命周期、重试、缓存及证据获取机制自行选择。

支持关闭节点、过载处理和 protocol.md 的接纳调度，说明各操作对未接纳、已接纳请求的影响。

### 3.3 网络与时间

传输层可替换，共识组件可脱离 socket 运行。明确可信集群边界，将配置成员身份与实际消息来源关联；编解码保留身份和载荷，不能只信任未经核对的消息内成员字段。

允许连接复用、流水化发送和同帧打包多条逻辑消息，但须满足：

- 保留各消息的发送者、接收者、实例、ballot、收集与阶段身份及处理规则。
- 缓冲和排队计入协议规定的相应时间界。
- 每实例仍只有一条逻辑请求，不将多条命令合成一个共识值。

设计副本通信时，考虑一次请求在协调过程中和后台分别触发哪些消息、接收方已经知道什么，以及双方准备、发送、等待和处理这些消息的成本。省略的信息应能从对应实例和请求上下文准确还原；缺少的数据须按协议要求取得后再使用。

说明真实计时和发送如何对应协议的窗口及心跳假设。入队或函数返回的名称本身不能证明假设成立；说明运行条件和可检测的局部违例，不将其视为全局窗口证明。

### 3.4 受控运行

提供时间、消息交付和相关运行时事件的控制与观察接口，以及经过真实 Node 或服务入口的可运行示例。受控与普通运行共用协议实现，说明经过的路径及替换、绕过的机制，不要求控制每个 goroutine。

## 4. 性能与验证

### 4.1 历史与资源管理

- 冲突查询、依赖展开和数据保留遵循 protocol.md。使用适当索引、增量处理，复用数据及已完成检查，避免每次请求或后台唤醒重处理全部历史，以及沿不同路径重复遍历、组装、传输共享依赖。
- 超龄检测可复用已有实例状态或索引，记录结构和检查方式自行选择。及时释放不再需要的临时状态。
- 限制排队和并发工作量，同时推进已接纳实例与后台任务。过载时调节新请求接纳，避免将主要资源花在反复准备无法入队或马上被丢弃的工作上。
- 等待缺失数据的任务不能占尽资源，须保留发送、处理 Fetch 请求及回复的能力。

队列、限额、缓存、编码和调度方案自行选择。

### 4.2 负载与统计

共识并发度指全系统已接纳但尚未决定的实例数，不用客户端等待请求数代替。区分目标与实测并发度，测量并发度增加时的吞吐、延迟和资源占用；负载和测试方法自行选择。评估持续吞吐量时，负载应持续到能比较前后时段的请求完成速率，并观察未完成请求是否持续积累。

报告应包括：

- 实际负载与资源配置、指标单位、统计的请求和时间范围。
- 按实际回复状态统计的成功、拒绝、超时、结果未知等数量，以及仍在等待回复的请求数。
- 停止新请求后对已有工作的继续观察，包括观察时长和未完成工作。
- 普通请求、依赖展开、缺失数据获取的时间、通信和内存开销如何随历史规模变化，以及资源限制对已接纳请求的影响。

需要解释明显延迟或目标与实测并发度差距时，使用低开销观察区分接纳前、决定前、执行前和回复前的等待。

### 4.3 并行与部署验证

通过正常 Node 路径，说明哪些主要协议步骤可以同时执行、哪些串行及原因。worker 数量、仅收发或辅助准备并行、测试屏障中的重叠、跨副本扩核收益，均不能单独证明副本内共识并行。

在可比负载下比较不同并行度配置的吞吐、延迟和副本 CPU 使用，区分实际并行证据与扩展收益，并说明本机资源限制。

同进程多 Node 可做功能和受控调度检查；目标部署性能结论须来自真实多进程运行，并说明资源条件。

## 5. 交付

支持离线构建，随交付提供所需第三方依赖。依据正确性、运行成本和实现复杂度选择依赖、传输与编码方案。服务端和客户端通过普通命令启动，默认使用回环地址。

自动化测试放在 `tests/`，通过 `go test ./...` 运行。保留实际使用的可运行测试和命令；相关进程与运行时配置、负载规模、持续时间和随机种子可在另一机器调整，无须改写测试逻辑。

文档内容：

- `README`

  - 配置、接口、服务语义、运行条件，以及本地多进程集群的构建、启动、使用和清理命令。
  - 七成员配置、并发客户端、同请求重试的用法，展示应用结果、重复和未知状态的区别。

- `DESIGN.md`

  - 实际架构、状态归属、重要接口与设计选择，包括计时、冲突索引、依赖展开、数据获取和保留。
  - 实际检查及本机覆盖范围、未执行的大规模测量、未满足要求和已知限制；记录限制不能取消要求。
