# 生成与修复实现要求

本文件说明生成和修复实现时应遵循的工作要求。具体任务分别见 `TASK.md` 和 `REPAIR.md`。`protocol.md` 和 `system.md` 是提供给你的协议与系统要求；`DESIGN.md` 由你编写，用来解释实际实现的结构、重要选择及其依据，并随代码一起更新。

## 工作范围

不要修改本次任务提供的材料。对于材料没有规定的实现细节，由你比较可行方案，选择最适合本任务的一种，并说明重要取舍。如果发现要求缺失、互相矛盾，或发现遵守给定规则仍会出错的具体场景，在 `DESIGN.md` 的未解决问题中写明相关条款、场景和已有依据。分清问题来自设计材料、实现代码，还是尚未完成的调查。

继续完成不受这些问题影响的工作。不要放宽协议要求，或额外依赖材料中没有承诺的外部条件。不要查看其他实验，也不要获取另一份共识实现来替代本次实现。

在提供的项目目录内编写和测试代码。你可以启动本地测试集群、运行客户端发送请求、让副本交换协议消息，以及模拟协议允许的故障。测试结束后，关闭自己启动的进程，清理临时资源，并保留需要交付的测试结果。

保留现有认证与沙箱保护。不要更改凭据、对外发布代码、部署到远程或生产环境、向第三方发送通信，或修改与任务无关的资源。不要把凭据写入代码和配置；本地测试使用回环地址。

可以使用原生 Codex 子智能体，沿用相同模型、推理强度、权限和预算。协调它们对共享文件的修改，汇总结果和证据，并在交付前结束或停止仍在运行的子任务。不要启动嵌套 Codex 会话或调用外部模型服务。

## 实现与设计说明

明确协议处理、运行时调度、传输、存储、应用和客户端各自的职责。自行选择代码布局与同步机制，说明哪些组件维护哪些状态，以及重要接口如何处理阻塞、重入、完成、取消和关闭。检查组件之间的交互，整理重复逻辑。

说明协议中的抽象动作在代码中由哪些入口和事件实现，以及并发执行时如何保持要求的原子性、顺序和持续推进。讨论时间保证时，计入相关假设覆盖的实际工作。函数与协议动作同名，或消息已经进入本地队列，都不能单独说明相应要求已经满足。

`DESIGN.md` 应帮助审阅者理解交付的代码，围绕以下内容组织：

- **系统结构：**说明模块职责、状态归属、请求经过的主要路径，以及哪些工作可以并发执行。
- **关键选择：**说明依据哪项要求、采用什么机制、相关代码在哪里、为什么这样能满足要求，以及已有检查支持到什么程度。对重要机制说明处理条件和生命周期，分清协议要求、外部假设与自己的实现选择。
- **检查与未解决问题：**说明做过哪些检查、哪些要求尚未满足、哪些行为还没检查，以及已知问题，并引用相关证据。

标题可以合并或调整，相关内容可以共用解释。重点解释影响行为的重要选择，不必复述协议、逐函数列清单或填充空章节，也不要求每项说明都单独配一个测试。分清推理与实际测试结果；详细调查过程和命令日志通过引用提供，不堆放在 `DESIGN.md` 中。

## 检查与执行

测试应经过实际的 Node 或服务处理代码。说明测试控制了哪些事件、替换或绕过了哪些组件；测试适配器不能补上实现缺失的消息发送或协议步骤，也不能隐藏实现中的失败。测试输入和故障须符合协议假设。区分测试要求执行的动作与实际发生的事件，说明断言能支持什么结论。等待一段时间仍未完成，不能单凭这一点认定系统永远无法推进。

保留失败的输入和结果，调查尚未解释的异常；后来一次测试通过，并不能解释此前为什么失败。在可比条件下，选择不同的负载或历史规模检查开销。模拟结果不能回答问题时，测量实际运行成本。定位开销增长的原因，优化时保留协议要求的工作和证据，并重新检查受影响行为。说明资源限制是在接纳前拒绝新请求，还是会影响已经接纳的请求。

TCP 或多进程测试使用 `forge_local.isolated_exec`，具体选项见工具说明。用 `outputs` 指定需要保留的文件，再查看 `result.artifacts`，确认它们是否保存成功。可选调度工具 `../inputs/schedule.py` 提供 `--help`；在隔离执行中使用，选择捕获的源码副本时通过绝对路径访问该工具。工具记录了事件或重放成功，都不能单独证明实现正确。

自动化测试放在 `tests/`。报告实际执行的命令、结果和检查局限。Markdown 段落不要段内换行。
