独立复核所提供问题的修复。在运行简报的只读 `review_context` 中阅读 `request.json`：它标明修改前后提交、问题 ID、修复声明、原始反馈，以及已有的修复执行记录。捕获的 `source/` 和可写的 `work/` 包含修改后版本。以 protocol.md 和 system.md 为要求。任何一方 agent 的声明都不自动正确。

必须且只复核 `request.issue_ids`。其他待处理问题，以及可选 `history_file` 和 `evidence_index_file`，仅提供规格、回归背景，不代表额外必须给出的处理结论，也不代表当前候选已经经过验证。即使代码没有变化，也要评估 `needs_specification`。真正的规格缺口是必需行为缺失或矛盾，导致无法判断实现是否符合要求；存在多个有效机制或调查不完整，都不足以构成缺口。如果没有这种缺口，应根据证据判断发现和修复，不要自动返回 `unresolved`。确认缺口后只暂缓该项问题，不授权削弱保证，也不阻碍独立可做的修复。

有帮助时，可在已有权限和预算内使用原生 Codex 子智能体开展独立检查，模型和推理强度保持相同。协调共享文件的修改并整合证据；完成回复前结束或停止委派的工作。不要启动嵌套 Codex CLI 会话，也不要调用外部模型服务。复核应独立于生成和修复。

对每项问题，检查要求或候选声明、场景是否合法且可达、原因，以及修改前后的实际行为。区分外部假设、理想模型下的结论和实现选择，将给定的通信、故障和计时假设应用于计时声明涉及的操作与事件。判断依据是必需行为，不是你偏好的架构、未声明的性能目标或审计者提出的修复方案。符合要求的选择可以保留不变；证据支持反驳发现时使用 `not_substantiated`，调查不完整时使用 `unresolved`。区分更正候选夸大的声明与修复运行时行为；修改文档不能取消已提供的要求。保留复现，解释适配，阅读断言和 `polarity`。确认观察能够支持结论，没有绕过必需行为，也没有由测试驱动补上该行为。说明检查和剩余不确定性。

独立阅读 diff，识别变化的机制和假设。核对受影响的协议流程是否保留规定的处理条件、消息义务及后续处理路径；不能仅凭原始反例消失或请求最终成功，就认定实现符合协议。选择原始触发输入以外的检查，有帮助时使用相关历史复现和复核新增测试。区分协议偏离、正确性错误与性能变化；需要判断改动影响时，检查可比条件下的修改前后开销。过去的关闭结论只对应其记录版本。如果变通修复破坏了必需行为，应保持该问题未解决并描述回归，即使尚未造成冲突决定或永久停滞。在现有字段中解释推理、检查和不确定性，不要求固定的回归清单。

TCP 或多进程检查使用 `isolated_exec`，选项见工具描述和简报。`source="before"` 和 `source="candidate"` 分别选择紧邻此次修复之前的版本和修复后版本；发现本身可能来自更早版本。用 `outputs` 在清理前保留选定的工作区相对路径文件或目录，并查看 `artifacts` 中的排除项。引用 `executions/<id>/result.json` 或其日志，关联执行与起始源码。可变工作区和普通 shell 检查仍可使用，但需解释源码版本；通过 `turns/<turn>/stdout.jsonl#<item_id>` 选择实际已完成的 shell 命令。整个回合的日志不能定位具体复核命令。记录证明执行事实，不证明断言有效或与所述语义有关。

通过 `execution_records` 复用证据：`restore` 定位保留的输入，`outputs` 定位日志和选定输出文件，有记录时 `cwd_relative` 表示相对于源码的目录。路径相对于反馈包。检查原始命令、断言和替换实现的 overlay，重建临时二进制，并解释适配。保留场景和断言含义。输入缺失、适配器损坏或 API 过时属于复现限制，不代表缺陷已修复。

用证据、解释或更窄的结论回应 `evidence_feedback`。简报列出提供 `--help` 的可选调度、重放工具；在 `isolated_exec` 中运行调度并保留输入、输出。`--replay` 比较同一版本上的精确记录；`--plan` 在不同版本上重复场景。检查适配器通过公共 Node 接口进入，还是直接调用孤立协议状态转换，并指出绕过的运行时行为。计时和故障应在假设内，不能在驱动中修正候选的 bug。重放一致不能证明符合给定假设、场景可达或实现正确；有限等待本身不能否定最终进展保证。

保留 `report.md`、复现和输出。每完成一项问题检查，先保存报告和对应 `review.json` 条目，再开始额外调查。对于尚未检查的工作，应保留不确定性，不要为使中间文件看起来完整而编造观察或结论。最终回复前，`review.json` 必须包含 `before_commit`、`after_commit`、说明性的 `summary`，并且 `issues` 恰好包含提供的那些问题 ID。每项问题需要 `id`、`disposition`（`fixed`、`unresolved`、`not_substantiated`、`needs_specification`、`environment_blocked`）、`reason`、`method`（`executed`、`source_review`、`blocked`）、`before_observation`、`after_observation` 和非空 `evidence`。提交、ID 和控制字段使用字符串；说明性字段可以使用非空文本、列表或对象。证据路径指向保留的 `work/`、`executions/` 或 `turns/` 文件。保留的轨迹、日志和 JSONL 应在 `evidence` 中引用；控制器不验证其协议语义。其他解释自由组织。

`fixed` 声明要求独立运行修改后版本，并关联本次复核中已完成的命令。仅有文字说明或修复方的执行不够。使用上述保留的执行或原生命令路径，解释被测版本和所做修改，尤其是使用可变工作区时。控制器检查记录是否存在、是否有明确版本不匹配，不判断命令断言是否足以支持结论。如果无法执行，保留 `unresolved` 或 `environment_blocked`。`blocked` 不能关闭问题；明确的源码推理可以用 `not_substantiated` 反驳不成立的发现。所有处理结论仍是 agent 的报告。将重要疑点、已排除解释和修订结论的原因保留在报告中，供后续审阅。

报告全部指定问题后结束。若另有证据充分的独立缺陷，放入可选 `new_issues`，使用说明性的本地 `id`、`summary`、`property`、`assumptions`、`reproduction`、`polarity` 和非空 `evidence`，遵循相同的证据路径规则。这些描述修改后的候选，并进入普通问题列表。是否继续修复或发现新问题，取决于剩余修复轮次和工作流所处阶段；本次复核可能是最终阶段。推测性疑虑保留在报告中，并说明不确定性。如果某项修复只是引入相关回归，不要再复制一个已指定的问题。

可以在 `review.json` 顶层 `cases` 中保留可复用检查，每项包含 `summary`、`reproduction` 和非空 `evidence`，并在这些说明或额外字段中解释范围、假设和断言含义。可选顶层 `open_questions` 记录未解决的规格或调查问题及其背景。这些字段用于后续修复导航，即使案例未发现缺陷也可保留；它们既不关闭问题，也不增加必须给出的处理结论或额外轮次。
