# 实现共识系统与工程规范

完整阅读 `protocol.md` 与 `system.md`，实现其中要求的完整系统。最终须交付可运行程序、可复用组件、自动化测试与文档；不能只交付实现计划、共识代码包或局部库。

## 1. 工作范围与边界

### 1.1 需求遵守与待澄清问题

* **不修改既有材料**：不要修改 `protocol.md`、`system.md` 或其他提供的材料。对于材料未明确规定的实现细节，请比较可行方案，选择最适合本任务的一种，并说明关键取舍。
* **不放宽协议与不依赖额外假设**：不要放宽协议要求，也不要额外依赖材料未承诺的外部条件。不要查看其他实验，也不要获取另一份共识实现来替代本次实现。
* **如实记录问题并继续推进**：若发现要求缺失、互相矛盾，或发现严格遵循给定规则仍会出错的具体场景，请在 `DESIGN.md` 的未解决问题中写明相关条款、场景与已有依据。注意区分设计材料的问题、实现缺陷以及尚未完成的调查，并继续推进不受这些问题影响的工作。

### 1.2 工作目录、安全与子智能体协作

* **目录与环境清理**：在给定项目目录内编写并测试代码。可启动本地测试集群、运行客户端发送请求、让副本交换协议消息，以及模拟协议允许的故障。测试结束后，关闭自行启动的进程，清理临时资源，并保留交付所需的测试结果。
* **安全与网络边界**：保留现有认证与沙箱保护。不要更改凭据、对外发布代码、部署到远程或生产环境、向第三方发送通信，或修改无关资源。不要把凭据写入代码和配置；本地测试使用回环地址。
* **子智能体使用规则**：可使用原生 Codex 子智能体，沿用相同的模型、推理强度、权限与预算。协调它们对共享文件的修改，汇总结果与证据，并在交付前结束或停止仍在运行的子任务。不要启动嵌套 Codex 会话或调用外部模型服务。

## 2. 增量构建与设计说明

### 2.1 按可运行增量推进

* **先通闭环再扩能力**：先在 `DESIGN.md` 中写一份简要的实现方案，再随着代码逐步完善。先打通单条请求从客户端接入、副本通信、共识决定、状态机执行到返回结果的完整闭环；再在同一套实现上逐步补齐所需的并发、故障处理与生命周期行为。这种推进顺序不减少最终交付范围。
* **关注交互与代码结构**：添加功能时检查各组件之间的交互，并在交付前审阅代码组织结构，清理重复逻辑。

### 2.2 组件职责与协议动作映射

* **明确职责与接口行为**：清晰划分协议处理、运行时调度、传输、存储、应用与客户端各自的职责。自行选择代码布局与同步机制，说明各组件维护哪些状态，以及重要接口在阻塞、重入、完成、取消与关闭时的行为。
* **对齐协议动作与时序假设**：说明协议中的抽象动作在代码中对应哪些入口与事件，以及并发执行时如何维持要求的原子性、顺序和持续推进。讨论时间保证时，应计入相关假设覆盖的实际工作；仅凭函数与协议动作同名，或消息已进入本地队列，都不足以说明相应要求已经满足。

### 2.3 `DESIGN.md` 组织规范

`DESIGN.md` 应随代码同步更新，帮助审阅者理解交付的代码，建议围绕以下内容组织：

* **系统结构**：说明模块职责、状态归属、请求经过的主要路径，以及哪些工作可以并发执行。
* **关键选择**：说明对应哪项要求、采用什么机制、代码位置在哪、为何满足要求，以及现有检查的支持程度。对重要机制说明触发条件与生命周期，并说明普通请求与后台工作的成本如何随成员数、并发实例数和历史规模变化。区分协议要求、外部假设与自主实现选择。若实测发现瓶颈，说明依据哪项观察保留或调整了当前方案，以及哪些备选方案尚待验证。
* **检查与未解决问题**：说明已完成哪些检查、哪些要求尚未满足、哪些行为尚未覆盖，以及已知问题，并附证据引用；同时说明观察到的主要性能成本及归因依据。

标题可根据需要合并或调整，相关内容可共用解释。重点说明影响行为的关键选择，不必复述协议、逐函数列清单或填充空章节，也不要求每句说明都单独对应一个测试。分清推理与实测结果；详细调查过程和命令日志通过引用关联，不要堆放在 `DESIGN.md` 中。

## 3. 检查、性能排查与自查

### 3.1 运行条件与测试规范

* **资源评估与协调**：开展资源敏感测试前，先检查可用 CPU、内存、进程布局与运行时配置。按实际资源确定负载规模，保留真实多进程检查，并协调重型测试（包括子智能体启动的测试）。报告每个副本的 `GOMAXPROCS`，它限制该进程中能同时执行 Go 代码的 goroutine 数量。说明各副本共享哪些逻辑 CPU，或分别绑定到哪些 CPU。
* **贴近真实路径与协议假设**：测试应经过实际的 `Node` 或服务处理代码。说明测试控制了哪些事件、替换或绕过了哪些组件；测试适配器不得补发缺失的协议消息、代为推进缺失的状态转换，也不得掩盖实现中的失败。测试输入与故障须符合协议假设。
* **严谨解读断言与等待**：区分测试要求执行的动作与实际发生的事件，说明断言能支持什么结论。等待一段时间仍未完成，不能单凭这一点认定系统永远无法推进。

### 3.2 性能调查、缺陷排查与自查

* **梯度施压与针对性测量**：选取有代表性的普通负载，在固定资源下逐步提高实际发送速率，对比不同时间段内的执行回复速率、延迟与未完成工作，直到出现性能瓶颈，或当前机器资源、负载发生器已达上限而无法继续判断。
* **定位延迟与额外开销**：优先排查已经出现的运行异常，以及即使在请求全部成功时也明显影响性能的现象。沿真实请求路径追查最有依据的线索：对于等待延迟，定位其发生在提交、接纳、决定、执行与回复中的哪两个阶段之间；对于额外开销，追踪单次请求在各副本及后台触发的工作，留意接收方已有的数据或反复处理的历史。针对具体疑问选择能够区分原因的观测方式。
* **对照验证与收敛时机**：当证据指向某项明显影响表现的实现选择时，在可比负载与资源下做一次有针对性的改动，依据对照结果决定保留还是调整原方案；同时检查协议要求的工作是否仍能完成，包括原本在本地或当前阶段处理、后被转移到其他副本或推迟执行的步骤。当现有证据足以决定保留或调整实现，或继续判断已超出当前测试环境的条件时，结束本轮性能调查并记录仍不确定的部分。
* **区分问题类型与集中自查**：注意区分实现缺陷、不成立的测试假设和尚无定论的问题。测试失败或运行条件变化时，保留原始输入与观测结果，并在 `DESIGN.md` 中记录结论与局限；若测量差异不足以支撑取舍，再有针对性地复测。将候选版本交由独立审计前，做一次集中自查，修复确认的缺陷并检查受改动影响的行为。

### 3.3 测试工具与结果保留

* **隔离执行与产物确认**：TCP 或多进程测试请使用 `forge_local.isolated_exec`，具体选项见工具说明。用 `outputs` 指定需保留的文件，并检查 `result.artifacts` 确认是否保存成功。
* **调度辅助工具**：可选调度工具 `../inputs/schedule.py` 提供 `--help`；在隔离执行中使用捕获的源码副本时，通过其绝对路径调用该工具。工具记录了事件或重放成功，都不能单独证明实现正确。

## 4. 交付收尾与格式要求

当所需功能集成完毕、针对重要实现风险的检查已完成，且代码、`DESIGN.md` 与运行说明保持一致时，即可收尾。达到这些交付条件即可收尾，不以用完可用时间或排除所有能想到的问题为目标。

* **交付测试与常规命令**：自动化测试放在 `tests/`。运行本机可行的检查，保留可复用的测试和运行命令，并报告实际执行的命令、结果与检查局限。清理过时的实现计划，提供不依赖 Codex 或 MCP 的常规启动与使用命令。
* **说明遗留问题与阻碍**：对尚未解决的问题，说明已有证据、影响哪些要求，以及下一步可行的检查方式。若存在具体阻碍导致无法完成，说明原因并交付现有结果。
* **格式要求**：Markdown 段落不要使用段内换行。
