# 生成与修复的公共工作要求

这些要求同时适用于生成和修复。依据当前任务提示开展工作：`TASK.md` 定义初始生成任务；`REPAIR.md` 定义对所提供候选和指定问题的修复任务。将 `protocol.md` 和 `system.md` 一起阅读，作为给定设计和目标要求。

根据所分配的任务选择计划和代码组织方式。在本次 Codex 会话中完成实现、测试和修复。有帮助时，可以把独立工作委派给原生 Codex 子智能体，使用相同模型和推理强度，并遵守现有权限。协调共享文件的修改，整合子智能体结果，并在最终答复前完成或停止委派工作。内部委派不能替代独立审计和修复复核。不要启动嵌套 Codex CLI 会话或调用外部模型服务。可以编写自己的本地脚本和测试工具。

在本工作区内开展工作。给定设计在本次运行中保持不变。不要修改所提供的文档，也不要等待另一个 agent 修订设计。材料未规定的机制由你自行选择，并说明重要选择。存在多个符合要求的机制，不构成规格缺口。在 `DESIGN.md` 中记录缺失或矛盾的要求，以及有证据支持的设计反例，注明相关规则和证据；将它们与实现错误、尚未完成的调查区分开。继续不依赖该缺口的工作，不削弱保证，也不加强外部假设。不要查看其他实验运行，也不要获取其他共识实现来代替本任务。

任务范围是本地实现与测试，包括启动多进程集群、交换副本和客户端消息、注入协议允许的故障，以及清理测试创建的资源。保留现有认证和沙箱保护。不要更改凭据、对外发布代码或软件包、部署到远程或生产基础设施、向第三方发送通信，或修改无关数据和资源。

## 实现与证据

按清晰职责组织协议处理、调度与生命周期、传输与编码、状态存储、应用执行和客户端集成。自行选择包、接口、同步机制和数据结构，不规定固定布局。明确状态由谁维护，以及重要接口的阻塞、重入、完成、取消和关闭语义。审阅组件之间的交互，整理明显的重复逻辑和职责混杂。

把材料中的抽象操作和事件对应到实际运行时边界。解释同步与调度如何保持所要求的原子性、顺序和进度。追踪相关入口到处理函数的路径：谁维护状态，等待期间哪些工作可以交错，每个调用入口是否满足处理函数依赖的前提。推导时间关系时，应计入给定假设覆盖的工作和事件边界，包括相关的传输、编码、校验和调度。名称对应或本地入队本身不能说明要求已经满足。

让 `DESIGN.md` 保持简洁，并随代码及时更新。对影响行为的重要选择，说明原因，把实际文件、函数与要求联系起来，引用已有检查或指出尚未检查的部分。区分必需行为、外部假设、附带条件的结论和实现选择。按实现风险选择需要解释的内容，不重述算法；调查历史和命令记录放在报告中。不要求固定模板，也不要求为每项说明单独编写测试。

调查运行时行为时，通过受支持的服务或 Node 入口，使用给定的控制、观察接口执行实际处理函数。说明测试控制、替换或绕过什么，以及观测代码如何影响行为。适配器负责连接实现接口；实现必须自行产生应有反应，适配器不能补上实现遗漏的状态转换或消息发送。仅仅共享处理函数，不能说明队列、定时器、传输或应用集成行为已经经过检查。控制方式必须允许所怀疑的失败发生，输入和故障须符合给定假设。

记录实际观察，保持身份和事件含义一致。测试要求执行的动作不等于实际观察。说明哪些断言支持结论、哪些路径尚未检查。区分测量条件、外部前提和未解决行为。按照给定进度保证解释超时；有限等待本身不能否定最终进展保证。运行适当测试，报告准确命令和结果；检查通过不是共识正确性的证明。

用证据调查重要开销和运行限制。在可比较的条件下，比较相关工作负载或保留状态规模，包括设计要求的生命周期转换。如果模拟时间或对象数量不能回答疑问，就采用真实执行测量。追踪显著增长或重复工作的原因，区分必需保留的数据与表示、复制、校验或调度造成的额外开销。选择保持语义的改进，或解释为何保留原机制，并重新检查受影响行为。说明限制是在接纳前拒绝工作，还是影响已接纳工作；说明优化是否消除了开销，还是把开销转移到了别处。不要从某个数据结构变小推断总资源有界，也不要为了降低开销而丢弃必需工作或证据。

自动化测试代码放在 `tests/`。Markdown 段落不要在段内换行。依赖和配置文件不得包含凭据。本地实验使用回环地址，并在结束前停止子服务。
