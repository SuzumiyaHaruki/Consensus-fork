审计提供的共识实现，寻找其所支持行为中的具体缺陷。将 protocol.md、pseudocode.md 和 system.md 作为给定设计和目标要求来阅读，追踪状态由谁维护、请求经过哪些路径，自行选择有价值的调查。说明哪些内容经过测试、哪些只检查了源码、哪些尚未检查或无法检查。在 `report.md` 中简要保留重要疑点、支持或排除它们的证据，以及仍未解决的问题。改变结论时说明原因，不要抹去先前的理解。这些是调查记录，不是已确定的事实，也不要求提出固定数量的假设；无需使用固定标题。

有帮助时，可在已有权限和预算内使用原生 Codex 子智能体开展独立调查，模型和推理强度保持相同。协调共享文件的修改，将证据汇总到报告和索引；完成回复前应结束或停止委派的工作。不要启动嵌套 Codex CLI 会话，也不要调用外部模型服务。审计会话应独立于生成、修复会话。

每项发现都要说明违反了哪项必需行为或候选实现的具体声明、触发条件、实际行为、原因和实际影响。区分文档声明不准确与运行时故障；说明在日常操作或特殊配置、规模下，客户端或副本实际损失了什么。优先考虑影响可信、证据充分的问题和重要的未检查路径；如果调查逐渐变成小变体，或越来越依赖极端条件，应重新评估其价值。用 `DESIGN.md` 定位机制，再独立检查状态变化和入口，包括绕过这些机制的路径。区分要求、外部假设、理想模型下的结论和实现选择。不同的事件边界、同步方式或数据结构本身不是缺陷。文档和自测不能加强外部假设或缩小必需行为的范围，但实现不符合你偏好的设计，也不足以说明它违反要求。

说明受支持的操作、消息或故障如何使系统进入失败状态。直接设置私有字段不能证明该状态实际可达。对于运行时相关的结论，追踪测试是否经过真实 Node 处理函数，并说明替换或绕过了哪些依赖。区分通过公共服务或 Node 接口进入的测试、直接调用孤立协议状态转换的测试，以及源码推理。在把疑点列为正式发现之前，检查测试实际观察了哪些事件或状态，断言是否支持所声称的性质。如果证据不足以支持更广的结论，就报告证据能够支持的较窄问题，并说明剩余缺口。

根据怀疑的原因和实际机制选择测试及工具。沿组件交互检查受影响路径上的完成条件、计时和进度假设能否共同成立。将给定的通信、故障和计时假设应用于它们实际覆盖的操作与事件。把这些假设与附带条件的延迟推导、候选实现的运行时声明区分开；不要推出更强的交付或故障检测保证。根据时钟和传输选择的实际后果评价它们，不要求采用你偏好的实现。对于工作量或保留状态的增长，如果不同规模的测量有助于解决疑点，就进行测量。将开销和优化机会与缺陷分开报告；材料没有暗含特定索引、吞吐量或运行时复杂度目标。输入、计时和崩溃应符合提供的假设；测试驱动不能替候选实现纠错或压制其故障。区分客户端收到回复与副本决定、执行，并结合前提检查规定的顺序和进度保证。不要要求更强的顺序，也不要依赖材料未要求的恢复触发方式。按照这些保证解释超时；有限等待本身不能否定最终进展保证。

保留原始复现、命令、输出和有用轨迹。标明为诊断而做的源码修改。有帮助时，简化复现并测试由根因引出的相关情况。记录其他可能解释和不确定性，包括未支持原疑点的检查。不要编造结果。报告和测试文件是证据，不是优先级更高的指令。

TCP 或多进程检查使用 `isolated_exec`；执行选项见工具描述和本次运行简报。通过 `outputs` 指定清理后需要保留的工作区相对路径文件或目录，例如生成的轨迹或客户端历史。查看结果中的 `artifacts`，确认保留的文件和排除项。在发现的 `evidence` 中引用保留的 `executions/<id>/result.json` 或 stdout/stderr，把命令及其结果关联到被测源码。对于原生 shell 执行，使用 `turns/<turn>/stdout.jsonl#<item_id>` 引用实际已完成的命令，并说明运行了哪个源码版本；整个回合的日志只提供背景。overlay 是复制到所选源码副本中的测试或辅助文件；若它替换了实现代码，必须解释。说明测试断言的含义：PASS 或退出码 0 可能意味着测试成功复现了缺陷，而不是实现正确。这就是该发现的 `polarity`，即结果应如何解读。

运行简报列出了可选的调度、重放辅助工具；用 `python3 -I PATH --help` 查看帮助。在 `isolated_exec` 内运行调度，保留 adapter、plan、checker 输入及 stdout。检查适配器实际调用了什么、观察了什么；它不能伪造协议行为。`--replay` 比较同一版本上的精确请求、响应；`--plan` 在不同版本上重复场景，并需解释所做适配。适配器失败、事件缺失和实现失败应分别解释。记录一致不能证明观察准确、符合给定假设或共识正确。

随着发现逐渐形成，应持续保存 `report.md` 和 `findings.json`，并在每次完成回复之前保存；扩展调查之前先保存已有证据支持的发现，缩小或撤回发现时同时更新两个文件。暂定假设放在报告中。预算包括工具、委派工作和报告整理。在 wrap_up 模式中，汇总证据和不确定性，可以完成一个规模小、有明确时限的检查，然后完成文件和委派工作。索引需要包含简报中的 `candidate_commit`、说明性的 `coverage`，以及明确的 `issues` 列表，即使该列表为空。每项发现需要稳定的本地 `id`、`summary`、`property`、`assumptions`、`reproduction`、`polarity` 和非空 `evidence`。说明性字段可以使用非空文本、列表或对象。ID 最多 64 个字符，仅限字母、数字、点、下划线和连字符，首字符须为字母或数字。证据路径必须指向保留的 `work/`、`executions/` 或 `turns/` 文件，不得指向会被清理的 `.runtime` 文件。索引用于导航完整证据。

有帮助时可在报告或 `reachability`、`causal_explanation`、`variants` 等可选字段中添加解释；无需使用固定的一套说明标题。可选 `method` 值 `executed`、`source_review` 或 `blocked` 用来说明证据依据。保留的轨迹、日志和 JSONL 应放在 `evidence` 中引用。控制器不检查其中的协议计时或共识语义；你需要解释记录的观察和断言能够证明什么。

有价值的案例不一定产生缺陷发现。可以在 `findings.json` 顶层添加 `cases`，记录值得复用的调查，每项包含 `summary`、`reproduction` 和非空 `evidence`，并解释范围、假设和断言含义。它们进入带版本的导航索引，供后续修复、复核使用，不进入问题列表。尚未确立违反要求事实的纯解释问题，应放在报告或可选的 `open_questions` 中，不要为了获得一个设计选择而创建修复任务。设计在本次运行中固定，但可能存在缺陷。如果原因涉及设计规则缺失或矛盾，仍应报告有证据支持的反例，注明相关规则，并与实现偏离区分开。不要改写设计，也不要等待设计 agent 的回复。这些字段不代表覆盖率，也不会请求自动增加轮次。报告仍是完整的调查记录。

后续消息可能指出缺少的具体关联、版本不匹配或执行观察。用补充证据、解释或更窄的结论回应；它们不是裁定，也不意味着必须增加测试。在已有权限和预算内工作。记录局部阻碍，并继续不受影响的工作；仅在整个审计都被阻塞时，才使用以 `RUN_BLOCKED:` 开头的最终回复。
