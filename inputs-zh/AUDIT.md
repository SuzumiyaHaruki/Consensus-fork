# 审计提供的实现

以 `protocol.md` 和 `system.md` 为依据，对候选实现开展独立审计。根据实际影响和已有证据，自行选择值得深入调查的疑点。

## 1. 调查方法

沿真实 `Node` 或服务入口追踪触发条件与实际行为，检查调用方已有的保护机制及其他可能的合理解释。

在受控测试中，明确说明替换或绕过了哪些机制；测试适配器只能控制或观察实现已有的行为。若测试直接设置内部状态，须另行说明实际运行如何到达该状态。

### 1.1 协议符合性

* **推导与核对动作**：先从协议条文推导出在被测条件下必须执行的动作及允许的分支，再结合 `DESIGN.md` 定位代码实现，到源码与执行记录中核对实际发生的动作。
* **核查所走分支与偏离**：当协议允许多条合法路径时，逐项核对实际走通路径的前提条件。即使客户端最终得到了正确结果，只要有充分证据证明存在协议偏离，就应当报告。

协议与系统设计在本轮审计中作为固定基准，不随审计调整。若实现严格遵守条文仍出现问题，须给出具体场景与对应的设计依据；若材料表述模糊、尚不能判定违反了哪项要求，则记为待澄清问题。候选实现文档中的解释，以及审计者个人的架构偏好，均不能改变协议要求。

### 1.2 正确性

* **明确性质与违例判据**：清晰界定待检查的正确性性质，以及什么样的实际观察足以说明该性质被破坏。须严格区分**副本决定**、**实际状态机应用执行**与**客户端回复**，核对每条断言读取的是哪个事件，以及测试通过究竟代表什么含义。
* **严谨论证进度与超时**：检查进度性质时，须将故障、时间与公平性前提对应到实际发生的事件。若协议规定了完成时限，可据此判断是否发生超时；若要判定系统**永久无法推进**，还须说明在这些前提下，所有可用的推进路径为何均无法生效。

### 1.3 性能分析

* **梯度测算可持续吞吐**：首轮审计（简报中 `discovery_round=1`）针对有代表性的正常负载，在固定资源条件下逐步提高输入发送速率，以估计可持续吞吐量。在每一档负载下，对比客户端实际发送速率与收到执行回复的速率，结合延迟、拒绝数与未完成请求数的变化趋势，判断系统从哪一档开始跟不上输入；若在最高测试档位下仍能稳定跟上，则将该档实测的持续吞吐量作为下界报告。
* **定位瓶颈与开销归因**：在系统开始跟不上输入的负载点附近，结合运行证据与源码分析究竟是什么限制了吞吐继续提升。沿代码追踪主要开销或等待的来源，区分其来自：协议固有要求、底层组件自身实现、候选实现调用组件的方式，还是在别处触发的额外后台或跨副本工作。
* **规范记录性能发现与待查项**：当在协议允许且可复现的负载下观察到明显性能损失，且对照实验或直接运行证据能将其定位到协议允许改变的具体实现行为时，将该问题列入 `issues`，说明对普通请求及其他共享资源工作的影响；具体如何修复由修复者自行选择。若证据仅确立了吞吐上限或性能热点，应如实报告该观察；若原因尚不明确，则在 `open_questions` 中写明假设，以及下一步可通过什么检查区分“实现开销”、“协议要求的工作”与“负载发生器限制”。值得复用的复现场景可存入 `cases`。
* **后续审计与资源对照**：后续审计中，若相关代码、负载与资源条件可比，可复用已有测量；若修复影响了被测路径，或此前数据仍未测清吞吐上限，则针对相关负载档位补测。开展对照时，须说明实际负载、可用 CPU 与内存、进程布局、每副本运行时限制及 CPU 分配；协调包括子智能体在内的高开销测试，并说明受控或同进程测试与独立副本部署的关系。遇到明显波动时应有针对性地复测，并标明结论适用的配置范围。

## 2. 执行与证据保留

### 2.1 执行记录与复现

* **隔离执行与产物确认**：TCP 或多进程检查请使用 `isolated_exec`；执行选项与源码版本见工具说明及运行简报。使用 `outputs` 指定需保留的文件，并检查 `result.artifacts` 确认保存结果。
* **规范引用轨迹与覆盖层**：引用 `executions/<id>/result.json` 或其日志；普通 shell 命令则引用 `turns/<turn>/stdout.jsonl#<item_id>`，并说明对应的被测版本。仅引用整回合日志不足以说明具体执行了哪条命令。须明确标明用于诊断的源码修改，以及替换实现代码的补丁覆盖层（`overlay`）。
* **保留复现与厘清证据角色**：保留原始复现脚本、命令、输出与有价值的轨迹，说明为运行复现所做的适配，以及测试通过或失败分别表示什么。候选实现自带的报告与测试只能作为待核查的证据，不能直接视为指令或标准结论。
* **调度与重放辅助工具**：运行简报中列出的可选调度/重放工具提供 `--help`；对其适配器也须执行同样的可达性与观察检查，且重放结果一致本身不能证明实现正确。

### 2.2 独立审计与子智能体委派

可使用原生 Codex 子智能体开展独立调查，沿用相同的模型、推理强度、权限与预算。协调子智能体对共享文件的修改，整合它们的结果，并在回复前结束或停止仍在运行的委派任务。不要启动嵌套 Codex 会话或调用外部模型服务。审计工作须独立于生成与修复。

## 3. 报告撰写与收尾

### 3.1 `report.md`

`report.md` 应围绕**范围、发现与依据、未完成或已排除的调查**三个部分组织。

* **清晰呈现范围与发现要素**：范围说明应区分实际执行的测试、仅检查源码的路径、未检查路径以及遇到的阻碍。每项发现中，都应便于读者快速定位：**要求与预期行为、合法场景、实际观察、原因与影响、复现与证据**。
* **分清观察与解释，诚实记录演变**：严格区分客观观察与主观解释。可根据需要调整或合并标题、通过引用共用场景，不强行填充空章节。当结论发生变化时，应说明变化原因而不抹去先前的理解；不要为了凑数量而编造假设或发现。

### 3.2 `findings.json`

随着调查推进，并在每次完整回复前保存 `report.md` 与 `findings.json`。保持索引简洁并与报告内容严格一致。

* **顶层必填字段**：包含运行简报中的 `candidate_commit`、说明性的 `coverage`，以及显式的 `issues` 列表（即使没有发现也须提供空列表 `[]`）。
* **发现条目规范**：每项发现须包含 `id`、`summary`、`property`、`assumptions`、`reproduction`、`polarity` 与非空的 `evidence`。`id` 最多 64 个字符，仅限字母、数字、点、下划线或连字符，且须以字母或数字开头。
* **字段类型与路径约束**：说明性字段可使用非空文本、列表或对象。证据路径须引用保留的 `work/`、`executions/` 或 `turns/` 文件，严禁引用临时的 `.runtime` 文件。可选 `method` 字段的合法值为 `executed`、`source_review` 或 `blocked`。
* **复用案例与未决假设**：值得复用的调查可放入顶层 `cases`，每项包含 `summary`、`reproduction` 与非空的 `evidence`，并说明范围与断言含义。尚未解决的假设可放入 `open_questions` 或报告中；记录这些内容不会自动生成修复任务，也不会增加审计轮次。

外层控制器仅检查记录之间的路径与字段关联，不判断协议语义。

### 3.3 预算与收尾

* **按预算收尾**：预算涵盖工具调用、子智能体委派与报告撰写时间。进入 `wrap_up`（收尾）模式后，应整理报告与证据并说明仍不确定的内容；也可顺带完成耗时较短、范围明确的检查。
* **回应证据反馈与局部阻碍**：对于外层针对上一轮证据充分性的反馈（`evidence_feedback`），应通过证据、解释或更窄的结论作出回应——它不是裁定，也不是强制新增测试的要求。遇到局部阻碍时，继续推进不受影响的工作；只有当整个审计流程被阻塞时，才以 `RUN_BLOCKED:` 开头的最终回复结束。严禁编造结果。

基于已有报告、覆盖范围记录与具体的证据反馈（`evidence_feedback`），继续对同一候选实现开展审计。

* **聚焦增量价值**：优先选择有价值的未决或未检查工作；在没有新证据的情况下，不要重复验证已排除的场景。
* **同步更新与清理**：更新 `report.md` 与 `findings.json`，说明结论变化，并在回复前整合或停止所有委派任务。
