## 运行

从仓库根目录执行，要求本机 Go 1.25.8 或兼容版本、Python 3.10+，TCP 检查需要允许监听回环地址。没有外部 Go 依赖下载，也不会发送模型请求。

```bash
python3 comparison/run.py --case correctness --repeat 3
python3 comparison/run.py --case boundary --targets baseline v000 v001 v002
python3 comparison/run.py --case http
python3 comparison/run.py --case history --repeat 3
python3 comparison/run.py --case network --repeat 3
```

`correctness` 和 `boundary` 使用 Go race detector。`history`、`network` 不启用 race detector，并按轮次轮换候选顺序。每个 `go-test.jsonl` 保存原始测试事件，`execution.json` 保存候选提交和退出码；顶层 `results.json` 汇总本次运行。运行器会继续比较剩余候选，测试是否失败应看逐项退出码和输出，不能用运行器结束来代替测试通过。

## 测试实际覆盖什么

共同受控测试使用真实 Node 的入口、所有者 goroutine、发送工作、计时处理和真实 KV 应用。网络适配器深拷贝消息并保留已接受发送，发送方停止不取消交付义务；只在崩溃接收方丢弃消息，向存活方交付时检查相对接受时间不超过 Delta。部分广播场景在传输接受之前阻塞选定发送。没有注入手工构造的决定、恢复状态或依赖关系。这里替换了生产网络和实际时钟，因此真实编码和网络成本由另外的 TCP、HTTP 测试检查。

并发检查使用 20 个工作负载种子，每个产生 18 条同一分配会话下的并发 Put/Get/Delete，分散到三个协调者并重复投递协议消息；三轮重复使用相同种子。检查实际每命令结果、副本内执行次数、客户端结果、已发送决定之间的一致性及错误死亡事实。种子控制工作负载和可交付队列的抽样，但不控制 Go 的所有 goroutine 调度，不承诺逐事件确定重放，也不要求不同实现选择相同的合法执行顺序。

依赖环场景先阻止 OBSERVE 投递，等两个协调者各自接纳命令，再释放消息形成真实双向依赖；随后阻塞应用回调，检查既定 SCC 顺序、本地执行后从新观察省略旧命令以及未完成成员仍被观察。恢复场景使用五副本，b 已崩溃，a 只向 c/d 完成原始传播后崩溃；e 原先不知道命令，c 必须通过资格后的新读取和第二代 Seal 自主推进，测试没有再次提交客户端命令。等待超时是调查的有限观察窗口，不自动等于协议活性反例。

成员 ID 检查使用生产 TCP 传输和三个真实 Node，覆盖普通名称、换行、尾随空格与 800 KiB 名称。Delta 检查允许实现拒绝无法表示的配置；如果接纳，则启动三个真实存活 Node，用有限真实延迟观察是否产生错误死亡事实。JSON 检查启动未修改的单副本服务器，通过正常写读、重复字段和 Unicode 字段别名请求观察实际 HTTP 回复与后续 KV 读值；记录观察，不把所有边界策略差异都自动归类为共识违例。

单 Node 历史测量顺序执行 12,000 条固定大小的 Put，每 1,000 条记录延迟，不启用观察回调和快照读取。应用外包了一层相同的执行结果记录，内存数字包含该记录及测试进程，不能视为候选单独的存储占用。三进程测量通过真实 HTTP 发送 1,000 条 Put，固定原协调者、最多一个在途请求、请求之间等待 5ms；最后分别向三个副本提交新的读命令。它使用各自的生产传输，baseline 另有一个 relay 进程，进程 RSS 汇总包含 relay。该工作负载不是最大吞吐压力测试。

## 与实验流程的关系

这组测试是看到现有实现与审计结果后整理的研究检查。其中有已知回归和从另一份实现迁移的场景，不是预先隐藏的终测。比较过程中不把发现反馈给候选修复，也不修改 `inputs/`。问题是否违反当时要求、断言是否充分、差异是否来自方法，仍需结合保存的规格、源码和实际轨迹分析；这里没有通用性质评分器。
