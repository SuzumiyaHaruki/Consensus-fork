# Requested system artifact

Implement `protocol.md` and `pseudocode.md` as a runnable Go replicated key/value system. These materials specify protocol behavior; this document defines service deliverables and guides engineering choices. Choose mechanisms the materials leave open and continue without waiting for a researcher to select an answer. Explain consequential choices, their operating conditions and observed costs. Multiple compliant mechanisms do not constitute a specification gap. Report a gap when missing or contradictory required behavior prevents judging compliance; uncertainty about your implementation calls for investigation. Do not narrow requirements or strengthen external assumptions to make code appear correct.

## Service scope

Deliver reusable consensus Node components, separate server processes, real network transport, a reusable client interface and CLI, and local launch/cleanup instructions. Configure member identity and addresses, a consistent configuration identity, n/f/s/W/e/K within the protocol's parameter relations, and implementation scheduling settings as needed. Multiple independent clients may submit concurrently. A client deliverable does not limit the number of clients, connections or outstanding operations. Use loopback by default. A deployment platform and general storage engine are unnecessary.

Implement deterministic single-key Put, Get and Delete. Define their results, errors and conflict classification, including request-result deduplication state. Nonconflicting operations must preserve each request's result as well as final state when reordered. Same-rid commands conflict. Reads use the consensus execution path rather than arbitrary local state. Explain the service guarantee under the protocol's Agreement, Visibility and execution premises; distinguish those targets and conditional arguments from what your checks establish. Return retained application outcomes only after execution, not after admission or metadata decision.

## Responsibilities and design explanation

Separate protocol transitions, node scheduling/lifecycle, transport/encoding, evidence storage/retrieval, application execution and client integration by clear responsibilities. Choose package layout, API names, synchronization and data structures. Document important interface semantics near declarations: ownership, blocking/reentry, completion, cancellation and shutdown. Avoid independent protocol implementations in the simulator, server and tests.

Keep `DESIGN.md` as a concise explanation of the current implementation, updated alongside generation and repair. Connect important mechanisms, state changes and completion events to actual files/functions and requirements. Link relevant checks or retained results and state what remains unchecked. Keep investigation history and command transcripts in reports. Useful questions include:

- How do per-instance promises/tasks interact with the shared conflict registry, admission slots and application result table? Which transitions must be atomic, and how are immutable first scans distinguished from fresh recovery scans?
- Which actual events begin a broadcast window, complete sending, admit a reply, cut a collection and allow its completion? How do queueing, evidence retrieval and processing fit the stated window assumptions?
- When a reply, Fetch completion or timer arrives after a task changes, what can it still contribute as historical evidence, and what can it no longer authorize? How does complete acceptance evidence differ from an obsolete task callback?
- How does required evidence become available, validated and retained before a response uses it? What continues progressing while another instance is fetching data or waiting for HELP?
- What distinguishes instance decision, execution completion, slot release and a client's retained logical result? What continues after client cancellation, retry or origin failure?

These are reasoning prompts, not mandatory headings or a fixed test inventory. Atomicity concerns specified local state transitions, not the entire network-to-execution lifecycle of one command. Select mechanisms yourself and explain their behavior. Design statements and code references aid review without proving correctness.

For an engineering limit affecting supported behavior, explain its trigger, enforcement and actual consequences, distinguishing refusal before admission from failure afterward. Describe effects on admitted work and clients. For growing work or retained data, compare suitable observations at different workload/history sizes within protocol.md's experimental scope, holding other conditions comparable. Choose relevant latency, bytes, memory or queued-work measures; no fixed benchmark or throughput target is prescribed. Report observations without extrapolating universal bounds. Naming a limit does not add a protocol assumption or authorize dropping required work.

## Runtime, transport and evidence

The Node owns background progress after startup; applications do not manually tick or pump transitions in ordinary use. Support concurrent requests, incoming messages, timers and application work safely. Keep transport replaceable and consensus logic usable without sockets. Real-time and controlled execution use the same implementation. Explain shutdown, input ownership, backpressure, reentry and pending work semantics. Keep tests in `tests/`; choose their contents and methods.

Map abstract sends, full broadcasts, response reception and cuts to actual Node/transport events. A crash can interrupt a broadcast between sends. Do not treat local enqueueing as proof that unsent messages reached peers. Explain failed sends, retransmission and progress when peers have crashed. Preserve the protocol's start-of-broadcast W rule, complete-send prerequisites, phase distinctions and actual-response semantics. Additional transport exchanges must fit the declared model. Costs between event boundaries remain real work.

W is a complete RPC window with up to s still-alive missing responders, not a deadline on every message. Slow identities may change. Investigate overlapping reception, timer and task-completion handling against these rules; do not replace Omega with accurate timeout-based death detection. A measurement supports its tested conditions, not a universal timing guarantee. Client waiting and application execution have separate latency. A finite delay or timeout is not alone evidence that eventual progress is impossible.

Preserve identities and payloads across codecs. Choose and validate unspecified representations/ranges consistently; accepted values must work across components. Bind configured member identity to the actual message source within an explicit trusted-cluster boundary; an unchecked payload field is insufficient. This crash-stop task does not demand Byzantine tolerance or production PKI. Protocol certificates are actual retained records and their checked relationships, not cryptographic signatures or opaque booleans.

Implement the source's Omega construction and background recovery, HELP and Fetch obligations; do not substitute an always-correct leader oracle in the delivered Node. Controlled components may supply reproducible scheduling, while tests must identify any mechanism they replace. Explain task eligibility, stale-event handling, missing-object resumption and evidence lifetime. Normal envelopes must supply the objects needed to preserve the intended fast path; references alone do not justify extra retrieval rounds as a one-round-trip implementation.

## Admission, retained history and execution

Implement the private K-slot admission rule and fair FIFO queues. Distinguish queued requests, admitted instances and remote recovery work. Slots remain occupied until origin-local execution completion, including deduplication; decision or timeout is insufficient. Full slots must leave recovery, Fetch, HELP, message handling and execution able to progress.

Executed instances remain visible to conflict scans. Retain first scans, votes, accepted history, decision certificates, evidence sources and results. Physical sharing and equivalent indexes are implementation choices; local execution does not authorize dependency retirement, evidence deletion or snapshot compaction. Explain and investigate growth under these retention rules. nK bounds occupied admission slots, not history bytes or a closure's historical size. Do not silently add a cutoff that breaks the protocol to obtain a memory or timing bound.

Execute dependency-ready work while requests continue, obtaining full decided closures and respecting dependency order and `(final seq, instance ID)` order inside SCCs. Coordinate overlapping closures and retain each instance's execution marker. Ready work must get fair opportunities. Application state and rid results change atomically; a duplicate instance reuses the original result without repeating its effect. The protocol's finite-closure argument is conditional and provides no uniform execution deadline.

## Client integration

Provide concurrent request allocation with distinct rid values for new operations and exact ID/payload preservation for retries. Concrete encoding is your choice; safe concurrent allocation and uniqueness between independent clients are required. Do not conflate rid with `(origin,localCounter)`, ballot, attempt or nonce. A new operation after client restart may use a fresh allocation session; recovering pending requests across client restart is not a required journal feature.

Support retry at another entry using the same rid and payload after an unknown outcome. Choose and explain waiting, retry and backoff policy. At one entry, merge queued/active duplicates and return cached completed results; another entry may legitimately create a different instance for the same rid. Retain connected waiters appropriately and return only retained execution outcomes. Reject malformed input and known contradictory payload reuse without creating dependencies or corrupting legal requests. Normal clients do not intentionally change the payload of an existing rid.

Distinguish a definite pre-admission rejection, an application outcome including application error, and an unknown result. Timeout/disconnection/cancellation does not cancel admitted replica work, prove death or authorize a new rid for the same logical request. A new Get is a new operation, not a result query for an old one. Background recovery cannot depend on client retries; retry may recover the logical operation when the old instance was never made publicly available. Do not claim durable exactly-once external effects or a fixed end-to-end completion time.

## Faults, observability and delivery

Support fixed membership and up to f cumulative crash-stop failures. A crashed replica never returns. No WAL, restart recovery, catch-up, arbitrary partition tolerance or safe history deletion is required. Keeping records in surviving process memory is acceptable. Holding/releasing an event within the declared model is scheduling control, not crash followed by recovery. Explain what already issued transport work survives a process crash under the selected transport and source assumptions.

Provide documented narrow control and observation points for actual Node behavior, with a runnable example a reviewer can adapt. A test enters supported Node/service interfaces and runs affected implementation handlers; it must not supply their transitions. Choose an interaction relevant to the implementation and identify the event held/released, actual observations, unchanged runtime code, substitutions and instrumentation effects. Core tests remain useful but do not establish queue, timer, transport or application integration behavior. No fixed architecture or control over every goroutine is required.

Expose enough actual observations to relate rid and instance ID, message source/target, ballot/task/stage where relevant, broadcasts/replies/cuts, decisions, execution, slot release and crashes. Requested test actions are not observations. Do not impose a fixed schema or build another protocol in the adapter. Use the same declared event meanings in code, DESIGN and tests. Legal slow replies must not be rejected just because they exceed a per-message Delta model from another protocol. Tests exceeding W/s or fairness assumptions need that limitation explained rather than presented as an in-model counterexample.

Deliver module `example.com/mixepaxos`, reusable Node/client interfaces, server/client programs, configuration examples, local launch/cleanup instructions including the protocol's seven-member example, separate tests and current `DESIGN.md`. Explain actual checks and remaining failures. Server/client programs run independently of Codex; private execution tools are test facilities only. A local cluster does not establish long-term production readiness.
