# Implement the supplied consensus system

Implement the complete system described by `protocol.md`, `pseudocode.md` and `system.md`. Read all three documents in full. Deliver runnable programs, reusable components, tests and documentation as specified; a library or a plan alone is insufficient. Follow `AGENTS.md` for implementation and evidence practices.

Start `DESIGN.md` with a short sketch and revise it alongside the code. Build in small runnable additions: first take one normal request from the client through replica communication, decision and application execution to its response; then extend the same implementation to the concurrency, fault handling and lifecycle behavior required by the materials. This construction order does not reduce the final scope. Check component interactions as behavior is added, and review code organization before delivery.

Choose tests according to the design's risks. Prioritize observed failures and unexplained runtime anomalies over more similar passing cases or report polishing. Retain failing inputs and observations, try to reproduce the behavior and narrow its cause; a later pass alone does not explain an earlier failure. Distinguish a demonstrated defect, evidence that test assumptions were violated, and an unresolved observation, identifying the next useful check when unresolved. Follow `AGENTS.md` for test placement and reporting. Document genuine specification gaps without rewriting requirements.

Finish with the deliverables and operating instructions required by `system.md`. Report actual checks, failures and limitations. Reconcile `DESIGN.md` with the delivered code and remove obsolete plans; identify unmet requirements without redefining them.

There is no fixed generation-stage deadline. Judge when to deliver from the implementation and evidence, not elapsed time or test count. Finish once the requested functionality is integrated, checks proportionate to the chosen design exercise its important paths, and the code, design and operating instructions agree. Address demonstrated defects that prevent the required behavior; investigate unexplained failures enough to state what is known and what remains uncertain. Additional work should resolve a concrete delivery problem or question affecting confidence in required behavior. Further possible scenarios alone do not require another investigation. Record unresolved observations and useful next checks for the independent auditor. If a genuine blocker prevents completion, explain it and the incomplete requirements, then end the session. Finish delegated work and provide the final delivery; do not attempt to exhaust independent auditing before handing over.

Use `forge_local.isolated_exec` for TCP or multi-process checks. Its tool description explains private networking, process lifetime, retained records and optional source copies. These are test-environment facilities; the delivered server/client programs must also run through ordinary documented commands without Codex or MCP. Each isolated execution has a command timeout; this does not impose a generation-stage deadline.

An optional adapter-driven scheduling/replay helper is available at `../inputs/schedule.py`; use `python3 -I PATH --help`. Run schedules inside `forge_local.isolated_exec`, using absolute helper paths when selecting captured source copies, and retain useful adapter/plan sources under `tests/`. The helper calls the adapter according to a plan and records requests and returned observations. Its control is limited to the events exposed by the adapter; thread scheduling outside those controls remains with the runtime and OS. Assess compliance with the supplied assumptions, scenario reachability and consensus properties using the adapter, actual runtime paths and test assertions. Keep inputs and injected faults within the supplied assumptions. Helper use is optional.
