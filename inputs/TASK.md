# Implement a runnable synchronous consensus system

Implement the Go replicated KV system described by `protocol.md` and `system.md`, using module `example.com/syncepaxos`. Deliver reusable node components, separate server processes, real transport, client tooling usable by multiple concurrent clients, controlled execution support, tests and documentation. A library or a plan alone is insufficient. Prefer the standard library for offline builds. Do not substitute another consensus algorithm.

Start `DESIGN.md` with a short sketch that you can revise while implementing. Explain what each component does, who can modify shared state, which guarantees the system provides and why, and which events mean an operation has completed. Distinguish requirements in the supplied documents, assumptions about the environment, your implementation choices, and unanswered specification questions. Cite the relevant material when an interpretation affects behavior. Mark choices you have not implemented as open. Use the design guidance in `system.md` to explain how important behavior works.

Build the system in small runnable additions. First make one normal request travel from the client through replica communication, decision and application execution to the response. Then extend that same implementation to concurrent requests, duplicate messages, dependency execution and takeover after crashes. Update the design when you change who owns state, an interface, synchronization, or when an operation counts as complete. Check that the components work together as you add behavior; the final delivery must cover the requested scope. Leave time to review the code structure. Choose packages and interfaces by their responsibilities; no fixed layout, line-count target or test inventory is prescribed.

Real-time operation and tests that control time or message delivery must use the same protocol implementation. Explain how each calls it. Expose enough actual events for another engineer to investigate a particular order of deliveries, timeouts and crashes. A testing adapter connects the test driver to the implementation; it must not supply missing protocol behavior or implement a second version of the protocol. Use the materials for detailed rules; the design examples are not a complete checklist.

Choose tests according to the design's risks and investigate boundaries beyond the examples above. Follow `AGENTS.md` for test placement and reporting. Document precise specification gaps without silently inventing guarantees or editing supplied materials. The supported service and fault scope are defined in `system.md`; a local runnable cluster does not establish long-term production readiness.

Finish the implementation and provide build, launch and cleanup instructions for a local three-process cluster and concurrent operations, each submitted once. Show normal execution results and make unknown outcomes explicit. Client resubmission, result retrieval after losing the response, and pending-request recovery are outside this task; replica recovery and execution deduplication remain required by the materials. Report implemented behavior, executed checks, failures and remaining limitations. Before delivery, reconcile `DESIGN.md` with the actual code: point important explanations to real files, functions and relevant entry paths, replace obsolete plans with the implemented choices, and identify unmet requirements without redefining them. Distinguish design reasoning from checks actually performed; reference useful existing tests or results and state what remains unchecked. No separate test per explanation or fixed document template is required.

Use `forge_local.isolated_exec` for TCP or multi-process checks. Its tool description explains private networking, process lifetime, retained records and optional source copies. These are test-environment facilities; the delivered server/client programs must also run through ordinary documented commands without Codex or MCP. The stage budget includes execution.

An optional helper checks recorded message-send, delivery and crash events: run `python3 ../inputs/tracecheck.py --help`. It checks only the finite record supplied to it, not whether the implementation could actually produce that record or whether consensus is correct. Test inputs and injected faults must respect the protocol's assumptions; do not hide implementation bugs by having the test driver correct them.

An optional event scheduling and replay helper is available at `../inputs/schedule.py`; `python3 -I ../inputs/schedule.py --help` describes its JSON-line adapter protocol and plan format. Run schedules inside `forge_local.isolated_exec`; use the helper's absolute stage path when selecting a captured source copy. A thin candidate-specific adapter can expose enabled actions and actual observations from your implementation; it must state whether it exercises the core, Node runtime or transport and what it bypasses. The helper selects events and retains requests/responses in stdout; it does not implement consensus, dispatch OS threads deterministically, or judge correctness. Keep useful adapter/plan sources under `tests/`. No particular adapter, scenario inventory or helper use is required.
