# Implement a runnable synchronous consensus system

Implement the Go replicated KV system described by `protocol.md` and `system.md`, using module `example.com/syncepaxos`. Deliver reusable node components, separate server processes, real transport, client tooling usable by multiple concurrent clients, controlled execution support, tests and documentation. A library or a plan alone is insufficient. Prefer the standard library for offline builds. Do not substitute another consensus algorithm.

Start `DESIGN.md` with a short sketch and revise it alongside the code, following `system.md`'s design guidance. Explain responsibilities, state ownership and important completion events. Distinguish supplied requirements, external assumptions, implementation choices and unresolved questions; cite the material when an interpretation affects behavior.

Build the system in small runnable additions. First make one normal request travel from the client through replica communication, decision and application execution to the response. Then extend that same implementation to concurrent requests, duplicate messages, dependency execution and takeover after crashes. Update the design when you change who owns state, an interface, synchronization, or when an operation counts as complete. Check that the components work together as you add behavior; the final delivery must cover the requested scope. Leave time to review the code structure. Choose packages and interfaces by their responsibilities; no fixed layout, line-count target or test inventory is prescribed.

Real-time operation and controlled tests must share implementation code. Follow `system.md` to make relevant Node runtime events controllable and observable, and exercise the actual handlers when investigating runtime behavior. A test adapter connects to candidate interfaces without supplying missing protocol behavior. Explain what each test reaches and bypasses; design examples are not a complete checklist.

Choose tests according to the design's risks and investigate boundaries beyond the examples above. Follow `AGENTS.md` for test placement and reporting. Document precise specification gaps without silently inventing guarantees or editing supplied materials. The supported service and fault scope are defined in `system.md`; a local runnable cluster does not establish long-term production readiness.

Finish with build, launch and cleanup instructions for a local three-process cluster and concurrent operations, each submitted once. Show execution results and make unknown outcomes explicit, within `system.md`'s client and replica recovery scope. Report actual checks, failures and limitations. Reconcile `DESIGN.md` with the delivered code and remove obsolete plans; identify unmet requirements without redefining them. No separate test per explanation or fixed document template is required.

Use `forge_local.isolated_exec` for TCP or multi-process checks. Its tool description explains private networking, process lifetime, retained records and optional source copies. These are test-environment facilities; the delivered server/client programs must also run through ordinary documented commands without Codex or MCP. The stage budget includes execution.

Optional helpers are available at `../inputs/tracecheck.py` (finite event-ledger consistency) and `../inputs/schedule.py` (adapter-driven scheduling and replay); use `python3 -I PATH --help` for their formats. Run schedules inside `forge_local.isolated_exec`, using absolute helper paths when selecting captured source copies, and retain useful adapter/plan sources under `tests/`. Helpers do not judge consensus correctness, establish reachability, or control OS threads. Keep inputs and injected faults within the supplied assumptions, and expose implementation failures without correcting them in the driver. Helper use is optional.
