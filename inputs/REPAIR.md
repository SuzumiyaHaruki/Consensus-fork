# Repair the supplied candidate using retained evidence

Read the original materials, `.forge/feedback/handoff.json`, its `issues_file`, and relevant full reports and reproductions. `overview_file`, when present, is navigation rather than an independent verdict. The handoff identifies the current input commit; older findings retain their source commits. Report exactly `handoff.repair_issue_ids`, using each global ID once; for older handoffs without that field, use all IDs in `issues_file`. Other pending issues may be retained as specification context after independent review; they remain unresolved but are outside this repair batch. Indexed evidence paths are relative to `.forge/feedback/`; raw execution records retain their original run-local paths.

For each issue, check the expected behavior against the requirements, whether the triggering inputs and faults are allowed, how supported operations reach the failing state, and whether another explanation fits the evidence. Where feasible, run the original reproduction on the current candidate before editing. Preserve the original test or script; if APIs changed, explain the small adapter needed to exercise the same scenario. A test that no longer compiles does not show that the bug is fixed. Read its assertions: a reproduction may PASS because it observed the defect. The `polarity` field explains this meaning.

Use linked `execution_records` to reuse executable evidence: `restore` maps workspace destinations to retained input files, `outputs` locates the original logs, and `cwd_relative` gives the directory inside the selected source when recorded. Read the original `argv`, source context and assertions before running. Commands are preserved, not automatically made portable: missing relative directories, old absolute paths and temporary binaries need investigation or rebuilding. Restore useful test inputs under their recorded relative paths, inspect any replacement of implementation files, and execute inside `forge_local.isolated_exec`. Preserve original evidence and explain path/API adaptations. Keep build and run steps together when needed; no particular test language or scheduling helper is required. Relate before/after commands and outputs in the existing issue reasons or evidence references without inventing results when reproduction is blocked.

Explain the cause and fix the behavior that causes it, rather than special-casing the reported test. Choose the implementation yourself, preserving the protocol and supported service behavior. Do not weaken assertions or disable necessary features. Check the original scenario and useful related cases selected from the cause; retain commands, outputs and limitations. Update the design if state ownership, interfaces or engineering limits change, distinguishing supplied requirements, assumptions about the environment and implementation choices. For affected limits, follow `system.md`'s guidance on explaining what happens when they are reached, including the consequences for accepted work and supplied guarantees.

If a necessary behavior is not defined by the supplied protocol and you cannot choose a sound fix without deciding it, mark that issue `needs_specification`. Explain exactly which decision is missing and which material you checked. Continue repairs that do not depend on it, without rewriting the supplied materials. If another issue does depend on it, identify that issue's ID and explain why. The independent reviewer will assess the gap claim even when no code changed. Follow `AGENTS.md` for native delegation and workspace boundaries.

Before editing, identify which behavior the change affects and which existing requirements it must preserve. After editing, inspect the diff and choose checks for those states and transitions, including previously successful operations that the change might now reject, delay or repeat. Passing the existing suite or stopping the original reproduction from detecting a bug is insufficient if those assertions do not cover the affected behavior. Explain the reasoning and checks actually performed in the existing summary/reason fields; no fixed test inventory or extra report template is required. Writing a limitation into `DESIGN.md` does not remove a supplied requirement. A missing specification decision is different from a repair breaking behavior that was already required.

`evidence_feedback` points to specific concerns in the retained records. Answer with evidence or an explanation, or limit the claim to what the evidence supports. A note is not a verdict and does not require an extra field or test just to make it disappear. For logs from a workspace that was being edited, explain which code ran. For inconsistent traces, investigate whether the cause is the recording, the test setup or the implementation before judging the finding.

Use `forge_local.isolated_exec` for TCP/multi-process checks; consult its tool description for execution options. Default work contains your evolving repair; `source="candidate"` selects the original input candidate. Cite actual execution IDs and outputs when useful. A source record does not establish that a command tested the stated property. For the optional helper that checks recorded send, delivery and crash events, run `python3 ../inputs/tracecheck.py --help`.

For tests that control the order of events, `python3 -I ../inputs/schedule.py --help` describes the optional shared runner. Run it inside `forge_local.isolated_exec`, retaining the thin adapter and plan as test sources; use the helper's absolute stage path when selecting a captured source copy. Preserve the original requested actions, actual observations and assertion meaning. `--replay` compares exact requests and responses on the same version. `--plan` repeats the intended scenario across versions, where event IDs or ordering may change. Keep the original record and explain adaptations; do not rewrite old events to match the repair. An unavailable trigger, changed API or broken adapter does not demonstrate a fix. Check that the adapter calls the affected implementation components and does not supply missing protocol behavior. State whether it tests only the core or also the real runtime.

Write `.forge/repair-result.json` with `input_commit`, `action` (`repaired` when candidate files changed, otherwise `no_change`), descriptive `summary`, and `issues`. Each issue needs `id`, `disposition` (`addressed`, `not_substantiated`, `unresolved`, `needs_specification`) and descriptive `reason`. Summary/reason may be nonempty text, lists or objects; control values are strings. Additional explanations and evidence references are welcome, without a fixed heading set. Explain relevant before/after checks, changes and remaining risks in a form that an independent reviewer can use. These are claims, not closure or deferral decisions.

Keep feedback intact and put regression tests in `tests/`. The reviewer receives the before/after candidates, your claims, feedback and retained isolated execution records. Finish with actual changes, commands/results and remaining limitations. Finite tests do not prove general safety or liveness.
