# Repair the supplied candidate using retained evidence

Read the original materials, `.forge/feedback/handoff.json`, its `issues_file`, and relevant full reports and reproductions. `overview_file`, when present, is navigation rather than an independent verdict. The handoff identifies the current input commit; older findings retain their source commits. Use every supplied global issue ID exactly once in your result. Indexed evidence paths are relative to `.forge/feedback/`; raw execution records retain their original run-local paths.

Evaluate the property, legal trigger, actual reachability and alternative explanations. Try the original causal scenario on the current candidate before editing where feasible. Preserve original witnesses; if APIs changed, explain a thin adapter that preserves the scenario. An uncompilable witness does not establish a fix. Interpret assertion polarity: a witness may PASS because it observed a defect.

Explain the cause and repair it coherently. Choose the implementation yourself, preserving the protocol and supported service behavior. Avoid witness-specific patches, weaker assertions or disabling necessary features. Check the original scenario and useful related cases selected from the cause; retain commands, outputs and limitations. Update the design if ownership or interfaces change, distinguishing supplied requirements, external assumptions and engineering choices. If missing protocol semantics prevent a sound fix, state the exact gap and continue independent work without rewriting supplied materials. Follow `AGENTS.md` for native delegation and workspace boundaries.

Before editing, identify the behavior affected by the proposed change and the existing promises it must preserve. After editing, inspect the actual diff and select checks around those affected states and boundaries, including successful paths that the change could now reject, delay or repeat. Running the existing suite or making the original witness fail is insufficient when its assertions do not cover that risk. Explain this reasoning and the checks actually performed in the existing summary/reason fields; no fixed test inventory or extra report template is required. A limitation written into DESIGN does not revoke a supplied requirement. Distinguish a genuine missing semantic decision from a regression in already required behavior.

`evidence_feedback` contains concrete record observations, not a checklist or verdict. Resolve a question with evidence or explanation, or narrow the claim. No extra field or test is required solely to remove a note. Logs from mutable work need a source explanation; trace inconsistencies need a cause, not automatic rejection of the finding.

Use `forge_local.isolated_exec` for TCP/multi-process checks; consult its tool description for execution options. Default work contains your evolving repair; `source="candidate"` selects the original input candidate. Cite actual execution IDs and outputs when useful. A source record does not establish that a command tested the stated property. The optional finite-ledger helper is `python3 ../inputs/tracecheck.py --help`.

Write `.forge/repair-result.json` with `input_commit`, `action` (`repaired`, `no_change`, `needs_specification`), descriptive `summary`, and `issues`. Each issue needs `id`, `disposition` (`addressed`, `not_substantiated`, `unresolved`) and descriptive `reason`. Summary/reason may be nonempty text, lists or objects; control values are strings. Additional explanations and evidence references are welcome, without a fixed heading set. Explain relevant before/after checks, changes and remaining risks in a form that an independent reviewer can use. These are claims, not closure decisions.

Keep feedback intact and put regression tests in `tests/`. The reviewer receives the before/after candidates, your claims, feedback and retained isolated execution records. Finish with actual changes, commands/results and remaining limitations. Finite tests do not prove general safety or liveness.
