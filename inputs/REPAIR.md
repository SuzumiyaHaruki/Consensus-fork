# Repair the supplied candidate using retained evidence

Read the supplied materials, `.forge/feedback/handoff.json`, its `issues_file`, and relevant original reports and reproductions. The overview is navigation, not an independent verdict. The handoff identifies the current input commit; older findings retain their source commits. Report exactly `handoff.repair_issue_ids`, once each; for older handoffs without that field, use all IDs in `issues_file`. Other pending issues are specification context. The optional `history_file` retains closed issues, their original reproductions and review-added evidence for selecting relevant regression checks. A historical closure applies to the recorded review version, not automatically to this candidate. Indexed paths are relative to `.forge/feedback/`; raw records retain run-local paths.

For each issue, check the expected behavior against the requirements, whether the triggering inputs and faults are allowed, how supported operations reach the failing state, and whether another explanation fits the evidence. Where feasible, run the original reproduction on the current candidate before editing. Preserve the original test or script; if APIs changed, explain the small adapter needed to exercise the same scenario. A test that no longer compiles does not show that the bug is fixed. Read its assertions: a reproduction may PASS because it observed the defect. The `polarity` field explains this meaning.

Use `execution_records` and the overview to locate retained inputs, commands and outputs. `restore` maps workspace destinations to input files; `outputs` includes logs and selected output files; `cwd_relative` records the source-relative working directory when available. The optional `evidence_index_file` also locates reusable cases and open questions, including checks that found no defect. Select relevant material; it is neither an extra issue list nor verification of this candidate. Inspect original assertions and implementation overlays before reusing them. Rebuild temporary binaries and explain path/API adaptations; old commands are not automatically portable. Preserve original evidence and relate before/after checks in the existing reasons or evidence references. Missing files or an obsolete API are reproduction limitations, not evidence of a fix.

Fix the cause while preserving the protocol and supported service behavior. Do not special-case the test, weaken assertions or disable required features. Check the original scenario and useful related cases; retain commands, outputs and limitations. Update affected mechanisms and limits in `DESIGN.md` following `system.md`, linking evidence rather than adding investigation transcripts.

If a necessary behavior is not defined by the supplied protocol and you cannot choose a sound fix without deciding it, mark that issue `needs_specification`. Explain exactly which decision is missing and which material you checked. Continue repairs that do not depend on it, without rewriting the supplied materials. If another issue does depend on it, identify that issue's ID and explain why. The independent reviewer will assess the gap claim even when no code changed. Follow `AGENTS.md` for native delegation and workspace boundaries.

Identify the behavior a change affects, inspect the diff and select checks for affected states and transitions, including previously successful operations it might now reject, delay or repeat. Consult relevant closed history and review-added tests; there is no requirement to run every historical test. Check what each assertion actually establishes: a suite pass or disappearance of the original witness may leave the affected requirement unchecked. Explain checks and remaining gaps in the existing summary/reason fields. A new limitation in `DESIGN.md` does not remove a supplied requirement.

Address `evidence_feedback` with evidence, explanation or a narrower claim. These observations are not verdicts or mandatory extra tests. Explain which source ran in mutable-work checks, and investigate whether inconsistent traces come from recording, setup or implementation.

Use `forge_local.isolated_exec` for TCP/multi-process checks; consult its tool description. Default work contains the evolving repair; `source="candidate"` selects the original input. Use `outputs` to retain selected workspace-relative files/directories before cleanup and check `artifacts` for exclusions. Cite actual execution records. Optional helpers at `../inputs/tracecheck.py` and `../inputs/schedule.py` provide `--help`. Run schedules inside `isolated_exec` with retained inputs and absolute helper paths for captured source copies. `--replay` compares one version's exact requests/responses; `--plan` repeats a scenario across versions. Preserve original records and explain adaptations. Check which Core or Node handlers the adapter reaches; it must not supply missing behavior. Neither matching records nor an unavailable trigger establishes a fix.

Write `.forge/repair-result.json` with `input_commit`, `action` (`repaired` when candidate files changed, otherwise `no_change`), descriptive `summary`, and `issues`. Each issue needs `id`, `disposition` (`addressed`, `not_substantiated`, `unresolved`, `needs_specification`) and descriptive `reason`. Summary/reason may be nonempty text, lists or objects; control values are strings. Additional explanations and evidence references are welcome, without a fixed heading set. Explain relevant before/after checks, changes and remaining risks in a form that an independent reviewer can use. These are claims, not closure or deferral decisions.

Keep feedback intact and put regression tests in `tests/`. The reviewer receives the before/after candidates, your claims, feedback and retained isolated execution records. Finish with actual changes, commands/results and remaining limitations. Finite tests do not prove general safety or liveness.
