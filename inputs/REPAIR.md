# Repair the supplied candidate using retained evidence

Read the supplied protocol.md, pseudocode.md and system.md, along with `.forge/feedback/handoff.json`, its `issues_file`, and relevant original reports and reproductions. The overview is navigation, not an independent verdict. The handoff identifies the current input commit; older findings retain their source commits. Report exactly `handoff.repair_issue_ids`, once each; for older handoffs without that field, use all IDs in `issues_file`. Other pending issues are specification context. The optional `history_file` retains closed issues, their original reproductions and review-added evidence for selecting relevant regression checks. A historical closure applies to the recorded review version, not automatically to this candidate. Indexed paths are relative to `.forge/feedback/`; raw records retain run-local paths.

For each issue, check the claimed requirement, allowed inputs/faults, reachability and alternative explanations. Distinguish required behavior, ideal-model results and candidate claims. Apply protocol.md's complete W/s window premises when interpreting elapsed time; a preferred mechanism or unstated performance target is not a requirement. Keep a compliant implementation when evidence refutes the finding; do not change code merely to match the auditor's preference. Where feasible, run the original reproduction before editing. Preserve it and explain any small API adapter; failure to compile does not show a fix. Read its assertions and `polarity`: PASS may mean it reproduced the defect.

Use `execution_records` and the overview to locate retained inputs, commands and outputs. `restore` maps workspace destinations to input files; `outputs` includes logs and selected output files; `cwd_relative` records the source-relative working directory when available. The optional `evidence_index_file` also locates reusable cases, open questions and `supplemental_turns` from unfinished later investigations. Supplements retain changed files and raw logs; assess relevant tests or revised explanations before using them, without treating a draft as a completed report or another repair assignment. Inspect original assertions and implementation overlays before reusing them. Rebuild temporary binaries and explain path/API adaptations; old commands are not automatically portable. Preserve original evidence and relate before/after checks in the existing reasons or evidence references. Missing files or an obsolete API are reproduction limitations, not evidence of a fix.

Fix established causes while preserving the protocol and supported service behavior. Choose and justify the repair mechanism; the auditor's suggested solution is optional. Do not special-case tests, weaken assertions or disable required features. Check the original scenario and useful related cases, retaining commands, outputs and limitations. Update affected mechanisms and limits in `DESIGN.md` following `system.md`. An unsupported candidate performance claim may need correction without changing runtime behavior; describe that as a documentation correction, not a runtime fix. Neither correction nor a new limitation can remove a supplied requirement.

Choose unspecified mechanisms yourself and continue; multiple valid choices do not require researcher approval. Use `not_substantiated` when evidence supports rejecting the finding, and `unresolved` when your investigation remains incomplete. Reserve `needs_specification` for missing or contradictory required behavior that prevents determining a compliant fix; uncertainty about your implementation or its timing derivation alone is not such a gap. Identify the conflicting or missing rule and the materials checked. Continue independent repairs without rewriting supplied materials; identify any issue IDs that truly depend on the gap. Independent review assesses these claims even when code is unchanged. Follow `AGENTS.md` for delegation and workspace boundaries.

Inspect the diff and identify which mechanisms and assumptions changed. Select checks beyond the original triggering input to exercise the affected behavior and its interactions, including previously successful operations the change might now reject, delay or repeat. Consult relevant closed history and review-added tests; there is no requirement to run every historical test. Check what each assertion actually establishes: a suite pass or disappearance of the original witness may leave the affected requirement unchecked. Explain why the selected checks address the change, and what remains unchecked, in the existing summary/reason fields. A new limitation in `DESIGN.md` does not remove a supplied requirement.

Address `evidence_feedback` with evidence, explanation or a narrower claim. These observations are not verdicts or mandatory extra tests. Explain which source ran in mutable-work checks and how trace observations support the claim; distinguish recording, setup and implementation behavior.

Use `forge_local.isolated_exec` for TCP/multi-process checks; consult its tool description. Default work contains the evolving repair; `source="candidate"` selects the original input. Use `outputs` to retain selected workspace-relative files/directories before cleanup and check `artifacts` for exclusions. Cite actual execution records. Optional scheduling/replay helper `../inputs/schedule.py` provides `--help`; it does not validate protocol timing or correctness. Run schedules inside `isolated_exec` with retained inputs and absolute helper paths for captured source copies. `--replay` compares one version's exact requests/responses; `--plan` repeats a scenario across versions. Preserve original records and explain adaptations. Check which Core or Node handlers the adapter reaches; it must not supply missing behavior. Neither matching records nor an unavailable trigger establishes a fix.

Write `.forge/repair-result.json` with `input_commit`, `action` (`repaired` when candidate files changed, otherwise `no_change`), descriptive `summary`, and `issues`. Each issue needs `id`, `disposition` (`addressed`, `not_substantiated`, `unresolved`, `needs_specification`) and descriptive `reason`. Summary/reason may be nonempty text, lists or objects; control values are strings. Additional explanations and evidence references are welcome, without a fixed heading set. Explain relevant before/after checks, changes and remaining risks in a form that an independent reviewer can use. These are claims, not closure or deferral decisions.

Keep feedback intact and put regression tests in `tests/`. The reviewer receives the before/after candidates, your claims, feedback and retained isolated execution records. Finish with actual changes, commands/results and remaining limitations. Finite tests do not prove general safety or liveness.
