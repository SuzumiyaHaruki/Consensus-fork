## 2. 本次怎样定义和测量并发

### 2.1 统计协议中的实例

全局实际共识并发数 N(t) 是已接纳并开始协议、尚未在任何副本观察到决定的实例数。终点是第一次实际决定，不必等所有副本收到决定。

测量使用实现已有的 `admitted` 和 `decision` 事件，按实例 ID 去重。前者位于启动初始 Collect 之后，后者位于本地安装决定和清理任务之后；时长以这两个运行时位置为准。

驱动设置目标上限 1、4、16 或 32，观察到决定后释放请求名额，不等待 HTTP 回复。分别记录目标值、实际并发的时间平均值和峰值、客户端在途数。接纳、日志传递和补发需要时间，所以实际平均并发通常低于目标。

例如，独立键、均匀协调、目标 16 时，v003 的实际平均共识并发约 13.82，客户端平均在途数约 15.26，实际共识峰值为 16。

### 2.2 三种协调者分布

| 分布 | 驱动方式                                   | 保持一致的量     |
| ---- | ------------------------------------------ | ---------------- |
| 单点 | 所有请求交给副本 0 初始协调                | 全系统目标并发 N |
| 均匀 | 优先交给当前保留名额最少的副本，平局时轮转 | 全系统目标并发 N |
| 随机 | 固定随机种子，均匀随机选择初始协调者       | 全系统目标并发 N |

目标 16 是全系统共 16 个保留名额，分给七个协调者；副本参与其他协调者的实例，不另计为新的全局实例。

K 统一为 32，约束初始协调者尚未完成本地执行的实例，不直接限制参与其他副本实例的数量。

两版都由一个 goroutine 串行维护 Node 的协议状态，配合发送 worker 和 HTTP goroutine。实例等待回复时可推进其他实例，实现了共识过程并发，但没有并行修改同一 Node 的协议状态。

### 4.1 v003 没有普遍提高普通请求吞吐量

均匀和随机分布、目标 16，以及大载荷条件下，两版基本接近。低并发和单点协调的几个条件中，v003 的中位数反而较低。

重复间也有波动：目标 4、均匀分布，v000 为 379.6 / 436.0 / 436.4，v003 为 382.4 / 436.7 / 388.6，前两对接近，第三对差距较大。目标 16、单点协调时，三次 v003 都略慢。

### 4.2 增加并发为何会提高延迟

目标从 16 增至 32 后，均匀分布的实际平均并发从约 13.8 增至 29.6，但吞吐仍在约 400–435 请求/秒，客户端 P95 约翻倍。已经接近这套环境的处理能力时，再增加在途实例主要增加排队，而不是同比增加每秒完成量。

七个服务进程合计使用约 3.5–3.6 个 CPU 核，大载荷约 3.76 个核；状态处理、签名、编码和收发竞争有限资源，热点另有依赖等待。

### 4.3 内存与历史仍然增长

独立键、目标 16、均匀分布时，两版七进程总峰值 RSS 中位数约为 947 / 953 MiB；16 KiB 载荷时约为 3,209 / 3,263 MiB。这是集群 RSS 总和。

依赖向量压缩没有删除全部历史：初始值、决定、请求身份、执行记录和新增 KV 仍占内存。协议保留要求与实现冗余都可能贡献成本，不能全部算作泄漏。

同一轮 60 秒内也有吞吐下降。例如 v003、均匀分布、目标 16，前三次测量的首 10 秒/末 10 秒吞吐分别为 416.2/381.6、480.5/435.0、444.5/439.1。这个观察值得跟进，但固定时长会导致不同版本积累不同条数，且 GC、主机调度也在变化，所以本次不把它作为历史规模的独立因果实验。

## 5. 热点负载的结果

目标并发 16，协调者均匀分布，反复写同一个键。两版各测三次，每次 60 秒，其他参数与独立键测量一致。

| 指标                        |               v000 |                  v003 |
| --------------------------- | -----------------: | --------------------: |
| 三次吞吐量，请求/秒         | 96.1 / 98.1 / 99.8 | 124.3 / 116.6 / 127.2 |
| 吞吐量中位数，请求/秒       |               98.1 |                 124.3 |
| 实际平均共识并发的中位数    |              15.39 |                 15.36 |
| 共识并发峰值                |                 16 |                    16 |
| 客户端 P95 中位数，ms       |             366.37 |                352.92 |
| 共识阶段 P95 中位数，ms     |             341.04 |                334.69 |
| 七进程平均 CPU 核数的中位数 |               2.86 |                  2.44 |

六组测量均通过排空后的状态检查，没有观察到重复执行事件、丢失决定或 window miss。v003 的吞吐中位数提高约 26.7%，三次配对都更快，P95 只有较小下降。两版各有约 46–47 次/秒启动正式 Accept，v003 同时完成了更多请求；启动 Accept 的比例不同，不能将全部收益直接归因于某一个图算法优化，仍需 profile 或逐项消融才能进一步解释。

热点还有一个重要观察：客户端平均在途数中位数约为 31.16 / 36.82，而共识在途数只有约 15.4。决定后的执行和回复等待积累了更多客户端请求。若把客户端等待数当成协议并发，本来相同的目标负载就会被误认为 v003 使用了更高的共识并发。

## 6. 协议符合性与正确性

### 6.1 测试结果

两版的 `MIX_TCP_TEST=1 go test ./...`、`go test -race ./...` 和 `go vet ./...` 全部通过，包括原有恢复、依赖执行和客户端回归。部分大规模性能测试需单独启用，未随普通套件执行。

新增的 16 组七进程历史也全部通过：每版四个随机种子，分别测试无崩溃和请求开始前停止两个副本。每组在四个键上混合执行 96 个 Put/Get/Delete 逻辑请求，并向不同入口加入 16 次重复提交。

独立检查器根据实际决定、执行事件和客户端回复重建依赖图并重放 KV，检查决定一致性、冲突依赖、执行顺序、重复执行及返回结果。人为改坏观察数据中的决定、KV、执行事件或结果时，检查器均能报错。

原套件中的协调者中途崩溃、accepted 继承、HELP/SCC 和小门槛分支也已重跑。

### 6.2 已有问题的修复验证

下面两项均由原实验第一轮审计发现，本次重新运行复现，确认 v000 存在问题、v003 已修复。

| 问题                       | v000                                                                                                  | v003                                       |
| -------------------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| carry 数据完成后未及时登记 | 已取回的冲突命令要等下一次周期处理才可见，期间新命令可能遗漏该依赖                                    | 数据完成时立即登记，后续冲突观察包含该命令 |
| 客户端结果截断             | 合法读结果经 JSON 编码后超过读取上限，首次读取得到 UNKNOWN，重试只返回 ALREADY_EXECUTED，无法取回结果 | 调整响应读取上限，同一请求获得完整结果     |

carry 检查确认的是协议要求的登记时序被违反，没有进一步构造副本决定分叉。

## 7. 性能修复是否有真实收益

### 7.1 缺失历史：本次直接复现的收益

保留七个真实 Node，延迟到其中一个副本的部分原始消息，最后递送最新实际 Learn，让它通过 Fetch 取得缺失历史。

| 历史条数 | Fetch 发送次数：v000 / v003 | 补齐耗时 ms：v000 / v003 |
| -------: | --------------------------: | -----------------------: |
|       16 |                    138 / 90 |            169.8 / 156.7 |
|       64 |                 1,428 / 378 |            680.9 / 694.5 |
|      256 |              58,404 / 1,530 |        7,278.0 / 3,017.5 |

v000 已保存某条初始记录，却因其递归依赖尚不完整而继续 Fetch 该记录，重复传输随着链增长。v003 将“本条记录字节已取得”和“递归闭包已完整”分开：拿到本条记录就退休它自己的 Fetch，其缺失依赖各自继续获取。256 条时发送减少约 97.4%，耗时减少约 58.5%；64 条时没有墙钟时间提升，说明不能将通信减少直接当成每个规模都加速。

两版都完成对应历史和最终 KV；该受控场景没有观察到 window miss 或丢失事件。它测试的是活副本补齐尚不知道的材料，没有重新启动 crash-stop 副本。

### 7.2 不变的阻塞图

本次复用旧审计的同一份 `blocked_graph_test.go`，在两版分别建立三个真实 Node：一个副本已拿到后续决定，但缺少最前面一条命令的决定，使一组热点依赖暂时不能执行。随后重复递送 100 次实际捕获的 Learn，并提交 15 条无关键请求；最后释放被延迟的真实决定，检查所有历史仍能执行。三个 Node 用于隔离这个本地算法问题，普通性能矩阵仍是七个独立进程。

| 阻塞历史条数 | 100 次重复通知处理耗时 ms：v000 / v003 | 无关请求延迟中位数 ms：v000 / v003 |
| -----------: | -------------------------------------: | ---------------------------------: |
|           32 |                           30.09 / 1.76 |                      2.921 / 0.211 |
|          128 |                          277.03 / 1.07 |                     19.654 / 0.169 |
|          256 |                          959.65 / 1.70 |                     67.041 / 0.471 |

v000 反复计算未变化的阻塞图，拖慢了本可执行的无关命令。v003 复用就绪检查结果，256 条时将无关请求中位延迟从约 67 ms 降至 0.47 ms；释放缺失决定后，积压历史仍能完成。

该专项每个规模只测一次，在 W=60 秒内完成且无 window miss，用于验证成本机制，不代表普通 HTTP 请求的稳定延迟分布。

## 8. 对后续提示词与工作流的启示

第一，生成侧应分别报告客户端在途、已接纳未决定、已决定未执行的数量，以及协调者分布和 K。“并发请求性能”这一笼统要求不足以区分这些量，但无需限定实现的线程和队列结构。

第二，审计应把协议状态转移与实际结果结合。carry 问题发生在数据完整但尚未登记的短暂窗口，一般读写与 race 检查仍可通过。围绕原子性、时序和数据可用性构造真实 Node 场景，比单纯增加随机请求更有针对性。

第三，性能审计应说明场景可达性、重复工作和正确完成条件，同时测普通路径与特殊状态。普通吞吐接近不能否定 Fetch 修复的价值，特殊场景加速也不能替代普通路径回归。

第四，交接须保留复现及断言含义：本次旧测试的 PASS 表示“缺陷出现”，预期 FAIL 表示缺陷条件不再成立。还需核对实际状态和正向回归，避免把其他失败误当成修复成功。

优先完善性能报告要求和可复用测试材料，再决定是否修改控制器。
