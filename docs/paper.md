# 论文思路与研究记录

本文件持续记录实验和分析过程中形成的论文想法，区分已有观察、拟采用的方法表述和待验证的主张。它不是 agent 输入，也不自动改变协议、提示词或控制流。最近的测量与版本问题见 [v000 与 v003 评测](exploratory-1110.md)，评估方法见 [evaluation.md](evaluation.md)，仍待讨论的设计选择见 [design-issues.md](design-issues.md)。

## 1. 当前研究主线

研究问题：如何利用强 coding agent，从给定的新共识设计出发，从零构建具备真实运行时、高并发和副本内多核处理能力的系统，并通过适度的引导、审计和迭代修复提高交付质量？

工作的出发点是模型已经具有相当强的系统实现能力。已有 baseline 能自主交付 Node、传输、客户端和服务程序，组织真实网络测试，定位部分问题并修改代码。研究目标是在这个能力基础上，让 agent 承担更完整、更复杂的共识系统工程任务；不能预设直接使用 Codex 一定只能生成很差的实现。

给定协议核心后，实现者仍需决定状态归属、并发同步、消息与计时器调度、协议与应用执行的交互、资源限制和后台推进。单项选择往往有多个合法方案，困难在于组合后的实现是否仍符合协议、运行是否正确，以及负载与历史增长后是否保持合理成本。一次生成和自主测试可能遗漏交互场景，修复也可能影响原来正确的行为。

当前方法把协议要求、实现选择和执行证据连接起来：生成侧自主设计并解释重要机制；审计侧独立选择合法场景，检查真实运行行为；修复侧利用完整证据核查根因、选择修改方案；独立复核检查修改后的相关行为。提示词、控制器和流程共同支持这些工作，并在明确目标与保留自主判断之间取得平衡。

“接近生产可用”需要落实为可检查的能力，不以代码规模或能启动一个服务作为替代：

| 能力 | 本工作的具体关注 |
| --- | --- |
| 完整运行路径 | 可复用 Node、真实通信、独立服务进程、客户端、实际执行结果与运行说明 |
| 并发与并行 | 多个实例持续推进；协议允许的正常处理工作可在同一副本内利用多核，区分客户端等待数、共识在途数和实际同时运行 |
| 故障和生命周期 | 在给定故障模型内处理失败、重试、过载和关闭，后台工作不因新请求或满槽而失去推进机会 |
| 连续服务成本 | 检查不同负载、历史规模和空闲阶段的延迟、吞吐、通信与资源使用，区分必要保留和不必要工作 |
| 工程组织 | 状态与模块职责清楚，关键选择可解释，真实运行路径可测试，文档随实现更新 |

当前以混合 EPaxos 为深入案例，范围仍由给定的 crash-stop 模型和系统材料确定，不因使用“生产”一词就默认增加成员变更、崩溃重启或所有部署功能。协议设计在一次实验内给定，真实设计缺口应被记录，而不是通过偷偷改变保证来解决。

暂定标题：**Consensus Forge: Building Concurrent Consensus Systems with Coding Agents**。标题和贡献表述随实验调整，优先把现有任务做深，不以增加协议数量作为默认扩展方向。

## 2. 从 SYSSPEC 借鉴什么

SYSSPEC、Agora 和 Specula 在这里用于学习方法表达、论文结构和提示词组织，不作为已经确定的共识领域相关工作集合。相关工作需要围绕本研究问题另行梳理，不能根据这些参考对象就断言现有工作没有结合生成与审计。

SYSSPEC 将设计表达组织为功能、模块和并发规格，并用规格补丁及生成、评审、反馈重试和整体测试支持实现与演化。其规格借鉴形式化方法，以结构化自然语言表达；不能把这种组织等同于已经获得机器证明。[原文 §3–§4.5](https://arxiv.org/html/2512.13047v4)

值得借鉴的是把工程经验提炼为可解释的方法：明确处理对象，描述对象之间的关系，给出每一步操作及其理由，再通过实验分辨各部分的作用。提示词承载其中一些规则，工具和控制流承载另外一些规则。贡献应当落在这些规则如何解决具体困难，以及效果能否被检验，而不是提示词数量、agent 数量或 Python 代码规模。

我们可以先定义清楚“哪些要求必须保留”“如何把抽象动作落实到运行时”“什么证据支持一个发现”“怎样判断修改影响”。符号用于消除混淆，具体场景用于解释含义；不为了形式化外观引入没有用途的概念或公式。

## 3. 方法需要明确的对象与关系

以下是论文层面的候选表述，用于梳理已有实践及其不足，不要求新建数据格式或让 agent 填写另一套表格。

| 对象 | 含义 | 需要明确的边界 |
| --- | --- | --- |
| 给定设计 | 协议规则、外部假设和目标服务行为 | 一次实验内固定；材料未规定的工程机制由实现选择 |
| 实现版本 | 某个版本的源码及实际运行机制 | 文档说明和实现事实可能不一致，结论关联到具体版本 |
| 规则与机制的对应 | 某项要求由哪些入口、状态转换、任务和事件实现 | 相同函数名不说明语义相同；不同架构也可能满足相同要求 |
| 调查场景 | 请求、消息、时间、故障与本地事件的安排 | 场景需符合所引用的协议前提，测试替换的机制应明确 |
| 执行证据 | 场景中的实际观察、相关命令与结果，以及对观察的解释 | 测试请求的动作不等于实际发生的事件；记录存在不等于结论成立 |
| 修复及复核 | 对版本的修改，以及对原问题和相关行为的检查 | 旧版本的发现和关闭结论不会自动适用于新版本 |

最重要的对应关系可以写成：**协议规则 → 实现机制 → 合法场景 → 实际观察 → 修复后的再次检查**。论文需要说明每个箭头如何建立，以及哪一环可能失败；`DESIGN.md`、复现代码、报告和执行记录分别承载这些内容。

对能用有限执行反例支持的发现，可以采用简短记号：设 A 为相关外部假设，r 为要求，I_v 为实现版本，s 为场景，τ 为实际观察。一个发现需要分别解释三个判断：

```text
Legal_A(s)               场景满足相关前提
Executes(I_v, s, τ)      观察来自该版本在该场景中的实际运行
Violates_r(τ)            观察足以支持违反要求 r 的结论
```

这三个判断说明审计应提供什么依据，不是框架已经实现的三个自动判定函数。源码推理可以补充执行观察；涉及最终进度的主张还需要解释公平性、重复调度或缺少推进机制，单次有限等待不足以证明永久停滞。证据不足时保留更窄的结论与未解决疑点。

对实现映射，重点说明抽象事件的含义和寿命。例如“广播开始”“本地发送完成”“回复被处理”“观察收集结束”“任务终止”可能是不同事件。实现可以把它们拆开或合并，但必须说明相关要求怎样得到保留。该对应关系由生成者提出，并接受审计，不被当作可信答案。

## 4. 三个部分怎样形成一个方法

| 部分 | 要解决的具体困难 | 方法操作 | 保留给 agent 的选择 |
| --- | --- | --- | --- |
| 生成 | 抽象协议需要展开成完整、并发的运行机制，局部选择可能相互影响 | 按完整运行路径推进，说明关键状态归属和事件边界，提供实际 Node 的检查入口 | 架构、数据结构、同步机制、接口及具体开发和自测方案 |
| 审计 | 问题可能只在特定运行交错、故障组合或历史规模出现，测试本身也可能误解要求 | 独立提出怀疑，构造合法且可达的场景，核对观察、断言与结论 | 调查方向、复现方式、成本定位方法，以及确认、排除或保留疑问 |
| 交接、修复与复核 | 文字摘要容易丢失条件，局部修复可能改变其他路径 | 保留原始证据和版本，核查根因，检查改动影响，独立复核并复用历史案例 | 判断发现是否成立、选择修复方式和相关回归，不必照搬审计者的方案 |

三个部分围绕同一条关系工作：生成让实现选择可以被检查，审计形成有依据的发现，交接和复核让这些发现对后续版本继续有用。发现问题、解释原因和判断修复是不同任务，即使由同一种模型承担，也分别保留依据。

### 4.1 约束与自主性的边界

基本原则是明确目标行为、判断依据和交付责任，把实现与调查方法留给 agent。约束过松时，“支持并行”可能只落实成辅助任务并行，测试通过可能被扩大为整体正确，生成也可能不断增加交付前检查。约束过机械时，指定架构、固定调查路线、僵硬格式或不合适的阶段截止会限制合法方案，带偏调查，或阻断已经获得的有用证据。

| 需要明确的内容 | 不提前固定的内容 | 怎样观察这个边界是否有效 |
| --- | --- | --- |
| 协议义务、服务能力和运行前提 | 队列、锁、线程与数据结构的具体组合 | 检查真实代码和运行路径是否满足目标，而不按架构名称判定 |
| 发现需要场景、观察、原因与复现依据 | 必查缺陷清单、唯一反例形式和固定测试数量 | 人工判断发现质量、证据是否支持结论，以及遗漏发生在哪里 |
| 文档能定位关键选择和证据 | 逐函数填表、逐条配测试或唯一章节结构 | 检查作者是否梳理清楚、接收者是否能理解和复用，文档整齐本身不计质量收益 |
| 版本、执行记录与交付文件的关联 | 由控制器判断协议语义或自动认定修复正确 | 检查错配、丢失、中断和错误关闭；记录机械检查是否不必要地阻断工作 |
| 生成、修复与审计的职责及收尾责任 | 用一个固定时长代替所有阶段的完成判断 | 区分必要调查、有效修复、重复验证和交付整理的时间与产出 |

这些是待检验的方法选择，不是新增一套格式、质量门禁或自动性质判断器。安全隔离与权限边界继续保留。对“平衡”的论证需要说明具体约束改变了什么行为，不能仅用“既有约束又有自由”概括。

### 4.2 提示词与控制器各自承担什么

提示词澄清能力目标，帮助 agent 建立要求、机制和证据的对应，明确角色职责。Python 处理材料交付、执行环境、版本与证据关联、阶段状态和结果流转。控制器能核对引用和版本等事实，不能仅凭字段、退出码或测试数量裁定共识正确。

生成侧需要认真自测，但不承担无限调查所有潜在场景的责任；已完成重要实现与相关检查后，应整理交付，把未覆盖部分作为审计线索。修复侧围绕成立的问题和改动影响工作，独立审计保留重新选择调查方向的空间。当前提示已经允许报告不确定性，具体收尾行为和是否需要进一步引导仍需观察，不在本文直接改变运行策略。

当前已有上述组织方式的基本实现。哪些提示改善了设计选择，哪些控制器机制减少了交接损失，以及哪些额外检查只有成本没有收益，应通过对照分别判断。

## 5. 共识系统带来的具体研究内容

**前提决定反例是否成立。** 同样的超时，在不同 W/s、故障和公平性条件下可能具有不同含义。审计需要解释哪些事件受假设约束，哪些属于实现应完成的本地工作。窗口条件不成立时的测量可以反映运行成本，却不能直接作为该条件下活性保证的反例。

**关键行为分散在多个位置。** 客户端收到成功只观察到一条服务路径。决定传播、恢复排队和迟到票处理可能尚未完成，真实 Node 的队列、计时器和传输会影响它们是否发生。测试需要选择能观察相应要求的位置，而不只是增加请求数量。

**共享运行机制承载多条协议路径。** 同一个取消、重试或资源清理机制可能同时服务正常流程与恢复流程。一个修复的影响需要沿这些使用关系分析；原缺陷消失不表示其他路径仍然保留。

**实现自由与协议边界需要同时保留。** 协议明确规定的条件、消息义务和分支必须实现；锁、队列和数据结构等未规定机制可以自主选择。没有必要把所有工程选择提前写成唯一答案，也不能把明确的协议偏离当作实现偏好。

## 6. 已有案例怎样支撑论文

### 6.1 强模型的能力、目标引导和剩余盲区

11 月 11 日两轮 baseline 都在约一小时内自主交付完整系统并进行了真实运行检查。第一轮有多个 worker，但常规入站协议处理仍集中使用全局锁；澄清正常共识路径的副本内并行要求后，第二轮采用实例锁，并根据实际 trace 中未出现同阶段重叠的观察，修改数据检查的锁粒度。重新核对的 trace 显示同一副本内普通 Accept 区间在不同 Go P 上同时 Running。这支持强模型可以自主完成更复杂的设计与调查，也支持明确目标和证据要求具有实际作用。

该观察的边界同样明确：重叠区间很短，部分主要路径仍串行，吞吐收益受窗口、发送并行和重试影响。研究者随后在没有新请求的空闲阶段确认，七副本各保留 2,048 条历史后，合计临时分配约 122 MiB/s，分配剖析将主要成本定位到按全部历史数量预留活跃列表的代码。正常功能与并行检查通过，仍没有覆盖连续服务的所有成本。

第一轮还存在真实 TCP 发送失败阻塞小门槛 Collect 的问题：分开的崩溃测试和小门槛测试都通过，组合场景却失败。第二轮独立生成没有重现该缺陷，不能将其称为流程反馈修复。详细材料见 [第一轮 baseline 分析](../experiments/baseline-analysis-20261111T033512Z/analysis.md)和[第二轮 baseline 分析](../experiments/baseline-analysis-20261111T045859Z/analysis.md)。

两轮共有的 system.md 发生了目标澄清，因此这些观察不能作为 Forge 独有方法优于 baseline 的结果。它们适合作为任务可行性、引导边界和自主验证盲区的动机；结构化生成指导及后续审计修复的额外作用由第 7 节的共同条件对照检验。

### 6.2 PreAccept 取消：协议偏离与修复回归

v001 为解决失败目标队列饥饿，引入了保留队列和取消机制，却把 Collect 完成与初始任务结束混为一谈；v003 仍保留该行为。七副本场景中，大门槛 L=4，快路径门槛 F=6，剩余首次发送被取消后无法产生所需快票。请求最终仍能通过慢路径完成，因此原缺陷检查和普通成功断言可能通过。

已有定向对照中，W=500ms，后三个 PreAccept 延迟 80ms；v000 约 83ms 完成，v003 约 522ms，让 v003 的排队 PreAccept 继续完成后约 88ms。最后一项是传输诊断对照，不是已交付的修正版。它把实现机制、实际执行和性能后果连接起来；见 [定向测试](../experiments/three-way-evaluation-20261110T004523Z/work/templates/fastcancel_test.go)、[原始观察](../experiments/three-way-evaluation-20261110T004523Z/work/supplemental/v003-fast-cancel-observations.json)及[候选源码](../experiments/three-way-evaluation-20261110T004523Z/work/sources/v003/protocol.go)。

这个案例支持“协议符合性需要单独检查”，也说明独立会话仍可能共同接受错误的生命周期解释。它应当用于提出问题、解释方法和分析失败。新方法能否更早发现或阻止此类回归，需要后续实验，不能把已经用于修改提示的案例当作未见场景成绩。

### 6.3 其他案例承担不同论证作用

| 案例 | 可支持的观察 | 需要避免混淆的结论 |
| --- | --- | --- |
| baseline 缺少决定重传 | 正常服务可运行，但遗漏后台协议工作；真实 HTTP 场景和源码共同支持缺陷 | 不能由一个缺陷推断 baseline 整体不可用 |
| 恢复与传播调度饥饿 | 持续新工作会影响旧工作，审计和修复解决了具体进度问题 | 有限等待本身不证明无限饥饿，需结合调度机制解释 |
| 发送完成通知丢失 | 实际运行时完成事件可能丢失，即使协议核心转换本身没有直接错误 | 4097 配置的定向测试不是 4097 进程部署 |
| Unicode 校验 | 外部输入到内部命令的转换可能改变语义，系统边界也有真实缺陷 | 这是服务输入问题，不算副本决定分歧 |
| 小队列故障配置延迟 | 已修复机制仍可能有很差的运行成本或不稳定测试预算 | 不能把所有超时都计作新的永久停滞 |

## 7. 拟检验的主张与实验

### 7.1 基本对照

| 条件 | 获得的内容与运行方式 | 回答的问题 |
| --- | --- | --- |
| A：原生自主生成 | 共同协议和系统目标、相同工具与必要工作范围要求；自主设计、实现、自测和交付 | 强 coding agent 本身已经能完成什么，仍会遗漏什么 |
| B：加入生成指导 | 与 A 相同的目标和工具，增加 Forge 的实现组织、关键选择说明及证据解释指导；只评价首次交付 | 方法指导是否改善首次实现和自主检查的质量 |
| C：完整 Forge | 在 B 的生成后继续独立审计、证据交接、修复与复核 | 后续协作在初始实现之上带来多少有效改进，代价和回归是什么 |

B 可以使用 Forge 保存的 v000 单独评价，C 使用同一次运行的后续版本；二者不是独立重复样本。A 与 B/C 使用相同版本的 protocol.md、system.md、模型和工具能力，并采用相同的默认生成停止策略。基准条件保留原生子智能体、自测和自主修正能力，不通过删除关键信息或工具人为削弱它。

共同系统要求的澄清是一类单独的变化。例如“正常协议处理路径中的并行”明确后，baseline 也必须获得该要求。分析应区分任务目标更清楚、生成方法更好、以及独立迭代带来的收益，不能将三者合并解释成流程效果。

### 7.2 机制与边界

| 拟检验的主张 | 已有观察或依据 | 有区分力的检查 |
| --- | --- | --- |
| 强 agent 能承担完整共识系统构建 | baseline 已能独立交付真实 Node、网络服务和自主测试，并作出并发设计选择 | 在固定任务范围下重复生成，用独立场景检查能力是否稳定落实 |
| 生成指导改善首次交付 | 现有过程记录显示不同的组织、自查和证据使用方式；尚需共同条件对照 | 比较 A 与 B 的协议符合性、正确性、并行能力、性能及实际投入 |
| 独立审计补充自主检查的盲区 | 研究者已在自主测试通过的实现中找到合法故障组合和空闲历史成本问题 | 对同一批候选比较继续自主检查与独立审计，记录真实发现、遗漏和成本 |
| 可执行证据使修复更可靠或高效 | 流程已能保留和复用原始复现，文字解释与复现含义仍可能不一致 | 对同一候选和同一发现比较文字反馈与附带可执行材料的反馈 |
| 复核和历史证据有助于控制回归 | 已有复用机制，也有 PreAccept 回归被审计和复核遗漏的案例 | 分别检查原问题、相关路径、错误关闭和旧问题重新出现 |
| 适度约束优于过松或过机械的组织 | 并行目标歧义、交接阻断和收尾过慢提供了具体问题 | 选有实际依据的约束做局部对照，评价合法方案是否被限制、调查是否被带偏、交接是否改善 |

基本对照之后再做有限机制比较，包括普通的生成—审阅—修复循环与当前证据交接、复核组织的区别。不为了“平衡”的叙述构造故意失效的机械基线，也不要求一次实验覆盖所有约束组合。

### 7.3 评价与资源投入

最终实现使用共同的独立评价场景，分别记录协议符合性、正确性、实际共识并发与副本内并行、故障推进、负载和历史成本。报告人工确认的不同根因、发现证据的有效性、有效修复、引入的回归、未见场景表现，以及模型、墙钟时间和 token 投入。测试数、报告数和代码行数只描述规模。

同时观察默认自主停止策略下的质量与成本，以及可比资源投入下的方法效果。完整流程投入更多资源时，需要给自主检查或普通审阅修复对照可比的后续投入，不能把多花时间全部解释为协作收益，也不要求 agent 为凑预算机械工作到最后一秒。多次生成和重复测量用于区分机制效果与运行差异。

分析过程本身也能提供论文证据：agent 提出了哪些怀疑，排除了哪些，哪些得到复现，哪些修复引入了回归，哪些阶段花费了时间却没有新增依据。研究者判断真实缺陷与证据充分性，不把 agent 的 fixed 声明或流程正常结束直接当作终测结论。

用于发展提示和工具的已知案例，与后续评价场景分别记录。协议和系统范围变化时同步给 baseline，历史输入与结果保持原样。不能把不同协议版本的代码量、缺陷数或吞吐差异直接解释为方法收益。

## 8. 论文组织与下一步

引言按以下顺序展开：

1. **能力与机会：**强 coding agent 已能自主完成较复杂的实现，可以尝试从新共识设计构建完整并发系统；用已有 baseline 的实际交付建立这个出发点。
2. **任务与困难：**协议核心与真实运行系统之间存在工程选择，正确性、并行、故障处理和连续服务成本需要共同满足；用具体案例说明组合后的问题。
3. **方法问题：**完全自由的生成与自测会有盲区，固定架构、调查路线和僵硬交接又可能限制能力。需要明确目标、依据和职责，同时保留实现与调查的自主权。
4. **方法设计：**介绍生成指导、独立审计、可执行证据交接、修复和复核如何共同工作，以及提示词和控制器各自承担的有限职责。
5. **评价与发现：**通过 A/B/C 和必要的局部对照，报告质量、有效修复、回归、性能与资源成本，并解释收益来自哪里、哪些情况下没有收益。

摘要可以据此组织为“强模型使完整系统构建成为可研究任务—工程细化和迭代仍存在困难—提出保留自主性的引导与验证方法—在给定共识设计上开展对照—报告实际效果与边界”。目前只确定这个骨架，定量效果随正式实验填写。

方法章节保留第 3 节的对象与关系，用实际案例解释如何建立对应、如何调查和如何修复；实现章节再介绍提示词、Python 和工具怎样承载这些操作。讨论章节分析设计材料的责任、模型判断的失效、约束的代价和生成收尾效率。SYSSPEC 等参考用于表达与组织，相关工作另按共识实现生成、分布式系统检验和协作修复问题梳理。

候选贡献包括：面向新共识设计的完整并发系统构建任务与实证研究；在明确目标和保留自主权之间组织生成、审计及修复的方法；落实该方法的框架和可复现评价。方法价值通过它缓解的具体困难与对照效果体现，不以提示词长度、流程环节数或“多 agent”本身作为贡献。

下一步优先固定当前协议与系统目标，保存强 baseline，评价 Forge 的首次与最终交付，再安排有区分力的对照。新发现优先沉淀为案例和回归资产，不不断变成给生成或审计的点名答案。暂不为论文表述增加独立语言、自动性质裁定器或复杂流程。

### 2026-11-10：从提示词工程提炼方法

用户提出 SYSSPEC 的优点在于清晰、形式化，并把看似简单的工程组织成方法论。当前采用的方向是先明确研究对象、语义关系、阶段操作与可检验主张，再将提示词和 Python 解释为实现载体。上述对象和记号是研究表述草案，不是新增运行要求。

同日已核对上一轮中英文提示同步：`protocol.md` 明确 Collect 完成不单独终止未完成 PreAccept；`AUDIT.md` 区分协议符合性、正确性和性能；`REPAIR.md` 与 `VERIFY.md` 要求按修改影响检查条件、消息义务及后续路径。baseline 的共同协议已同步。协议澄清和方法提示的收益需由新实验判断。

### 2026-11-10：用轻量文档结构帮助推理与交接

已在中英文角色提示中落实少量信息类别：`DESIGN.md` 组织系统结构、关键实现选择与检查缺口，关键选择串联要求、机制、符合性解释和证据；审计报告组织范围、发现、未完成或已排除的调查，每项发现分清要求、场景、观察、原因与复现。修复沿用现有 summary/reason，复核沿问题 ID 对照原要求、前后观察与相关影响。

标题可以合并或调整，相关内容通过引用复用，不要求填空式逐函数说明，也没有新增控制器格式校验或交付文件。共同协议与 baseline 提示保持原样。待检验的作用是让作者更容易发现自己的推理缺口，并让接收者更容易定位依据、复用证据和核查改动；文档整齐本身不计作方法有效的证据。

### 2026-11-11：以强模型构建复杂共识系统为主线

用户明确调整研究定位：以当前 LLM 已经具备较强实现能力为起点，利用它从零实现更接近生产使用的高并发新共识系统；同时针对仍会存在的问题与遗漏，优化提示词、控制器和生成—审计—修复组织。核心取舍是约束过机械会限制或带偏模型，过于自由又难以保证目标落实和可靠交付，最终用实验对照说明这种组织的意义。

据此重写当前主线、方法边界和论文组织，保留“要求—机制—场景—观察—修复复核”的方法框架。基本对照分为原生自主生成、加入生成指导的首次交付、完整 Forge；共同需求澄清不计作 Forge 独有收益。近期两轮 baseline 作为能力、引导与盲区的观察，尚不替代共同条件下的正式方法评价。本次只更新研究笔记，不改变正在运行的实验或其输入。
