# 论文思路与研究记录

本文件持续记录实验和分析过程中形成的论文想法，区分已有观察、拟采用的方法表述和待验证的主张。它不是 agent 输入，也不自动改变协议、提示词或控制流。最近的测量与版本问题见 [v000 与 v003 评测](exploratory-1110.md)，评估方法见 [evaluation.md](evaluation.md)，仍待讨论的设计选择见 [design-issues.md](design-issues.md)。

## 1. 当前研究主线

研究问题：给定共识协议与系统目标，如何组织 coding agent 的生成、审计和修复，使协议规定的行为在真实运行时实现及多轮修改中得到保持，并提高交付系统的正确性和运行质量？

当前核心思路是把协议要求、实现选择和执行证据连接起来：生成侧解释重要机制如何满足要求；审计侧通过实际 Node 的合法执行寻找反例；修复和独立复核使用可复现证据检查原问题及改动影响的其他路径。实现者保留选择队列、锁、任务、网络接口和数据结构的自由。

暂定标题：**Consensus Forge: Generating and Refining Consensus Implementations with Executable Evidence**。标题和贡献表述随实验调整，目前优先围绕混合 EPaxos 做深入案例，不以加入更多协议或功能作为默认扩展方向。

## 2. 从 SYSSPEC 借鉴什么

SYSSPEC 将设计表达组织为功能、模块和并发规格，并用规格补丁及生成、评审、反馈重试和整体测试支持实现与演化。其规格借鉴形式化方法，以结构化自然语言表达；不能把这种组织等同于已经获得机器证明。[原文 §3–§4.5](https://arxiv.org/html/2512.13047v4)

值得借鉴的是把工程经验提炼为可解释的方法：明确处理对象，描述对象之间的关系，给出每一步操作及其理由，再通过实验分辨各部分的作用。提示词承载其中一些规则，工具和控制流承载另外一些规则。贡献应当落在这些规则如何解决具体困难，以及效果能否被检验，而不是提示词数量、agent 数量或 Python 代码规模。

我们可以先定义清楚“哪些要求必须保留”“如何把抽象动作落实到运行时”“什么证据支持一个发现”“怎样判断修改影响”。符号用于消除混淆，具体场景用于解释含义；不为了形式化外观引入没有用途的概念或公式。

## 3. 方法需要明确的对象与关系

以下是论文层面的候选表述，用于梳理已有实践及其不足，不要求新建数据格式或让 agent 填写另一套表格。

| 对象 | 含义 | 需要明确的边界 |
| --- | --- | --- |
| 给定设计 | 协议规则、外部假设和目标服务行为 | 一次实验内固定；材料未规定的工程机制由实现选择 |
| 实现版本 | 某个版本的源码及实际运行机制 | 文档说明和实现事实可能不一致，结论关联到具体版本 |
| 规则与机制的对应 | 某项要求由哪些入口、状态转换、任务和事件实现 | 相同函数名不说明语义相同；不同架构也可能满足相同要求 |
| 调查场景 | 请求、消息、时间、故障与本地事件的安排 | 场景需符合所引用的协议前提，测试替换的机制应明确 |
| 执行证据 | 场景中的实际观察、相关命令与结果，以及对观察的解释 | 测试请求的动作不等于实际发生的事件；记录存在不等于结论成立 |
| 修复及复核 | 对版本的修改，以及对原问题和相关行为的检查 | 旧版本的发现和关闭结论不会自动适用于新版本 |

最重要的对应关系可以写成：**协议规则 → 实现机制 → 合法场景 → 实际观察 → 修复后的再次检查**。论文需要说明每个箭头如何建立，以及哪一环可能失败；`DESIGN.md`、复现代码、报告和执行记录分别承载这些内容。

对能用有限执行反例支持的发现，可以采用简短记号：设 A 为相关外部假设，r 为要求，I_v 为实现版本，s 为场景，τ 为实际观察。一个发现需要分别解释三个判断：

```text
Legal_A(s)               场景满足相关前提
Executes(I_v, s, τ)      观察来自该版本在该场景中的实际运行
Violates_r(τ)            观察足以支持违反要求 r 的结论
```

这三个判断说明审计应提供什么依据，不是框架已经实现的三个自动判定函数。源码推理可以补充执行观察；涉及最终进度的主张还需要解释公平性、重复调度或缺少推进机制，单次有限等待不足以证明永久停滞。证据不足时保留更窄的结论与未解决疑点。

对实现映射，重点说明抽象事件的含义和寿命。例如“广播开始”“本地发送完成”“回复被处理”“观察收集结束”“任务终止”可能是不同事件。实现可以把它们拆开或合并，但必须说明相关要求怎样得到保留。该对应关系由生成者提出，并接受审计，不被当作可信答案。

## 4. 三个部分怎样形成一个方法

| 部分 | 要解决的具体困难 | 方法操作 | 可检查的交付 |
| --- | --- | --- | --- |
| 生成 | 协议抽象动作展开成并发运行机制时可能丢失条件或职责 | 按完整运行路径推进实现，说明关键状态归属、事件边界及生命周期，提供实际 Node 的控制和观察入口 | 可运行系统、与代码对应的设计说明、真实路径检查及其范围 |
| 审计 | 缺陷依赖合法执行交错，测试自身也可能误解模型或断言 | 从要求和实现机制提出怀疑，在实际入口构造场景，核对观察是否支持结论 | 带版本、场景、观察、因果解释的发现，及被排除或未完成的调查 |
| 交接、修复与复核 | 文字结论可能丢失触发条件，局部修复可能改变其他协议路径 | 交付原始证据，重放并核查根因；按修改影响检查协议行为，独立复核并保留可复用案例 | 前后版本、原问题的处理依据、相关回归观察和未检查范围 |

这三个部分围绕同一条证据关系展开。生成让实现选择可以被检查，审计获得反例，交接和复核让反例在修改后继续有用。发现问题、解释原因和判断修复是不同任务，即使由相同模型承担，也需要分别保留依据。

提示词负责引导语义推理与调查，Python 负责版本、执行、文件传递和结果关联。控制器能检查引用是否存在、版本是否匹配，却不能仅凭 JSON 字段或退出码判断共识正确。方法的效果最终通过独立测试、源码审阅及实验比较检验。

当前已有这些机制的基本实现，但它们的收益和失效边界仍需分别验证。尤其是“按改动影响选择回归”目前主要依靠 agent 判断，新提示的效果尚不能从旧实验推出。

## 5. 共识系统带来的具体研究内容

**前提决定反例是否成立。** 同样的超时，在不同 W/s、故障和公平性条件下可能具有不同含义。审计需要解释哪些事件受假设约束，哪些属于实现应完成的本地工作。窗口条件不成立时的测量可以反映运行成本，却不能直接作为该条件下活性保证的反例。

**关键行为分散在多个位置。** 客户端收到成功只观察到一条服务路径。决定传播、恢复排队和迟到票处理可能尚未完成，真实 Node 的队列、计时器和传输会影响它们是否发生。测试需要选择能观察相应要求的位置，而不只是增加请求数量。

**共享运行机制承载多条协议路径。** 同一个取消、重试或资源清理机制可能同时服务正常流程与恢复流程。一个修复的影响需要沿这些使用关系分析；原缺陷消失不表示其他路径仍然保留。

**实现自由与协议边界需要同时保留。** 协议明确规定的条件、消息义务和分支必须实现；锁、队列和数据结构等未规定机制可以自主选择。没有必要把所有工程选择提前写成唯一答案，也不能把明确的协议偏离当作实现偏好。

## 6. 已有案例怎样支撑论文

### 6.1 PreAccept 取消：适合作为贯穿案例

v001 为解决失败目标队列饥饿，引入了保留队列和取消机制，却把 Collect 完成与初始任务结束混为一谈；v003 仍保留该行为。七副本场景中，大门槛 L=4，快路径门槛 F=6，剩余首次发送被取消后无法产生所需快票。请求最终仍能通过慢路径完成，因此原缺陷检查和普通成功断言可能通过。

已有定向对照中，W=500ms，后三个 PreAccept 延迟 80ms；v000 约 83ms 完成，v003 约 522ms，让 v003 的排队 PreAccept 继续完成后约 88ms。最后一项是传输诊断对照，不是已交付的修正版。它把实现机制、实际执行和性能后果连接起来；见 [定向测试](../experiments/three-way-evaluation-20261110T004523Z/work/templates/fastcancel_test.go)、[原始观察](../experiments/three-way-evaluation-20261110T004523Z/work/supplemental/v003-fast-cancel-observations.json)及[候选源码](../experiments/three-way-evaluation-20261110T004523Z/work/sources/v003/protocol.go)。

这个案例支持“协议符合性需要单独检查”，也说明独立会话仍可能共同接受错误的生命周期解释。它应当用于提出问题、解释方法和分析失败。新方法能否更早发现或阻止此类回归，需要后续实验，不能把已经用于修改提示的案例当作未见场景成绩。

### 6.2 其他案例承担不同论证作用

| 案例 | 可支持的观察 | 需要避免混淆的结论 |
| --- | --- | --- |
| baseline 缺少决定重传 | 正常服务可运行，但遗漏后台协议工作；真实 HTTP 场景和源码共同支持缺陷 | 不能由一个缺陷推断 baseline 整体不可用 |
| 恢复与传播调度饥饿 | 持续新工作会影响旧工作，审计和修复解决了具体进度问题 | 有限等待本身不证明无限饥饿，需结合调度机制解释 |
| 发送完成通知丢失 | 实际运行时完成事件可能丢失，即使协议核心转换本身没有直接错误 | 4097 配置的定向测试不是 4097 进程部署 |
| Unicode 校验 | 外部输入到内部命令的转换可能改变语义，系统边界也有真实缺陷 | 这是服务输入问题，不算副本决定分歧 |
| 小队列故障配置延迟 | 已修复机制仍可能有很差的运行成本或不稳定测试预算 | 不能把所有超时都计作新的永久停滞 |

## 7. 拟检验的主张与实验

| 主张 | 当前依据 | 下一项有区分力的检查 |
| --- | --- | --- |
| 生成指导改善首次交付 | 本次 v000 健康路径性能优于 baseline，但来自单次生成比较 | 相同材料、模型和工具条件下重复生成，独立评估协议行为、正确性与性能 |
| 实际运行路径调查能发现自主测试遗漏的问题 | 已复现多个队列、恢复和传播问题 | 对同一批候选比较继续自主检查与独立审计的真实发现、遗漏及成本 |
| 可执行证据改善修复 | 当前流程能够传递和复用原始反例 | 对同一候选和同一发现，比较文字反馈与附带复现材料，其他条件保持可比 |
| 独立复核及历史证据减少错误关闭与回归 | 已有跨版本复用机制，同时本次漏掉 PreAccept 回归 | 分别考察复核和历史案例复用，记录有效修复、错误关闭、回归及检查开销 |

baseline 应得到与 Forge 相同的协议和系统目标、相同工具能力，自主实现与自测；方法指导与后续协作是比较变量。还需要与普通的生成—审阅—修复循环比较，分清可执行证据和复核组织的作用。对每个待检验机制单独控制变量，不把一次同时改变多个部分的对照解释为其中某一部分的效果。

记录实际模型投入、墙钟时间和 token 消耗，并在可比资源条件下重复运行；没有自动用满预算不等于投入相同。不同协议版本的结果分别分析。用于发展提示和工具的案例与后续评价场景分开记录，新协议澄清同步给 baseline，历史实验材料保持原样。

主要指标是人工确认的不同根因、证据是否支持发现、有效修复、修复回归、未见场景表现、性能和成本。测试数、报告数和代码行数用于描述规模，不能替代方法效果。论文中的“发现成立”与“测试能支撑该发现”也应分别分析。

## 8. 论文组织与下一步

建议顺序：引言用真实案例提出研究问题；动机部分归纳实现转换、合法反例和修复影响三类困难；方法部分定义上述对象、关系与操作；实现部分说明 Forge 如何落实方法；实验逐项检验主张；讨论部分解释输入设计的责任、模型判断的失效和适用范围。

可能的贡献表述包括：对生成共识实现及修复偏差的实证分析；连接协议要求、真实执行证据与迭代修改的方法；实现工具和可复现的案例评价。具体措辞由后续实验支持程度决定，不将 agent 编排本身作为唯一贡献。

下一步优先把一个完整案例写成“要求如何落实、反例怎样形成、证据怎样支持修改、复核检查什么”的方法实例，再用共同候选做小规模机制对照。结果若不支持预期收益，应修改主张或方法，保留失败原因。暂不为形式化表述增加独立语言、自动性质裁定器或复杂流程。

## 9. 讨论记录

### 2026-11-10：从提示词工程提炼方法

用户提出 SYSSPEC 的优点在于清晰、形式化，并把看似简单的工程组织成方法论。当前采用的方向是先明确研究对象、语义关系、阶段操作与可检验主张，再将提示词和 Python 解释为实现载体。上述对象和记号是研究表述草案，不是新增运行要求。

同日已核对上一轮中英文提示同步：`protocol.md` 明确 Collect 完成不单独终止未完成 PreAccept；`AUDIT.md` 区分协议符合性、正确性和性能；`REPAIR.md` 与 `VERIFY.md` 要求按修改影响检查条件、消息义务及后续路径。baseline 的共同协议已同步。协议澄清和方法提示的收益需由新实验判断。

### 2026-11-10：用轻量文档结构帮助推理与交接

已在中英文角色提示中落实少量信息类别：`DESIGN.md` 组织系统结构、关键实现选择与检查缺口，关键选择串联要求、机制、符合性解释和证据；审计报告组织范围、发现、未完成或已排除的调查，每项发现分清要求、场景、观察、原因与复现。修复沿用现有 summary/reason，复核沿问题 ID 对照原要求、前后观察与相关影响。

标题可以合并或调整，相关内容通过引用复用，不要求填空式逐函数说明，也没有新增控制器格式校验或交付文件。共同协议与 baseline 提示保持原样。待检验的作用是让作者更容易发现自己的推理缺口，并让接收者更容易定位依据、复用证据和核查改动；文档整齐本身不计作方法有效的证据。
