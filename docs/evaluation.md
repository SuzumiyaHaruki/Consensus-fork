# 实验评价方法

本文件供研究者评价 Forge，不作为候选 agent 的额外规格。协议符合性与正确性依据每次实验保存的 protocol.md、system.md 和任务要求判断；历史候选按当时材料分析。方法组织与研究主张见 [paper.md](paper/paper.md)，运行和证据字段见 [workflow.md](workflow.md)。

## 1. 比较什么

| 对象 | 回答的问题 |
| --- | --- |
| baseline 自主交付 | 原生 coding agent 在相同设计、系统目标和工具能力下能完成什么，还会遗漏什么 |
| Forge 首次交付 v000 | 生成指导是否改善实现选择、自查及交付质量 |
| 同次 Forge 的修复后版本 | 独立审计、证据交接、修复与复核带来哪些改进、回归和成本 |

主对照采用实际的自主交付策略：baseline 和 Forge 生成侧自行判断何时结束，Forge 继续执行所配置的审计与修复流程。比较交付质量并报告实际时间和 token 成本，不要求 baseline 为凑时间继续工作，也不把完整 Forge 压缩到 baseline 的生成时长。若要进一步分辨某项机制的作用，可以另做相同候选上的反馈方式或审阅组织对照；等预算实验不是主对照成立的前提。

共同设计材料、目标范围、模型和工具能力需要对齐，主动中断、人工整合、材料变更与配置差异单独记录。v000 与同次后续版本属于同一条演化链，不是独立重复生成。多次运行同一实现用于观察测量波动，多次生成用于观察生成结果的差异，二者不能混为一谈。

## 2. 协议符合性与正确性

| 维度 | 判断依据 |
| --- | --- |
| 协议符合性 | 实际发送、收集、选值、恢复和执行是否遵守明确规则；违反消息义务也可以成立，不必等待决定分歧出现 |
| 正确性 | 同实例决定、依赖与 SCC 执行、rid 去重、应用效果和客户端结果是否满足要求；进度主张还需要相应故障、时间和公平性前提 |
| 性能与工程成本 | 在规定负载、资源和观察时间内的吞吐、完整响应延迟、恢复速度与资源消耗；成本增加不自动等于协议错误 |

先确认真实交付路径：独立服务进程、Node、网络传输、客户端及实际执行后回复。受控测试应说明调用了哪些真实处理代码、替换了哪些机制、绕过哪些队列或运行时行为。原生测试、直接 Core 测试和真实 Node 场景承担不同的检查范围。

协议调查围绕具体路径及其交互展开，例如 Collect 的响应集合、初始快票、Prepare 继承、Validate/HELP/NoFast、证据取回后的重新处理及过载时的后台推进。选择由实现与线索决定；大量单一图枚举不能替代这些交互检查。缺失历史不能被当成没有冲突，规定保留的数据也不能为改善性能而擅自删除。

场景按当次协议的 W/s、crash-stop 和公平性条件解释。配置了 W 不代表实际运行始终满足窗口前提；没有本地超标计数也不是全局证明。有限时间没有完成先记录为观察结果，需要结合机制或合法重复调度，才能进一步论证进度缺陷。存活副本补齐数据与崩溃节点重启是不同场景。

断言应依据要求和独立观察，不能调用候选自己的正确性判断来生成答案。无冲突命令不必在各副本按同一总顺序执行；若声明线性一致性，需要客户端调用历史与合法顺序分析，最终 KV 相同不足以支持该结论。

## 3. 性能测量口径

主负载采用固定速率：在发送窗口 T 内按计划发出请求，不等待前一条回复或首次决定。实际发送时间和发送延误分别记录，防止负载器变慢后把实际低负载误写成目标负载。不同请求使用新的 rid，不自动重试或用 ALREADY_EXECUTED 补齐原结果。

每个副本是独立进程，分别配置 CPU affinity 和 GOMAXPROCS；负载器使用独立物理核。三档资源为每副本 1核1线程/Go P=1、2核2线程/Go P=2、2核4线程/Go P=4，SMT 兄弟线程不跨副本分配。原生 worker 参数固定为 4，但各实现的工作池含义仍不同，不能把它当成相同并发上限；资源对照以实际 CPU 和 Go P 为准。

预热、历史预填、正式发送和收尾分别记录。预热与预填按固定数量完成并确认所需副本执行后，再开始测量。发送结束后继续等待原请求，取得最后一个执行结果即可结束，不固定等待满保护时限。

设 M 为计划请求数，t0 为发送开始，t_last 为最后一条执行回复时间：

| 指标 | 单位与含义 |
| --- | --- |
| 实际发送速率 | 条/秒；发送窗口内实际发起数 / T，同时报告计划数、未发出数和发送延误 |
| 发送期吞吐 | 条/秒；窗口内收到的执行结果数 / T |
| 整批吞吐 | 条/秒；M / max(T, t_last − t0)，仅全部计划请求取得执行结果时给出 |
| 整批平均、P99、最大延迟 | 毫秒；每条请求从实际发起 HTTP 调用到读取执行回复，包含排队及发送期后的长尾 |
| 收尾时间 | 秒；max(0, t_last − t0 − T) |
| 实际共识并发 | 个实例；接纳到集群首次决定的观察区间，不是客户端等待数，也不用于控制发送速率 |
| 资源与追赶 | CPU、RSS、分配、通信及每秒剩余工作量；区分新请求服务与旧历史补齐 |

普通负载在发送结束后另有 300 秒保护，冷历史最多观察 300 秒，待处理历史解除限制后最多观察 1,200 秒。这些是有限实验的观察截止，不是协议保证或每条请求原有的短等待策略。若仍缺执行回复、出现明确拒绝或传输错误，保留状态、等待时间和进度，不输出完整批次的平均延迟、P99 或整批吞吐；已完成部分可作为诊断，不能冒充完整分布。吞吐与长尾同时报告，不用一个总平均掩盖两者差异。

每组合重复五次，保留逐次值，汇总中位数、最小值、最大值和完整批次数。每次 P99 的中位数不等于合并所有请求后的 P99。同一场景的三个版本与各 CPU 档位放在同一服务器，四机分担不同场景并运行共同校准项。服务器分工、速率矩阵、时长与命令只维护在桌面测试包 consensus-server-evaluation-1111 的 README.md 和 scripts/plan.py，不在本文复制第二套参数表。

新固定速率测试已取得 [server A 普通请求](results/server/1116-fixed-rate/server-A.md)、[server B 热点与载荷](results/server/1116-fixed-rate/server-B.md)的阶段结果，以及 [server C 延迟与崩溃](results/server/1116-fixed-rate/server-C.md)、[server D 旧请求开销与补齐](results/server/1116-fixed-rate/server-D.md)的完整运行结果；未完成或未形成的场景与样本范围分别列在报告中。[1115 服务器报告](results/server/1115-closed-loop/README.md)仍使用旧闭环负载和短等待口径，不能与新方法混合汇总，也不能从旧成功子集恢复完整延迟。新测量重做性能部分，旧协议反例和正确性证据仍按其原始条件保留。

## 4. 发现、修复与证据

按根因分析发现，不按失败测试数累计。人工审阅同时判断“问题是否真实存在”和“证据是否支持声称的结论”；真实问题可能附带薄弱证据，未完成的合理怀疑也不直接算假阳性。可从报告和执行记录分析 agent 怀疑、排除、确认、收窄或撤回了哪些解释，不补猜未留下记录的思考。

假阴性需要明确的已知缺陷集合，并确认缺陷存在于当时被审计版本且属于其范围。区分从未怀疑、错误排除和未完成调查；未知全部缺陷时，只报告所选样本的遗漏情况，不声称测得总体漏报率。

修复分别回答原问题是否解决、是否引入新缺陷，以及其他行为的收益与代价。使用原反例、修复 diff、正确极性的回归断言和相关独立场景；复现用例的 PASS 可能表示成功触发错误。新审计没再报告、agent 标为 fixed 或原有测试通过，都不能单独证明修复有效。已进入候选的回归测试不再属于未见终测。

执行记录提供版本、命令、覆盖文件和输出的关联；指定源码副本仍可能被测试命令修改，因此实际断言和观察需要审阅。公共调度器不自动裁定 W/s、可达性或共识性质。字段和工具格式由 [workflow.md](workflow.md) 与 [scheduling.md](scheduling.md)说明，本文件不另设报告模板或机械质量评分。

## 5. 成本与结果记录

保留实际模型、墙钟、主/子会话用量、停止原因和人工干预。agents.json 中用量不完整时报告已观察值与缺失原因，不把未知值填零；缓存和推理 token 是对应类别的子集，原 CLI 累计数不与去重汇总相加。并行会话时长也不等于实验墙钟。

研究结论分别写明工程可用性、协议符合性、正确性和性能，附版本、材料、场景、命令及证据。环境错误、预算用尽、材料歧义、测试问题和实现缺陷分开解释。agent 的独立复核属于实验流程，研究者的后续判断另行记录，不用一个 assessment 字段代替。

具体案例入口见[实验报告索引](README.md#实验报告)。11 月 10 日是探索性实现与修复案例，11 月 13 日比较另一批生成结果，11 月 15 日服务器报告评测的是 11 月 11 日实现；报告日期不能代替候选身份。
