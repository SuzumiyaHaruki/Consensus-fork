# 实验评价：混合 EPaxos

本文件供研究者评价实验方法，不是隐藏的实现规格，也不复制到候选工作区。新分支按 `inputs/protocol.md` 与 `inputs/pseudocode.md` 的混合协议判断；旧候选和历史报告仍按当时材料分析，不追溯要求它们支持新协议。

本轮不设统一的逻辑请求总数上限。选择能回答具体问题的有限工作负载，并记录不同 rid 的请求数、重试、实际实例数量和检查点进度。测试停止新增请求后，可以继续处理未完成工作，并报告停止时的状态。每次集群运行使用选定的固定 W，结合实际事件检查前提；删除请求数上限并不证明任意历史规模都满足窗口或资源条件。

## 首批独立检查方向

先确认可运行交付：多进程真实 Node、并发客户端、实际执行后回复、正常自主推进、同 rid 同载荷重试与去重、真实时间和受控执行是否共用代码。检查实际命令、参数和原始输出，而不是仅看测试文件与最终自述。

协议检查要覆盖有意义的路径与交互，不能用大量单一图枚举替代。选择方向时可以关注两阶段 Collect 的实际响应与切点、快票和 Mismatch、Prepare 两阶段快照、最高 accepted 继承、Validate/HELP/NoFast、证据取回后重新处理，以及全槽占用时的后台推进。选哪些场景应由实现与调查线索决定，不把这些方向变成自动门禁或预先写好的通过答案。

故障与时间使用新模型：累计 crash-stop、广播可能部分发送、W 从广播开始计时、窗口内允许至多 s 个仍存活成员尚未回复，慢成员身份可以变化。Omega 是最终恢复者而不是准确死亡集合。区分外部调度不符合模型与实现未履行其声明的行为；也区分实际收到响应、队列中的事件和处理完成。有限等待未完成不自动证明无限不活跃。

分别检查同一实例的完整决定值、依赖执行顺序、每实例执行完成、同逻辑请求的应用效果与返回结果。无冲突命令不需要在各副本采用完全相同的总顺序。断言应依据要求与独立观察，不调用候选自己的“是否正确”逻辑代替判断。声明客户端历史线性一致性时，需要相应历史与合法顺序分析，不能只比较最后的 KV 状态。

当前 epoch 内，执行后仍保留规定的冲突可见性和证据，合法检查点安装后才能按规则替换旧历史。增长测量记录历史规模、依赖/证据字节、窗口实际耗时、执行/排队时间、检查点成本与资源用量，并区分可回收证据和继续增长的应用状态、结果等数据。K 不是历史容量上限。性能成本与已证实的协议违反分别报告，不能擅自套用旧本地剪枝方案或未规定的复杂度目标。

baseline 与主流程使用相同的三份设计材料（protocol、pseudocode、system）和工具能力，默认生成阶段都由 agent 判断交付时机，无固定截止时间。主流程额外提供工程推理指导、独立审计、证据交接、修复与复核。比较首次交付与后续版本，记录实际模型、墙钟与 token 投入；不能把协议变更、额外投入或更强模型带来的差异直接归因于流程。使用显式限时覆盖时需单独注明。

## 每次评估记录

研究者可在实验外记录工程可用性、设计忠实性、安全性、推进与执行的实际结论，附测试命令、场景、原始轨迹、预期依据与观察结果。本文件仅提供分析方向，不规定记录文件名，也不把人工研究流程嵌入实验。实验输出不再设置 `assessment` 字段；流程状态、逐项复核结论和原始证据已经分别表达运行中实际发生的事情。

多个失败测试可能来自同一个根因，应按根因分析而非简单累计失败数量。编译失败、预算耗尽、环境失败、文档歧义和协议实现缺陷分别记录。有限测试通过不等同于形式化正确性证明。

可以把审计的调查过程本身作为分析对象：agent 怀疑了什么，依据哪条要求，做过哪些检查，排除了什么解释，最终确认、收窄、撤回或留下了哪些问题。优先从报告、逐回合改动和执行日志重建这一过程，不再要求 agent 填一套独立表格。未写入记录的思考无法补猜；报告中的“确认”或“排除”仍是 agent 的判断。

人工审阅分别检查两件事：问题在规定范围内是否真实存在，以及提供的测试、断言和解释是否足以支持这个结论。真实缺陷也可能附带薄弱证据；合理怀疑因预算不足而未确认，也不应直接算假阳性。还可以分析错误发生在要求理解、入口可达性、观察与断言对应、结果解释还是修复后的回归检查，并区分生成、审计和复核各自的判断。

假阳性应以人工裁定的正式缺陷报告为依据。假阴性需要一个明确的已知缺陷集合，例如后来独立复现并确认的缺陷，并核对它是否已经存在于被审计版本、是否属于当时范围；再区分从未怀疑、错误排除和未完成调查。没有报告问题不能证明没有漏报，也不能在未知全部缺陷时宣称测得总体假阴性率。可以据明确的样本集合报告遗漏比例，并保留无法裁定的项。

新 `forge.py` 流程明确包含审计反馈和修复，并分别保留反馈前后的候选、实际预算与全部证据。独立审计与复核使用新会话，但候选中可能已经含有根据反馈新增的回归测试，不能把这部分测试算作未见过的终测。

修复效果需要结合旧反例、修复 diff 与正确极性的回归断言分别判定。CA 复现用例可能在观察到错误时返回 PASS；再审计没有重复提到某一问题也不证明它已经消失。独立复核保存前后版本、逐项结论和执行证据。它是实验中的 agent 复核，不能把问题项关闭直接解释为整个系统通过了独立评测。

## 本轮新增证据的评估方式

新增提示将合法性、入口可达性、因果解释和相关场景分别记录，便于区分“看起来像错误”与“在支持范围内实际到达的错误”。检查这些字段是否指向真实命令、输出和事件，不按字段数量或文字长度评分。可以分别统计人工确认的不同根因数、可复现比例、公开入口复现比例、修复后原问题是否消失，以及独立相关场景中是否出现同因错误或回归。没有实测可达路径的问题可以保留，但应与公开入口已复现的问题分别报告；极端配置缺陷也应保留其实际影响范围。

当前已取消固定质量说明字段的催填，相关解释可放在报告或自选字段中。`execution_records` 提供来自执行服务的命令、结果和起始源码关联；`candidate_copy` 仍不能证明命令没有改源码、没有弱化断言或没有执行无关程序。复核应检查原始命令、补充文件和实际输出，普通工作区执行则检查源码关联依据。具体反馈只是指出这些可观察缺口，不作为自动质量评分或真假判决。

调度工具只执行计划并保留实际适配器交互，新流程没有自动 W/s 或共识性质检查器。研究分析须检查输入模型、真实路径、观察完整性与断言含义。旧轨迹检查工具和历史结果属于旧模型，不能作为新协议合法性或正确性的证据。

为判断生成—审计协作是否有效，应固定协议、系统范围、模型与可比资源预算，分别记录首次交付、修复后交付和独立复核的质量与成本。不要把增加总时间、模型变化、更多人工协议信息或重复已知回归用例的收益全部归因于协作。三份设计材料应同等提供给 baseline，方法指导与交付目标分开；新旧协议的缺陷数量不直接构成提升结论。

原生子智能体允许按需使用，这改变了实验执行条件。现在每阶段的 `agents.json` 和 `agent-records/` 保留实际主/子会话模型、回合时间和逐响应去重用量，并排除 fork 继承记录、核对线程累计数。`usage_complete` 为 false 的阶段只能报告已观察用量及缺失原因，不能将缺失用量视为零；原始 CLI 的累计快照不能与新汇总相加。这里不估算账单费用，并行回合耗时也不能当作墙钟累计。相同墙钟预算仍不等于相同计算投入；历史缺失记录不会因新采集器而自动补齐。
