# 独立评估准备

此文件给研究者使用，不复制进候选 workspace。当前已接入 CA 的生成后审计、独立修复复核和新问题再审计，但没有实现独立的协议正确性评测器；Python 控制器的离线测试不构成共识测试，也不证明生成能力。独立目录在 host 模式下并不构成不可读取边界，正式隐藏评估需要单独的执行环境。

第一份候选产出后，读取其公开 API 并添加薄适配器。适配器可以编码消息、转接时间和发送完成事件、收集结果，不能替候选实现补齐观察、恢复、调度、执行或去重规则。缺失必需能力应记为不可测或工程缺口；如果修改候选实现，保存为明确的后续产物。

## 第一批人工检查场景

| 场景 | 依据 | 观察 |
| --- | --- | --- |
| 无冲突且覆盖提前完整 | PDF §2.2 | 完整发送后满足条件即 Fast 决定，不增加封存轮次 |
| 覆盖未完整，但已知依赖支持较高 | PDF §2.2 | 不因现有依赖支持高而提前 Fast |
| 已知 Fast 无望，但尚有存活成员未回复 | 当前 protocol.md §4；修订 PDF §2.3 | 继续收集，纳入该成员的新依赖；覆盖完成后才选 Seal |
| 本地完成后形成新观察，随后回复旧查询 | 当前 protocol.md §§3、12.1 | 新观察省略本地已执行命令；旧观察和恢复快照保留原内容 |
| Fast 决定后尚未通知即崩溃 | PDF §4.1 | 后继重建相同最终元组 |
| SEAL 部分发送后协调者崩溃 | PDF §§3.4–3.5、§4.2 | 资格后新正式读取，按合法状态继承 |
| 回复恰好按截止界到达 | PDF §1 | 先处理按时消息，不错误证死存活节点 |
| 已收集回复者后来证死 | PDF §§2.1、3.4 | 保留已有观察或快照 |
| 旧 request_id 或重复发送者携带 COMMITTED | PDF §§3.4–3.5 | 合法最终决定仍立即处理，普通快照不能混入新读取 |
| 同节点多命令订阅同一目标 | PDF §3.2 | 共享探测；一命令结束不取消其他订阅 |
| 主动恢复节点学习最终决定 | PDF §3.6 | 原子建立必要转发，终态清理不取消剩余发送 |
| 有环或尚不完整的依赖闭包 | PDF §5、当前 protocol.md §12 | 等待完整已决定闭包；局部完成和退出索引不改变 SCC 内原定顺序 |

故障注入必须遵守来源模型：最多 f 个累计 crash-stop，已完成发送给持续存活接收者的消息按界交付，广播可以部分完成，deadline 与消息处理顺序符合文档。任意永久丢包、重启或超过上界的网络延迟应单列为模型外探索。活性失败需给出满足前提的有限执行及适用时间界；不能以无限冲突工作负载的未证明性质判错。

2026-11-03 的完整收集与本地剪枝是对原 PDF 的配套修订，论证见 [本地剪枝说明](local-pruning-safety.md)。旧实验允许提前 Seal，应按旧输入判断；不能把旧候选提前进入 Seal 直接记为当时的实现错误。

当前客户端模型允许多个客户端并发操作，每个逻辑命令只提交一次。客户端重试、跨节点找回结果和旧请求恢复不属于当前交付要求；测试不能用反复重提同一命令代替当前支持的客户端流量，也不能靠再次提交来帮副本启动恢复。传输重复投递和副本通过观察、查询、决定转发反复获知同一命令仍在范围内，每个副本只能执行一次。历史实验继续按其保存的输入判定。

分别观察客户端回复、存活副本的决定和实际执行。如果完整命令从未到达任何永久存活副本，就没有最终决定保证；完整命令已到达永久存活副本后，应在协议前提下自主推进决定，执行还需依赖准备好。发送方崩溃不取消已经完成发送的交付义务，不能只看崩溃当时接收者是否已经处理消息。接入节点回复前崩溃时，即使其他副本已经执行，客户端也可能拿不到结果，这本身不是共识活性缺陷。无故障且客户端仍连接等待的正常路径，仍须执行后返回结果。客户端超时只代表结果未知，不能当作命令未执行的证据。

断言应检查允许行为集合与最终语义，不要求候选复制某套内部结构或唯一消息顺序。无需让无冲突命令在不同副本具有完全相同的全序。不直接调用候选的决策函数来计算“正确答案”。

## 每次评估记录

研究者可在实验外记录工程可用性、设计忠实性、安全性、推进与执行的实际结论，附测试命令、场景、原始轨迹、预期依据与观察结果。本文件仅提供分析方向，不规定记录文件名，也不把人工研究流程嵌入实验。实验输出不再设置 `assessment` 字段；流程状态、逐项复核结论和原始证据已经分别表达运行中实际发生的事情。

多个失败测试可能来自同一个根因，应按根因分析而非简单累计失败数量。编译失败、预算耗尽、环境失败、文档歧义和协议实现缺陷分别记录。有限测试通过不等同于形式化正确性证明。

可以把审计的调查过程本身作为分析对象：agent 怀疑了什么，依据哪条要求，做过哪些检查，排除了什么解释，最终确认、收窄、撤回或留下了哪些问题。优先从报告、逐回合改动和执行日志重建这一过程，不再要求 agent 填一套独立表格。未写入记录的思考无法补猜；报告中的“确认”或“排除”仍是 agent 的判断。

人工审阅分别检查两件事：问题在规定范围内是否真实存在，以及提供的测试、断言和解释是否足以支持这个结论。真实缺陷也可能附带薄弱证据；合理怀疑因预算不足而未确认，也不应直接算假阳性。还可以分析错误发生在要求理解、入口可达性、观察与断言对应、结果解释还是修复后的回归检查，并区分生成、审计和复核各自的判断。

假阳性应以人工裁定的正式缺陷报告为依据。假阴性需要一个明确的已知缺陷集合，例如后来独立复现并确认的缺陷，并核对它是否已经存在于被审计版本、是否属于当时范围；再区分从未怀疑、错误排除和未完成调查。没有报告问题不能证明没有漏报，也不能在未知全部缺陷时宣称测得总体假阴性率。可以据明确的样本集合报告遗漏比例，并保留无法裁定的项。

新 `forge.py` 流程明确包含审计反馈和修复，并分别保留反馈前后的候选、实际预算与全部证据。最后一次审计使用新会话，但候选中可能已经含有根据反馈新增的回归测试，不能把这部分测试算作未见过的终测。

首轮系统实验应先人工核查交付物能否以多个进程启动、并发客户端是否正确分配身份并且每条命令只提交一次、是否执行完成后才回复成功，以及真实时间和可控时间是否使用同一协议代码。还应检查客户端结束等待后，副本是否继续承担已有的恢复和执行义务。这些是评估方向，不是预先交给 agent 的测试答案。检查实际调用的测试、参数和原始输出，避免把仅有测试文件或最终自述当作测试已经执行。

修复效果需要结合旧反例、修复 diff 与正确极性的回归断言分别判定。CA 复现用例可能在观察到错误时返回 PASS；再审计没有重复提到某一问题也不证明它已经消失。独立复核保存前后版本、逐项结论和执行证据。它是实验中的 agent 复核，不能把问题项关闭直接解释为整个系统通过了独立评测。

## 本轮新增证据的评估方式

新增提示将合法性、入口可达性、因果解释和相关场景分别记录，便于区分“看起来像错误”与“在支持范围内实际到达的错误”。检查这些字段是否指向真实命令、输出和事件，不按字段数量或文字长度评分。可以分别统计人工确认的不同根因数、可复现比例、公开入口复现比例、修复后原问题是否消失，以及独立相关场景中是否出现同因错误或回归。没有实测可达路径的问题可以保留，但应与公开入口已复现的问题分别报告；极端配置缺陷也应保留其实际影响范围。

当前已取消固定质量说明字段的催填，相关解释可放在报告或自选字段中。`execution_records` 提供来自执行服务的命令、结果和起始源码关联；`candidate_copy` 仍不能证明命令没有改源码、没有弱化断言或没有执行无关程序。复核应检查原始命令、补充文件和实际输出，普通工作区执行则检查源码关联依据。具体反馈只是指出这些可观察缺口，不作为自动质量评分或真假判决。

轨迹工具仅检测提供的有限记录是否满足若干传输和 crash-stop 条件。`consistent_prefix` 不能代替逐项检查输入模型、适配器、完成事件含义及记录完整性；`violations` 也不能直接等同于模型外场景，因为代码自身可能违背其承诺的传输义务。未使用工具或没有轨迹只表示未提供这类证据。研究分析应据此判断证据支持到什么范围，实验中不另行输出研究者裁定。

为判断生成—审计协作本身是否有效，应固定协议、系统范围、模型与可比资源预算，分别记录初始交付、修复后交付和独立复核的质量及成本。不要把增加总时间、采用更强模型、给出更多人工提示，或重复运行已知回归用例的收益全部归因于协作机制。本次新增提示和轨迹工具属于输入与工具条件变化，不能直接把新旧实验的缺陷数量当作能力提升结论。

原生子智能体允许按需使用，这改变了实验执行条件。现在每阶段的 `agents.json` 和 `agent-records/` 保留实际主/子会话模型、回合时间和逐响应去重用量，并排除 fork 继承记录、核对线程累计数。`usage_complete` 为 false 的阶段只能报告已观察用量及缺失原因，不能将缺失用量视为零；原始 CLI 的累计快照不能与新汇总相加。这里不估算账单费用，并行回合耗时也不能当作墙钟累计。相同墙钟预算仍不等于相同计算投入；历史缺失记录不会因新采集器而自动补齐。
