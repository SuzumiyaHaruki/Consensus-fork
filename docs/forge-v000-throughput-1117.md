# 11 月 17 日 Forge v000：审计期间的吞吐短测

**在本次两 CPU 限制下，v000 比 baseline 更早过载，而且过载后完成速率明显下降。低负载时 v000 的执行延迟较低，但还不能据此判断其整机峰值吞吐。**本轮完成 24 项检查，测试进程均已退出；原 Forge 实验仍在独立审计。

## 1. 对象与资源条件

对象为 `20261117T100702Z-sol-high-forge-1117-01-to7zh4r8/candidates/v000`，提交 `37dde6616d279582fcb9dc8833228b3d3bb31a93`。生成正常结束，耗时约 66 分钟。通过 Git 导出到桌面独立目录构建，20 个 Go 文件与原候选逐一比对一致；原候选 Git 工作区保持干净。测试结果没有交给实验中的审计或修复 agent。

为给运行中的审计保留资源，七个独立副本进程和负载器共同绑定虚拟 CPU 6、7，nice=19，测试组内存上限 2 GiB、禁止使用 swap。每个副本各自 GOMAXPROCS=1，并非把七个 Node 放进同一个 Go runtime。测试组最多使用两个 CPU，其余六个 CPU 不被测试进程使用；采样期间系统可用内存始终超过 8 GiB，未发生 OOM。首次试跑使用四 CPU，后来发现用户级 CPUQuota 未实际生效，因此这项单列，不混入两 CPU 对比。

baseline 重新在完全相同的 CPU、内存和优先级条件下运行，使用之前的原始交付二进制。双方 n=7、f=4、s=1、e=1、W=200 ms、worker=4，队列与接纳阈值配置为 4,096；阈值的具体统计范围沿用各自实现。baseline 使用已有对照中的 Tick=5 ms，v000 使用自身事件推进机制。**这里不能直接套用之前七副本各独占一个 CPU 时的数千条/秒结果。**

负载复用 baseline 的 Go 发生器：每条请求写不同的新键，value 为 16 字节，无 Get、冲突、故障注入、共识 batch 或客户端重试。主表随机入口，固定速率发送 12 秒，每个请求从自身发出起最多等待 15 秒；服务端等待上限 20 秒，最后另观察副本最多 8 秒。吞吐为发送窗口内的 OK 执行回复数/窗口时长；回复比例包含发送结束后的回复。延迟只在实际发送的请求全部取得 OK 时报告。

## 2. 随机入口结果

200、500 条/秒各重复两次，其余主表项一次。回复比例按实际发出的请求合计。

| 输入（条/秒） | baseline 吞吐（条/秒） | baseline 执行回复比例 | v000 吞吐（条/秒） | v000 执行回复比例 |
|---|---:|---:|---:|---:|
| 50 | 50.0 | 100% | 50.0 | 100% |
| 100 | 100.0 | 100% | 45.8 | 47.08% |
| 200 | 199.8 | 100% | 21.2～25.6 | 13.23% |
| 500 | 464.6～478.2 | 95.38% | 23.0～23.8 | 4.99% |

50 条/秒时，baseline 平均延迟 6.81 ms，v000 为 4.35 ms。v000 又完成了 **50 条/秒持续 30 秒的全部 1,500 条请求，平均 3.97 ms；75 条/秒持续 20 秒的全部 1,500 条请求，平均 4.38 ms**，两项结束时所有副本均无未执行实例。这些是已观察到的可完成负载，不代表已经精确测出容量分界。

v000 的更高负载项主要是客户端 15 秒等待超时；原始负载器将它们记作 TRANSPORT_ERROR，具体错误均为等待 HTTP 回复头超时，不能解释成连接断开。200 条/秒两次共发出 4,800 条，只收到 635 条 OK。停止发压并继续观察后，各副本仍有大量未执行实例。baseline 在 500 条/秒下主要主动拒绝新请求，两次共拒绝 555 条；已接纳工作最终排空。

另有 1,000 条/秒检查，v000 触及负载器 8,192 个待回复请求保护，计划负载未完整发出，未纳入主表。

## 3. 入口分布和时间配置补测

同为两 CPU、100 条/秒、12 秒，v000 的单点入口和轮转均衡入口均完成全部 1,200 条请求，平均延迟分别为 **9.79 ms、9.43 ms**；随机入口那次只完成 565 条。说明接近饱和时对入口分布和实际调度敏感，不能把一次随机入口退化简单定为“最大只能处理 75 条/秒”。入口补测各一次。

把 v000 的 W 改为 1 秒后，输入 200 条/秒时吞吐为 74.0 条/秒，最终回复 1,064/2,400；输入 500 条/秒时为 55.8 条/秒，回复 761/6,000。其默认 Retry、Recovery、Overdue 和 Heartbeat 随 W 一起变化，因此这是时间参数组合对照，不是只改变一个截止时间。前一项同时采集了副本 0 的 CPU profile，数值包含剖析开销。放宽这些参数有所改善，但仍未消除积压。

最初四 CPU 试跑中，v000 在 200 条/秒下全部完成 2,400 条，平均延迟 2.27 ms，发送期副本合计约使用 2.43 个 CPU。它说明资源条件确实重要；本轮没有在审计期间继续用四或八 CPU 扫描峰值。

## 4. 已定位的成本

- **执行推进有改善。**v000 每次处理事件后推进 dirty 键，不受 baseline 每 Tick 最多调度 64 个键的限制；低负载的平均延迟较低。
- **协议传输更重。**v000 每个 peer 的 sender 顺序调用 HTTP POST，等本次 HTTP 响应后再发下一条；baseline 是持久 TLS/TCP 帧发送。v000 又为完整数据和决定逐 peer 维护确认，正常工作也包含大量后台传播。
- **过载会增加额外工作。**随机 200 条/秒第一项，两核接近用满，停止发压后重传与恢复仍持续。到观察结束累计 SendBusy 增加约 876 万次、WindowMiss 约 604 万次；这些是重复事件计数，不是独立请求数。该项 PendingData、DataGated、Fetches 均为零，问题没有表现为缺失依赖数据。
- **剖析支持通信与扫描成本。**W=1 秒、200 条/秒的副本 0 profile 中，HTTP 服务端处理累计约 29.8%、sender 累计约 14.4%、worker.tick 累计约 17.8%，系统调用自身约 21.2%；调用关系存在重叠，不能相加。tick 会扫描活跃记录，积压扩大时这部分工作也增加。

本轮显示的是资源受限时的承载和过载恢复表现，没有据此判定一致性错误或永久活性失败。较低负载的延迟改善，与较高负载的吞吐退化可以同时存在；生成阶段更仔细，并没有自动得到更高效的整体实现。
