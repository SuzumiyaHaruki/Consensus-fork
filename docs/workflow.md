# 工作流与证据边界

`workflow.py` 连接 `generator/` 和本地 `auditor/`。生成、修复与审计模型均为 `gpt-6.1-sol / high`。协议和系统范围保持在输入文档中；Python 负责版本、预算、文件和结果关联，不补充协议语义。测试仍只要求在 `tests/`，具体方案由 agent 选择。

## 阶段与执行能力

首次生成后导出候选 v000，启动新问题审计。若存在待处理问题且预算允许，启动新修复会话，导出下一候选，再启动独立的修复复核。复核只收到明确的旧问题、完整原始证据、修复声明及前后代码；审计提示为 `inputs/VERIFY.md`。复核结束后重新开启新问题审计，不向其提供旧报告或修复声明。两者都使用审计侧权限和执行环境，复核完成首个完整回复后结束，新问题审计在阶段预算内调查并安排收尾。

生成和修复通过 `generator/execution.py` 接入 `runtime/local_exec.py` 的真实 STDIO MCP 服务。`forge_local.isolated_exec` 使用白名单文件系统、离线 Go、私有网络与 PID/IPC 空间；输入与执行记录不能被测试程序改写。所有通信进程要在一次调用中启动，返回或超时后清理子进程。启动模型前执行私有 TCP 探测；失败记为环境问题，不回退到主机执行。生成/修复整体墙钟包含工具执行时间，审计仍保留原 CA 的回合计时方式。

普通生成 shell 保留原来的 host/workspace-write 模式与用户配置继承，没有主机文件读取隔离。MCP 中的隔离并不让整个生成 agent 变成隐藏评测环境。审计侧私有认证、只读源码与日志、凭据筛选、执行隔离及清理措施保留。

各阶段允许 Codex 原生子智能体按需分工，提示要求沿用当前模型、推理强度、权限和阶段预算，由主智能体协调共享文件、汇总证据并在回复前结束委派工作。生成与审计均启用本机 CLI 的 `multi_agent` 功能；不允许嵌套 Codex CLI 或外部模型服务。阶段内部分工不替代生成后的独立审计与修复复核，也不扩大外部发布、远程部署、第三方通信或凭据修改的权限。本地集群启动、客户端和协议通信、范围内故障注入及自有测试资源清理属于任务范围。

隔离工具在运行目录使用普通进程锁，协调多个子智能体可能创建的独立 MCP 服务，避免同时改写可变工作区和执行时钟；进程退出会释放锁。排队占用总预算，取得执行权后仍受单次动作时限和总截止时间约束。分析与其他独立工作可以并行；调用者仍需协调普通 shell 和文件编辑，因为执行锁只覆盖隔离工具调用。工具描述统一说明网络、生命周期、源码副本和日志选项，阶段提示只保留入口及该阶段特有的版本含义。

隔离工具内运行真实进程、套接字和计时器，所有通信进程在一次调用中启动并在返回后清理。这个生命周期是实验设施约束，不是服务器 API 要求；交付的服务和客户端必须能通过普通命令独立运行。当前检查仍以单机私有网络为主，不据此宣称验证了跨机器部署或长期持续服务。

## 版本与问题交接

四类提示分别落实不同责任：`TASK.md` 要求按性质依据、状态归属和完整运行路径推进生成；`AUDIT.md` 要求记录调查范围，并建立“要求 → 合法触发 → 可达入口 → 实际观察 → 因果解释”的证据链；`REPAIR.md` 要求先重放、解释根因、修复共享原因，再检查原场景和相关变体；`VERIFY.md` 独立检查前后版本及行为是否被削弱。它们不规定 Go 文件布局或固定测试集合，不要求为了多跑一轮而耗尽预算。

候选仍使用独立干净 Git 仓库的 commit 关联，不新增候选哈希。`artifacts.py` 从源码捕获和逐回合增量重建最后一个完成回合；原始未完成回合继续留存。报告和索引均取自该完成状态，不从超时后仍被改写的工作区取值。

审计维护 `report.md` 与 `findings.json`。后者是普通 JSON 导航：候选 commit、调查范围和限制、局部问题 ID、预期性质、合法前提、复现命令、断言极性和证据路径。控制器为 ID 加审计轮次前缀，例如 `a000-F1`，保存到实验根目录 `issues.json`。描述性字段允许非空文本、列表或对象，并按原结构保留；修复和复核中的说明、理由及观察也遵循这一规则，额外说明字段不会导致拒收。版本、ID、动作和状态仍必须使用对应字符串，证据仍是安全的相对文件路径列表。这是报告项标识，不是独立根因计数；不同审计可能重复发现同一根因，当前不按自然语言自动合并。

`handoffs/` 保留每次审计的完整证据；`feedback/` 为下一轮修复组合当前及历史未解决问题，并附独立复核证据。原始问题的来源 commit 不随候选升级而改写。修复结果必须对应输入 commit，逐项覆盖所给 ID；它只是声明，不关闭问题。候选导出排除反馈目录，保留新增的正式回归测试。

`reviews/` 中的复核有只读上下文、原始运行与完成回合交接包。`review.json` 关联 before/after commit，逐项记录处理结论、前后观察、执行或静态审阅方法以及保留证据。`fixed` 需要独立执行；只有静态推测或环境阻塞时保持未解决；`blocked` 不能搭配任何关闭问题的结论，包括 `not_substantiated`。缺陷 witness 的 PASS 可能表示触发了错误，复核按实际支持的性质判断；例如在输入要求允许的边界上显式拒绝过大响应可以是有效修复，但不能用新写的限制撤销既有成功语义。修复和复核都要检查 diff 影响的原有行为，特别是原先成功的路径是否变为拒绝、长期等待或重复执行；既有测试全部通过不能代替这些检查。

复核发现与原问题相关的回归时，应把原问题保持为未解决；另一个有充分依据的缺陷可以写入 `review.json.new_issues`，沿用发现阶段的问题和证据格式。控制器先完整校验复核结果，再更新旧问题并导入新问题，按修复后候选版本赋予 `r001-F1` 这类 ID。即使随后新审计没有发现问题，这些条目仍会进入下一轮修复；复核不承担额外的全系统发现任务。规格确有缺口时保留 `needs_specification`，不能把修复造成的退化重新解释为规格缺口。

质量说明可以写在报告或额外字段中，不要求固定标题集合。`legality`、`reachability`、`causal_explanation`、`variants` 等旧字段继续保留和传递，但缺失本身不产生催填提示。现有版本、ID、状态、最小报告结构和安全路径校验仍保留。修复说明按原结构进入复核的 `request.json.repair_claim`，修复阶段的隔离执行记录另复制到上下文 `repair-executions/`；原日志中的绝对路径仍是原运行路径。

修复交接新增 `overview.md`，路径记录在 `handoff.json.overview_file`。控制器从索引直接复制说明值、版本、断言极性、证据路径及复核历史，没有用模型二次概括。跨版本未解决问题及其复核材料复制到 `previous/` 时，普通证据和轨迹引用一起改为交接包内的路径；原始来源 commit 与原报告保持原样。API 变化时应保留原 witness，另写薄适配器并解释如何保留触发顺序；编译失败不能被解释为缺陷已修复。

`issues.json` 的 `import_status` 区分尚未审计、正在导入、已导入和导入不完整，`imports` 逐次记录来源版本、索引路径、错误与成功导入的问题数。失败时问题数为 null，不能把空 `issues` 列表解释为没有发现；`forge.py inspect` 同时输出 `issue_index_status`。结果内容或版本不合法时保留原始文件并明确记录不完整。JSON 字段和存在的日志引用不能证明测试推理正确。复核结论的来源与证据已经明确记录，不另设始终不变的 `assessment` 字段；历史实验保留原文件，`inspect` 不再输出旧字段。

## 有限轨迹检查

`runtime/tracecheck.py` 是标准库命令行工具，`python3 runtime/tracecheck.py --help` 给出完整格式与边界。生成/修复阶段得到 `inputs/tracecheck.py` 副本，从 workspace 可执行 `python3 ../inputs/tracecheck.py --help`；审计与复核得到运行目录下只读的 `tools/tracecheck.py`，绝对路径在 run brief 中。审计源码记录与交接包的 `raw/tools/` 保留当时的工具，普通 shell 与隔离执行均可读取；没有扩大对其他框架目录或认证信息的权限。

测试适配器可以把实际观察转换为 JSON 事件记录，不需要候选采用固定事件格式。顶层字段为 `clock`（`controlled` 或 `single_observer`）、`members`、`fault_limit`、`delivery_bound_ns`、`end_ns` 和 `events`。时间都是同一时钟上的非负整数纳秒；不能直接拼接不同机器的墙钟。以下仅演示格式，不代表真实共识执行：

```json
{
  "clock": "controlled",
  "members": ["A", "B", "C"],
  "fault_limit": 1,
  "delivery_bound_ns": 100000000,
  "end_ns": 140000000,
  "events": [
    {"at_ns": 0, "kind": "send", "id": "tx1", "src": "A", "dst": "B"},
    {"at_ns": 50000000, "kind": "send_complete", "id": "tx1"},
    {"at_ns": 130000000, "kind": "deliver", "id": "tx1"}
  ]
}
```

`send` 是实际发起的单次传输，不能用入队事件替代；`id` 是传输尝试 ID，重试要用不同 ID，不能直接用命令 ID。`send_complete` 对应单个接收者。消息可以在完成回调前交付，已完成传输的交付义务不会因发送者崩溃消失，接收者在截止时刻前或恰在该时刻崩溃则解除这项义务。`crash` 用 `node` 表示真实 crash-stop，不能把实现推断的死亡事实直接当作真实崩溃；后者可以记为不解释语义的 `observe`。同一时刻按列表顺序处理。重复交付允许，但工具不检查载荷；未完成的发送不被自动赋予交付期限。

返回状态只有 `consistent_prefix`、`violations`、`invalid_trace`，退出码分别为 0、1、2。在有限前缀结束时刚好到达截止界且尚未收到消息，结果列为 `pending`，因为同一时刻可能还有后续事件；时间推进超过截止界才报告缺失交付。此工具不检查完整广播、计时器优先级、处理耗时、载荷一致性、仲裁集合、状态机语义、安全性或活性，也无法检测被遗漏或编造的事件、错误的完成埋点及不真实的上界。空轨迹也只能说明所提供记录没有矛盾。

审计和复核可以在每个问题里添加 `trace_files`，指向保留的 JSON 轨迹，路径格式沿用 `evidence`。控制器用可信代码重新解析，覆盖输入中自称的 `trace_checks`，保存具体观察和后续问题；没有轨迹本身不产生缺项提示。导入阶段不会执行复现程序。轨迹 JSON 损坏会留下 `invalid_trace`，不会丢弃原问题；路径越界、符号链接或缺少被引用文件仍按已有证据规则拒收。检查结果不影响关闭条件，不自动归因：矛盾可能来自非法测试调度、错误埋点、前提不成立，也可能来自实现未履行自己承诺的交付义务。

## 指定版本执行与具体反馈

公共能力位于 `runtime/`，生成和审计都依赖它，公共模块不依赖两个 agent 角色。`local_exec.py` 保留执行隔离与清理，`replay.py` 准备候选副本，`evidence.py` 负责关联记录与提出具体问题，`storage.py` 保留既有凭据筛选，工具链、Codex 辅助和轨迹检查也在此处。审计的私有认证、配置与连续会话仍留在 `auditor/`。

当前 Go 实验的 `isolated_exec` 增加两个可选参数：`source` 选择 run brief 列出的候选别名，`overlays` 是当前 work 下的相对测试/辅助文件路径列表。审计提供 `candidate`，复核提供 `candidate`（修复后）与 `before`（紧邻的修复前），修复提供 `candidate`（本轮输入）；初次生成尚无候选可选。其他工具链保留原有工作区执行方式。这不是固定测试清单，agent 仍自行选择命令、测试内容和是否使用重放。

```json
{
  "argv": ["go", "test", "-run", "TestReproduction", "./tests/..."],
  "source": "candidate",
  "overlays": ["tests/reproduction_test.go"],
  "timeout_seconds": 60.0
}
```

选定 source 后，公共执行服务从捕获的源码准备私有可写副本，再加入指定文件。它记录起始 commit、所加文件及是否覆盖已有源码，将文件原字节保留在 `executions/<id>/inputs/`，命令与输出仍在同一执行目录。运行后清理副本与构建缓存，保留重建所需的输入和日志。新增文件只能从当前工作区安全相对路径读取，沿用凭据筛选、禁止链接和编译产物等保护。真实执行继续使用私有网络与进程空间，不在主机执行测试。

默认不指定 source 时沿用可修改工作区，`source_context.kind` 明确标为 `mutable_workspace`，其 `base_commit` 仅提供上下文。指定版本时标为 `candidate_copy`，表示起始输入来自该版本和所列补充文件；任意命令仍可能修改其副本或测试无关行为，因此不能据此声称全程运行原样源码或断言成立。`overlays` 覆盖已有源码会被记录和提出解释请求，不会禁止有用的诊断实验。自定义测试中的 PASS/FAIL 含义仍需检查断言。

问题的已有 `evidence` 引用 `executions/<id>/result.json` 或该执行日志时，控制器自动读取同目录由执行服务生成的记录，验证执行 ID，并填充 `execution_records`。agent 写在 work 中的同名 JSON 不作为可信执行记录，输入中自称的 `execution_records` 会被重算。跨轮次交接同时重映射记录和补充文件路径。生成阶段在阶段目录保留记录，修复记录交给复核；这一轮不新增自动批量重放器，不会在问题导入时执行 agent 的脚本。

`evidence_feedback` 中每项包含可定位的 `observation` 和针对它的 `request`：例如日志对应可修改工作区、命令超时、记录对应另一候选、补充文件覆盖了源码，或轨迹中的某次交付超过了所声明上界。仅缺少一个质量说明字段不会触发反馈。没有关联隔离执行记录也不等于没有执行；普通 shell 的记录仍可作为证据，需要解释来源。审计可用可选 `method: source_review` 或 `blocked` 明确静态/受阻依据，避免无意义地催促执行。

每个完整审计回合保存 `turns/<回合>/evidence-feedback.json`，下一回合注入尚未提示的具体观察，每次至多展示 12 项，其余仍保留。相同观察不反复推送；agent 可补充执行、说明为何不适用、收窄或撤回结论。修复通过问题交接收到这些反馈，复核收到原反馈和修复记录。没有新增强制补测轮次或通过阈值；复核仍在首个完整回复后结束，发现阶段仍按原预算续审。反馈不自动裁定问题状态，不能用两个 agent 的共识替代证据。

`AUDIT.md` 和 `VERIFY.md` 中的 `<!-- continuation -->` 分隔首轮任务与同一会话的后续提示；新一轮候选审计仍从首轮任务开始。审计在已有 `report.md` 中保留简要调查线索、被排除的解释和未决问题，续轮据此选择工作，不新增强制状态文件或固定调查模板。生成、修复、审计和复核均要求区分输入要求、外部假设、工程选择及规格缺口，不能用实现文档与自测的一致来替代要求依据。

## 会话过程与用量

公共 `runtime/agent_records.py` 在每个生成、修复、审计和复核阶段结束时，按根会话 ID、工作目录和父子关系读取本阶段的本地原生会话记录。审计会在删除私有 Codex home 之前完成采集。`agents.json` 汇总会话关系、实际模型和推理强度、各回合起止时间与可用的原生 duration、调用类型计数、用量及缺失提示；`agent-records/<thread_id>.json` 保留经过字段筛选的用量、生命周期与委派事件。它们随交接包保留，实验阶段条目给出路径。只导出这些元数据，不复制会话正文、指令、命令内容、账户信息或认证文件，并继续执行凭据筛选。

用量按原生 `token_usage_record` 的 `(thread_id, response_id)` 去重，排除子会话继承的父会话历史，再与各线程累计计数核对。原始 CLI usage 仍保留用于追查，但不与该汇总相加；cached 和 reasoning 是对应 token 分类的子集，不能另加到总数上。`usage_complete` 只描述已识别会话家族的记录完整性与计数核对结果，不是账单认证；缺失子会话、格式不支持、截断或未正常结束的回合都明确保留不完整提示，未知用量为 null。回合 duration 与从创建到最后记录的 observed span 分开保存，后者包含空闲时间；并行会话的时间不能当作实验墙钟直接相加。原生日志格式会随 CLI 变化，记录中保留实际 CLI 版本以便检查。

## 预算与停止

默认总墙钟 180 分钟，初始生成最多 90 分钟，新问题审计每次最多 20 分钟，修复最多 30 分钟，独立复核最多 10 分钟，最多修复三轮。启动生成和修复时预留最后 20 分钟新审计；下一轮修复至少有 5 分钟可分配时间，并另留复核与交接时间。交接复制完成、真正启动修复前还会重新检查最低可用预算，不足时直接转入最后审计。每一步使用实际剩余预算计算，提前结束的时间自然留给后续阶段，不要求耗尽某个阶段。

审计每回合都看到剩余时间。控制器用最近至多三个完整回合耗时的中位数估计下一次调查长度；不足以容纳该长度加收尾余量时，将下一次调用标为 `wrap_up`，让 agent 整理已有证据、完成适合的小检查并交付报告和索引，完成后结束本次审计。余量取阶段总时长的 5%，上限 60 秒；已有完整报告而连这段余量都不足时，保留已有报告，不启动只剩十几秒的新调用。这只是时间安排，不规定测试内容，也不判断覆盖充分。没有完整报告时不会伪装成成功收尾；收尾调用超时仍沿用最后完整回合的证据恢复规则。

| 状态或停止原因 | 含义 |
| --- | --- |
| `prepared` / `running` | 已准备材料 / 正在运行 |
| `cycle_complete` + `no_open_findings` | 本次调查没有待处理问题；不代表正确性已证明 |
| `cycle_complete` + `repair_limit` | 已达修复次数上限，最后审计可能仍有问题 |
| `cycle_complete` + `insufficient_repair_budget` | 不足以容纳下一轮修复、复核及最后审计，已保留末次审计 |
| `cycle_complete` + `no_change` | 修复明确未改动，独立复核和最后审计后停止 |
| `needs_specification` | 必需的语义决策缺失，或输入文档被改写 |
| `verification_incomplete` / `verification_failed` | 复核没有完整可用结果，问题保持未解决；随后执行最后新审计 |
| 审计阶段 `budget_wrap_up` | 完成最后一次收尾，或剩余时间过短而保留已有完整报告；仍需校验报告和索引 |
| `audit_incomplete` | 没有完整报告或有效索引；不能解释成零缺陷 |
| `environment_blocked` | 本地执行或复核被环境阻塞 |
| `budget_exhausted` / `stage_timed_out` | 总预算 / 当前生成修复阶段到期 |
| `audit_failed` / `agent_failed` / `controller_step_failed` | 审计、模型阶段或控制器步骤失败 |
| `interrupted` | 收到中断并保留部分产物 |

已有问题不能因为新审计没再提及而消失。只有独立复核的 `fixed` 或 `not_substantiated` 结论会将对应报告项移出待处理集合。复核交付不完整时不更新旧状态，继续最后一次新问题审计后停止。没有自动续跑、自动重试失败实验或固定 token/费用上限，正常清理和归档可能额外占用数秒。

## 仍需研究的内容

本轮不扩展协议至 crash-restart、成员变更、快照或追赶。新增的有限事件检查不等于协议模型检查；未实现独立线性一致性检查器、自动调度探索、自动反例最小化、隐藏终测或形式化裁决。提示要求 agent 根据根因自行简化反例和选择相关场景，这些动作是否执行仍需看原始记录。新审计会看到候选已加入的回归测试，因此不能把这些测试算作未见测试。具体共识性质仍需结合合法时序、故障界、客户端事件、预期依据和原始轨迹人工核验。
