# 工作流与证据边界

`workflow.py` 连接 `generator/` 和本地 `auditor/`。生成、修复与审计模型均为 `gpt-6.1-sol / high`。协议和系统范围保持在输入文档中；Python 负责版本、预算、文件和结果关联，不补充协议语义。测试仍只要求在 `tests/`，具体方案由 agent 选择。

## 阶段与执行能力

首次生成后导出候选 v000，启动新问题审计。若存在待处理问题且预算允许，启动新修复会话，导出下一候选，再启动独立的修复复核。复核接收指定问题、原始证据、历史回归材料、修复声明及前后代码；审计提示为 `inputs/VERIFY.md`。复核完整交付后结束；缺失索引、漏项或缺少执行关联会在剩余预算内交回同一会话补充。后续发现审计只在剩余预算及修复轮次允许时启动，不向其提供旧报告或修复声明。最后发现的正式问题仍可修复，最后一次修改以独立复核收尾；复核失败、未完成或仍有问题时保留相应状态，不强制追加完整审计。两者使用审计侧权限和执行环境，新问题审计在阶段预算内调查并安排收尾。

生成需给审计留下时间；修复只预留独立复核和交接余量，不再强制预留另一轮发现审计。审计分配时间时，在能容纳修复加复核的情况下保留这部分时间，并在审计结束后按实际剩余预算重算。达到修复次数上限时，最后一轮是审计、修复、独立复核；`max_repairs=0` 仍只生成并审计。复核后的新问题和未修复项继续保留为开放问题，停止不代表这些问题已经消失。

生成和修复通过 `generator/execution.py` 接入 `runtime/local_exec.py` 的真实 STDIO MCP 服务。`forge_local.isolated_exec` 使用白名单文件系统、离线 Go、私有网络与 PID/IPC 空间；输入与执行记录不能被测试程序改写。所有通信进程要在一次调用中启动，返回或超时后清理子进程。启动模型前执行私有 TCP 探测；失败记为环境问题，不回退到主机执行。生成/修复整体墙钟包含工具执行时间，审计仍保留原 CA 的回合计时方式。

生成/修复由 `generator/client.py` 建立临时私有 `HOME`、`CODEX_HOME` 和限定的进程环境，复用公共 Codex 功能设置，关闭本机配置、自动 AGENTS、skills、记忆和插件加载。项目指令从本阶段 `inputs/AGENTS.md` 显式传入，任务正文仍由 `TASK.md` 或 `REPAIR.md` 提供；候选工作区保留材料副本用于查看。启动前执行无模型的原生提示检查，并禁用 CLI 初始化时生成的内置 skills；检测到意外自动指令时停止，不回退为继承本机设置。阶段保留 `client-prompt.json`（检查上下文）和 `client-settings.json`（无凭据配置），实际执行命令与执行工具配置仍记录在 `run.json`。

生成侧只从宿主读取文件式 ChatGPT 认证副本，或使用显式 `CODEX_API_KEY`；不读取本机 provider/profile，不自动登录，不修改原认证文件。临时认证文件权限为 0600，认证值不进入 shell 环境或记录的 CLI 设置，结束前采集本阶段私有目录中的主/子会话用量，再清理私有目录。普通生成 shell 保留 host/workspace-write 模式，没有主机文件读取隔离。配置隔离和 MCP 执行隔离并不让整个生成 agent 变成隐藏评测环境。审计侧私有认证、只读源码与日志、日志中的认证值脱敏、执行隔离及清理措施保留。

各阶段允许 Codex 原生子智能体按需分工，提示要求沿用当前模型、推理强度、权限和阶段预算，由主智能体协调共享文件、汇总证据并在回复前结束委派工作。生成与审计均启用本机 CLI 的 `multi_agent` 功能；不允许嵌套 Codex CLI 或外部模型服务。阶段内部分工不替代生成后的独立审计与修复复核，也不扩大外部发布、远程部署、第三方通信或凭据修改的权限。本地集群启动、客户端和协议通信、范围内故障注入及自有测试资源清理属于任务范围。

隔离工具在运行目录使用普通进程锁，协调多个子智能体可能创建的独立 MCP 服务，避免同时改写可变工作区和执行时钟；进程退出会释放锁。排队占用总预算，取得执行权后仍受单次动作时限和总截止时间约束。分析与其他独立工作可以并行；调用者仍需协调普通 shell 和文件编辑，因为执行锁只覆盖隔离工具调用。工具描述统一说明网络、生命周期、源码副本和日志选项，阶段提示只保留入口及该阶段特有的版本含义。

隔离工具内运行真实进程、套接字和计时器，所有通信进程在一次调用中启动并在返回后清理。这个生命周期是实验设施约束，不是服务器 API 要求；交付的服务和客户端必须能通过普通命令独立运行。当前检查仍以单机私有网络为主，不据此宣称验证了跨机器部署或长期持续服务。

## 版本与问题交接

四类提示分别落实不同责任：`TASK.md` 要求按性质依据、状态归属和完整运行路径推进生成；`AUDIT.md` 要求记录调查范围，并建立“要求 → 合法触发 → 可达入口 → 实际观察 → 因果解释”的证据链；`REPAIR.md` 要求先重放、解释根因、修复共享原因，再检查原场景和相关变体；`VERIFY.md` 独立检查前后版本及行为是否被削弱。它们不规定 Go 文件布局或固定测试集合，不要求为了多跑一轮而耗尽预算。

`DESIGN.md` 由生成 agent 编写并随候选代码保留，作为贯穿实现、审计和修复的说明。开始时可以是简短且可修改的草稿；实现改变状态归属、接口、同步方式或完成事件时更新相应内容，交付前对应到实际代码位置。关键说明解释采用了什么机制、为什么满足要求、哪些入口使用它，以及已有检查覆盖到哪里。输入引导这种推导与检查，不指定接收时间戳、队列批次或历史索引方案。审计将设计说明用作调查线索，依据要求与实际行为判断；修复可自主选择解决方案，缺少具体机制说明不自动构成规格缺口。文档未更新与协议实现错误需要分别判断，不能把设计说明当成新的协议规则或正确性证明。控制器不检查固定标题，也不增加新的阶段或停止条件。

候选仍使用独立干净 Git 仓库的 commit 关联，不新增候选哈希。`artifacts.py` 从源码捕获和逐回合增量重建最后一个完成回合；原始未完成回合继续留存。报告和索引均取自该完成状态，不从超时后仍被改写的工作区取值。其后未完成回合通过 `supplemental_turns` 列出状态和原始目录；`changes/manifest.json` 指向新增或修改的测试、报告和索引。这些补充材料随证据目录进入后续交接的概览和索引，供 agent 检查并复用，不替换已完成报告，也不自动增加修复任务。

候选源码、测试、文档和审计证据都是交付材料，导出、捕获、重放、归档和清理均不按文件名或内容猜测其中是否存在凭据。测试密码、证书样例、`.env.example` 和测试用 `auth.json` 原样保留。模型登录文件留在候选工作区之外的私有目录，认证值继续在运行日志中脱敏。路径边界、私有运行目录排除、链接检查、执行隔离及资源限制继续保留。

审计回合因计时截止而中断时，仅在会话有效且可继续的情况下使用预留窗口收尾。已报告的 TLS 握手重连错误若之后已有正常工具完成事件，不再单独阻止同会话收尾；原错误仍保留。尚未恢复的连接错误、安全拒绝、会话不一致或 `turn.failed` 不会因此获得自动续轮。未完成报告仍不直接成为正式结论。

审计维护 `report.md` 与 `findings.json`。后者是普通 JSON 导航：候选 commit、调查范围和限制、局部问题 ID、预期性质、合法前提、复现命令、断言极性和证据路径。控制器为 ID 加审计轮次前缀，例如 `a000-F1`，保存到实验根目录 `issues.json`。描述性字段允许非空文本、列表或对象，并按原结构保留；修复和复核中的说明、理由及观察也遵循这一规则，额外说明字段不会导致拒收。版本、ID、动作和状态仍必须使用对应字符串，证据仍是安全的相对文件路径列表。这是报告项标识，不是独立根因计数；不同审计可能重复发现同一根因，当前不按自然语言自动合并。

审计一旦决定保留一个有证据的问题，就先同步保存报告和索引，再继续调查变体或其他问题；收窄或撤回结论时也同时更新。复核同样按已完成检查的问题保存报告和对应条目，不等到最终回复才统一写入。未确定的猜想留在报告里并说明不确定性，不为填满索引而编造结论。这是交付要求，不指定调查方向或测试清单。

`handoffs/` 保留每次审计的完整证据；`feedback/` 为下一轮修复组合待处理问题和已关闭历史，并附独立复核证据。`issues.json` 保留未解决项，`history.json` 保留已关闭项，后者由 `handoff.json.history_file` 指出。历史材料包含原始缺陷复现、复核新增测试和执行记录；导航中显示历史关闭所依据的版本，不把它解释为当前版本已验证。agent 按改动选择回归检查，不要求每轮跑完全部历史测试，也不自动把审计测试复制进候选。原始问题的来源 commit 不随候选升级而改写。修复结果只是声明；候选导出排除反馈目录，保留 agent 加入的正式回归测试。

交接中的 `handoff.json.repair_issue_ids` 明确本轮需要修复和复核的 ID；`issues.json` 同时保留其他待解决的规格问题作为上下文。修复侧可以逐项报告 `needs_specification`，在原有 `reason` 中说明材料缺少哪个决定、影响哪些行为；若另一项也依赖它，应指出对应 ID 和原因。全局 `action` 只描述是否改了候选文件：`repaired` 或 `no_change`。旧式全局 `needs_specification` 仍能读取，但也进入独立复核，不能直接结束整个流程。

是否因无改动停止，依据前后候选文件的实际新增、删除和内容修改，不由 `action` 自述决定。声明与实际不符时保留 `action_mismatch`；复核同时看到原声明和 `actual_changes`。规格缺口仍按逐项复核结果处理。

只有独立复核确认后，该项才处于 `needs_specification` 状态；它仍计入 `open_issues`，并列在 `awaiting_specification` 中，暂时不进入后续修复批次。其他问题继续修复，修改后的候选继续接受新的审计。若复核认为现有材料已明确要求，则保留 `unresolved`，不能靠修复侧的规格缺口声明跳过处理。没有其他可处理问题时才因规格缺口收尾；预算、轮次和环境限制仍独立生效。材料仍受保护，agent 擅自改写输入文件会停止交付。真正补充规格后应准备使用新材料的实验，不在运行中悄悄改变要求。

`reviews/` 中的复核有只读上下文、原始运行与完成回合交接包。`review.json` 关联 before/after commit，逐项记录处理结论、前后观察、执行或静态审阅方法以及保留证据。`fixed` 需要独立执行；只有静态推测或环境阻塞时保持未解决；`blocked` 不能搭配任何关闭问题的结论，包括 `not_substantiated`。缺陷 witness 的 PASS 可能表示触发了错误，复核按实际支持的性质判断；例如在输入要求允许的边界上显式拒绝过大响应可以是有效修复，但不能用新写的限制撤销既有成功语义。修复和复核都要检查 diff 影响的原有行为，特别是原先成功的路径是否变为拒绝、长期等待或重复执行；既有测试全部通过不能代替这些检查。

`fixed` 的执行依据必须关联本次复核中已完成的实际命令：可引用隔离服务的 `executions/<id>/result.json` 或日志，也可引用原生命令的 `turns/<回合>/stdout.jsonl`。只有说明文字、测试源文件、未完成执行，或仅有明确绑定修复前版本的副本执行，都不足以完成这一关联。普通 shell 或可修改工作区的来源仍需 agent 解释；代码不能从命令完成推断它检查了哪个性质，也不把退出码 0 当作修复成功。原始结论、具体反馈和执行日志都保留，语义上的误判留待审阅。

复核发现与原问题相关的回归时，应把原问题保持为未解决；另一个有充分依据的缺陷可以写入 `review.json.new_issues`，沿用发现阶段的问题和证据格式。控制器先完整校验复核结果，再更新旧问题并导入新问题，按修复后候选版本赋予 `r001-F1` 这类 ID。即使随后新审计没有发现问题，这些条目仍会进入下一轮修复；复核不承担额外的全系统发现任务。规格确有缺口时保留 `needs_specification`，不能把修复造成的退化重新解释为规格缺口。

质量说明可以写在报告或额外字段中，不要求固定标题集合。`legality`、`reachability`、`causal_explanation`、`variants` 等旧字段继续保留和传递，但缺失本身不产生催填提示。现有版本、ID、状态、最小报告结构和安全路径校验仍保留。修复说明按原结构进入复核的 `request.json.repair_claim`，修复阶段的隔离执行记录另复制到上下文 `repair-executions/`；原日志中的绝对路径仍是原运行路径。

修复交接的 `overview.md` 由 `handoff.json.overview_file` 指出，只放问题说明的短摘录、来源版本、最近复核和执行记录链接；已关闭项用简表指向完整历史。长说明按字符截短，不用模型改写，也不在导航里重复整份 JSON；原值仍完整保存在 `issues.json`、`history.json` 和原报告。跨版本证据复制到 `previous/` 时，普通文件、执行记录和轨迹引用一起映射；同一来源包只复制一次。原始 commit 与原报告保持原样。API 变化时保留原 witness，另写适配器并说明如何保留场景；编译失败不能被解释为缺陷已修复。

`execution_records` 还提供可复用的运行信息：`restore` 把工作区目标路径映射到当时保留的测试输入文件，`outputs` 指向原始 stdout/stderr 和所选产物，`cwd_relative` 是源码副本内的执行目录，`timeout_seconds` 是原执行时限。产物用 `artifact:<工作区相对路径>` 区分，例如 `artifact:results/history.json`。交接旧版本证据时，这些保留文件路径也随包更新，目标路径和原始 `argv`、`cwd` 保持不变。旧记录没有相对目录时写 null，不推测；绝对命令路径、临时二进制和未保留的依赖仍需 agent 检查或重建。这些信息用于沿用原场景，既适用于普通测试，也适用于事件调度；控制器不自动执行证据命令。原始报告中的断言极性仍是判断依据，退出码不代替性质判断。

审计的 `findings.json` 和复核的 `review.json` 可选填顶层 `cases`：每个案例至少包含 `summary`、`reproduction` 和非空 `evidence`，范围、前提和断言含义可写在描述或附加字段中。这让未发现缺陷但值得保留的检查也有复用入口。可选 `open_questions` 保存尚未解决的规格或调查问题，允许文字、列表或对象。控制器按报告版本写入实验根目录的 `evidence-index.json`，并通过下一轮交接的 `handoff.json.evidence_index_file` 提供映射后的副本；复核也收到该交接包。每条记录保留来源报告、记录版本和执行工具实际记录的源码，两者不被混同。可选案例引用有误时记录 `warnings`，不影响正常问题导入；原材料仍保留。它们不自动成为缺陷、额外修复任务、当前版本验证或继续实验的条件，也不交给全新的发现审计。

`issues.json` 的 `import_status` 区分尚未审计、正在导入、已导入和导入不完整，`imports` 逐次记录来源版本、索引路径、错误与成功导入的问题数。失败时问题数为 null，不能把空 `issues` 列表解释为没有发现；`forge.py inspect` 同时输出 `issue_index_status`。结果内容或版本不合法时保留原始文件并明确记录不完整。JSON 字段和存在的日志引用不能证明测试推理正确。复核结论的来源与证据已经明确记录，不另设始终不变的 `assessment` 字段；历史实验保留原文件，`inspect` 不再输出旧字段。

审计或复核交付失败，或已返回阶段还包含最后完成回合之后的未完成调查时，控制器在 `experiment.json.pending_audit_reports` 和 `issues.json.pending_reports` 中列出已有报告、索引及原始回合和执行记录的路径，标为 `needs_review`。这些是待复核材料，不是已导入的问题；正文和索引可能不同步，索引甚至可能损坏，空索引不能说明没有发现。控制器不从正文自动提取问题，不因此关闭旧问题或启动修复，原停止状态保持不变。失败阶段的模型用量和具体停止原因也从原始运行记录汇入。`inspect` 可以只读地补充旧实验的这些路径和元数据，不改写历史文件。若没有报告或索引，仍只报告原失败，不凭空产生待复核成果。

## 调度、重放与协议模型边界

在现有 `isolated_exec` 中使用可选 `runtime/schedule.py`，通过候选适配器控制实际事件并记录、重放交互。生成/修复收到 `inputs/schedule.py`，审计/复核收到只读 `tools/schedule.py`；工具与执行记录进入原有交接包。`runtime/replay.py` 负责准备指定源码副本和保留测试覆盖文件。没有新增模型阶段、固定测试清单或协议判断器，具体接口见 [scheduling.md](scheduling.md)。

旧 `runtime/tracecheck.py` 仍能独立检查逐消息有界交付的旧账本，但不适用于混合协议 W/s 的完整广播窗口。新实验不注入它，调度结束和证据导入也不调用它。原始实验保存的工具和结果不改写，当前审计实现源码快照仍可能包含该历史文件，这不代表它被提供为适用的检查工具。

新报告将轨迹、普通日志和 JSONL 放在 `evidence`。旧格式 `trace_files` 引用继续校验路径、保留和映射，但不解析为时间模型；新导入的 `trace_checks` 为空，不能将 agent 自报的检查结果当作控制器判定。路径越界、符号链接和不存在文件继续按原证据规则处理。控制器仍检查执行关联和显式版本不符，解释断言及其性质含义仍属于审阅工作。

## 指定版本执行与具体反馈

公共能力位于 `runtime/`，生成和审计都依赖它，公共模块不依赖两个 agent 角色。`local_exec.py` 保留执行隔离与清理，`replay.py` 准备候选副本，`evidence.py` 负责关联记录与提出具体问题，`storage.py` 提供日志脱敏和证据存储辅助，工具链、Codex 辅助和调度重放也在此处。审计的私有认证、配置与连续会话仍留在 `auditor/`。

当前 Go 实验的 `isolated_exec` 可用 `source` 选择 run brief 列出的候选别名，`overlays` 是当前 work 下的相对测试/辅助文件路径列表，`outputs` 选择执行后需归档的文件或目录。审计提供 `candidate`，复核提供 `candidate`（修复后）与 `before`（紧邻的修复前），修复提供 `candidate`（本轮输入）；初次生成尚无候选可选。其他工具链保留原有工作区执行方式。这不是固定测试清单，agent 仍自行选择命令、测试内容和是否使用重放。

```json
{
  "argv": ["go", "test", "-run", "TestReproduction", "./tests/..."],
  "source": "candidate",
  "overlays": ["tests/reproduction_test.go"],
  "timeout_seconds": 60.0
}
```

选定 source 后，公共执行服务从捕获的源码准备私有可写副本，再加入指定文件。它记录起始 commit、所加文件及是否覆盖已有源码，将文件原字节保留在 `executions/<id>/inputs/`，命令与输出仍在同一执行目录。运行后清理副本与构建缓存，保留重建所需的输入和日志。新增文件只能从当前工作区安全相对路径读取，禁止链接和编译产物。真实执行继续使用私有网络与进程空间，不在主机执行测试。

需要保留测试写出的轨迹或历史文件时，可在工具调用中添加 `"outputs": ["results/history.json", "results/traces"]`。路径相对于执行工作区根目录，而非 `cwd`；目录递归收集。进程停止后、临时副本清理前，把可保留文件复制到 `executions/<id>/artifacts/`，成功、非零退出和超时都执行此步骤。`result.json.artifacts.files` 列出原路径及保存路径，`excluded` 说明缺失或未保留原因。沿用链接、私有目录和编译产物筛选，最多 16 MB/文件、64 MiB 总量、1024 个目录与文件条目；超限会保留已收集部分并明确说明。产物归档不改变测试退出码，也不保证所选文件是本次新生成的；使用前仍需检查内容。未选择的临时产物会随副本清理，不能依赖事后读取。

默认不指定 source 时沿用可修改工作区，`source_context.kind` 明确标为 `mutable_workspace`，其 `base_commit` 仅提供上下文。指定版本时标为 `candidate_copy`，表示起始输入来自该版本和所列补充文件；任意命令仍可能修改其副本或测试无关行为，因此不能据此声称全程运行原样源码或断言成立。`overlays` 覆盖已有源码会被记录和提出解释请求，不会禁止有用的诊断实验。自定义测试中的 PASS/FAIL 含义仍需检查断言。

问题的已有 `evidence` 引用 `executions/<id>/result.json` 或该执行日志时，控制器自动读取同目录由执行服务生成的记录，验证执行 ID，并填充 `execution_records`。agent 写在 work 中的同名 JSON 不作为可信执行记录，输入中自称的 `execution_records` 会被重算。跨轮次交接同时重映射记录和补充文件路径。生成阶段在阶段目录保留记录，修复记录交给复核；这一轮不新增自动批量重放器，不会在问题导入时执行 agent 的脚本。

原生 shell 执行使用 `turns/0001/stdout.jsonl#item_7` 这样的引用，选择该日志中唯一的、已完成的 `command_execution` 项；`item_7` 应来自实际事件 ID。整份 `stdout.jsonl` 仍可作背景证据，但不会把其中所有命令都算成当前问题的验证。选择命令后仍需解释它运行的源码与断言含义；机械关联不能证明该命令检查了所声称的性质。

`evidence_feedback` 中每项包含可定位的 `observation` 和针对它的 `request`：例如日志对应可修改工作区、命令超时、记录对应另一候选、补充文件覆盖了源码，或轨迹中的某次交付超过了所声明上界。仅缺少一个质量说明字段不会触发反馈。没有关联隔离执行记录也不等于没有执行；普通 shell 的记录仍可作为证据，需要解释来源。审计可用可选 `method: source_review` 或 `blocked` 明确静态/受阻依据，避免无意义地催促执行。

每个完整审计回合保存 `turns/<回合>/evidence-feedback.json`。普通证据观察在下一回合展示尚未提示的至多 12 项，agent 可解释、补充或收窄结论。复核另记录 `delivery_errors`：报告或索引缺失、版本或 ID 不对应、证据引用无效、`fixed` 未关联执行等。这些交付错误使用与最终导入相同的校验规则，在原预算和调用次数内继续反馈，完整交付后即可停止。若预算耗尽仍无法交付，保留未完成材料，旧问题不据此关闭。轨迹疑点和来源解释等普通反馈不被转换成自动真假判决，也不要求为了消除每条提示而额外测试。

`AUDIT.md` 和 `VERIFY.md` 中的 `<!-- continuation -->` 分隔首轮任务与同一会话的后续提示；新一轮候选审计仍从首轮任务开始。审计在已有 `report.md` 中保留简要调查线索、被排除的解释和未决问题，续轮据此选择工作，不新增强制状态文件或固定调查模板。生成、修复、审计和复核均要求区分输入要求、外部假设、工程选择及规格缺口，不能用实现文档与自测的一致来替代要求依据。

## 会话过程与用量

公共 `runtime/agent_records.py` 在每个生成、修复、审计和复核阶段结束时，按根会话 ID、工作目录和父子关系读取本阶段的本地原生会话记录。各阶段都在删除私有 Codex home 之前完成采集。`agents.json` 汇总会话关系、实际模型和推理强度、各回合起止时间与可用的原生 duration、调用类型计数、用量及缺失提示；`agent-records/<thread_id>.json` 保留经过字段筛选的用量、生命周期与委派事件。它们随交接包保留，实验阶段条目给出路径。只导出这些元数据，不复制会话正文、指令、命令内容、账户信息或认证文件，并继续执行元数据中的凭据脱敏。

用量按原生 `token_usage_record` 的 `(thread_id, response_id)` 去重，排除子会话继承的父会话历史，再与各线程累计计数核对。原始 CLI usage 仍保留用于追查，但不与该汇总相加；cached 和 reasoning 是对应 token 分类的子集，不能另加到总数上。`usage_complete` 只描述已识别会话家族的记录完整性与计数核对结果，不是账单认证；缺失子会话、格式不支持、截断或未正常结束的回合都明确保留不完整提示，未知用量为 null。回合 duration 与从创建到最后记录的 observed span 分开保存，后者包含空闲时间；并行会话的时间不能当作实验墙钟直接相加。原生日志格式会随 CLI 变化，记录中保留实际 CLI 版本以便检查。

## 预算与停止

默认总墙钟 240 分钟，初始生成最多 90 分钟，首次独立审计最多 60 分钟，修复后的新问题审计最多 30 分钟，修复最多 30 分钟，独立复核最多 15 分钟，最多修复三轮。`initial_audit_seconds` 控制首次审计，`audit_seconds` 控制后续新问题审计，`verification_seconds` 控制末次新审计，`repair_verification_seconds` 控制修复复核。启动生成和修复时预留最后 30 分钟新审计；下一轮修复至少有 5 分钟可分配时间，并另留复核与交接时间。交接复制完成、真正启动修复前还会重新检查最低可用预算，不足时直接转入最后审计。首次审计即使也是唯一一次审计，仍使用首次上限。每一步使用实际剩余预算计算，提前结束的时间自然留给后续阶段，不要求耗尽某个阶段。旧配置或已准备实验缺少 `initial_audit_seconds` 时，首次审计沿用其保存的 `audit_seconds`。

审计每回合都看到剩余时间。收尾余量取阶段总时长的 5%，上限 60 秒；剩余时间不超过两倍收尾余量时，将下一次调用标为 `wrap_up`，让 agent 整理已有证据、完成适合的小检查并交付报告和索引，完成后结束本次审计。因此，默认 30 或 60 分钟审计只在最后最多两分钟安排收尾；还剩数分钟时，agent 可以选择较短的后续调查。最近回合已完整结束且连一份收尾余量都不足时，直接保留已有报告，不启动极短调用；如果最近回合超时可续接，仍利用剩余余量整理该回合留下的材料。

最近至多三个已完成或可续接超时回合的实际墙钟耗时中位数仍保留在记录中，包含工具执行和回合归档时间，但不再用于判定后续调查至少需要多久。`investigation_seconds` 给出扣除收尾余量后的调查时间；调查调用和隔离执行共享“阶段截止时间减收尾余量”的墙钟截止时间，测试暂停 agent 回合计时也不能越过它。达到此界限记为 `reporting_reserve`；会话可续接且还有调用次数时，下一回合在原阶段截止时间内收尾。归档和清理也消耗余量，实际可用收尾时间会相应减少。单回合和阶段总时限继续生效。这只是时间安排，不规定测试内容，也不判断覆盖充分。收尾调用仍可能超时，此时沿用最后完整回合的证据恢复规则；从未交付完整报告时，保留草稿和执行记录，但不能将它们作为完整交接。

| 状态或停止原因 | 含义 |
| --- | --- |
| `prepared` / `running` | 已准备材料 / 正在运行 |
| `cycle_complete` + `no_open_findings` | 本次调查没有待处理问题；不代表正确性已证明 |
| `cycle_complete` + `final_review_complete` | 最后一次独立复核完成，已报告问题关闭；不代表做过新的全面审计或证明整体正确 |
| `cycle_complete` + `repair_limit` | 已达修复次数上限，在最后一次独立复核后结束，可能仍有开放问题；零次修复配置只审计 |
| `cycle_complete` + `insufficient_repair_budget` | 不足以继续安排发现、修复和复核，保留当前候选及开放问题 |
| `cycle_complete` + `no_change` | 前后候选文件实际没有变化，独立复核后停止；逐项规格缺口声明交给复核判断 |
| `needs_specification` | 剩余问题均为复核确认的规格缺口，或输入文档被改写；具体 ID 见 `awaiting_specification`，原因见各问题与流程记录 |
| `verification_incomplete` / `verification_failed` | 复核没有完整可用结果，停止并保持问题未解决，不启动另一轮发现审计替代它 |
| 审计阶段 `budget_wrap_up` | 完成最后一次收尾，或剩余时间过短而保留已有完整报告；仍需校验报告和索引 |
| `audit_incomplete` | 没有完整报告或有效索引；不能解释成零缺陷 |
| `environment_blocked` | 本地执行或复核被环境阻塞 |
| `budget_exhausted` / `stage_timed_out` | 总预算 / 当前生成修复阶段到期 |
| `audit_failed` / `agent_failed` / `controller_step_failed` | 审计、模型阶段或控制器步骤失败 |
| `interrupted` | 收到中断并保留部分产物 |

已有问题不能因为新审计没再提及而消失。只有独立复核的 `fixed` 或 `not_substantiated` 结论会将对应报告项移出待处理集合。复核交付不完整时不更新旧状态，保留失败及待复核材料后停止。没有自动续跑、自动重试失败实验或固定 token/费用上限，正常清理和归档可能额外占用数秒。

## 仍需研究的内容

本轮不扩展协议至 crash-restart、成员变更、快照或追赶。新增的有限事件检查不等于协议模型检查；未实现独立线性一致性检查器、自动调度探索、自动反例最小化、隐藏终测或形式化裁决。提示要求 agent 根据根因自行简化反例和选择相关场景，这些动作是否执行仍需看原始记录。新审计会看到候选已加入的回归测试，因此不能把这些测试算作未见测试。具体共识性质仍需结合合法时序、故障界、客户端事件、预期依据和原始轨迹人工核验。
