# 11 月 17 日 baseline：生成结果与吞吐测试

**这版已经能达到数千条/秒，较之前两份 baseline 明显改善；但默认执行调度限制了吞吐，较高负载下又会直接拒绝部分请求。调整已有的 Tick 配置后，七副本随机入口可持续处理约 3,000 条/秒，短测约 5,600 条/秒；两者都不能理解为同等速率下完全无拒绝。**

## 1. 生成交付与测量方式

实验为 `20261117T070206Z-sol-high-baseline-1117-01-00tot07s`，使用 gpt-6.1-sol/high，49 分 26 秒正常结束。交付包含 Node、TLS/TCP 传输、服务端、客户端、测试及文档。Go 功能代码共 2,951 物理行，去空行与整行注释后 2,868 行；测试为 1,258/1,226 行。这次只有一个主 agent 会话，自行发现并修复过数据重传放大、测试调度和最大载荷编码问题。

它自带的性能检查多为 120 条请求、约 0.13 秒，最长一项也只有 1,000 条请求、约 0.88 秒，不能据此判断持续吞吐。本次在源码副本上重新运行原生功能测试，通过；随后完成 **37 项运行：33 项普通测量、2 项负载器限流诊断、2 项独立 CPU 剖析**。普通测量直接运行交付的 server，所有 Go 源码与原交付逐文件一致。

本机八个虚拟 CPU、约 12 GiB 内存、Go 1.25.8。主要配置是七个独立进程，各绑定一个 CPU、GOMAXPROCS=1，负载器使用剩余一个；n=7、f=4、s=1、e=1，worker=4。每项重启集群并预热，按固定速率发送独立键 Put，value 为 16 字节，无 batch、故障注入或客户端重试。队列和本地未执行接纳容量均为 4,096。

**吞吐＝正式发送期间收到的 OK 执行回复数 / 发送时长。执行回复比例＝包括收尾等待在内的 OK 数 / 实际发出数。**被拒绝、连接错误和负载器漏发分别记录。每条请求从自身发出时开始计时，等待上限为 15 或 20 秒。只有全部已发请求都取得 OK 时才报告全量延迟。

## 2. 七副本实际能处理多少？

### 持续 30 秒，随机入口

采用 W=200 ms、Tick=5 ms，每档重复两次。表中吞吐是两次范围，回复与拒绝是两次合计。

| 输入速率（条/秒） | 实际吞吐（条/秒） | OK / 实际发出 | 执行回复比例 | 接纳前拒绝数 |
|---|---:|---:|---:|---:|
| 1,500 | 1,499.7～1,499.8 | 89,999 / 89,999 | 100% | 0 |
| 2,000 | 1,999.5～1,999.6 | 119,992 / 120,000 | 99.993% | 8 |
| 3,000 | 2,998.0～2,999.0 | 179,960 / 179,997 | 99.979% | 37 |
| 4,500 | 4,386.8～4,403.3 | 264,260 / 269,998 | 97.875% | 5,738 |

这些持续测试没有连接错误，未返回 OK 的请求均收到 `protocol busy before admission` 拒绝。1,500 条/秒档位的全量平均客户端延迟为 **4.79～4.82 ms**，P99 为 **10.19～10.81 ms**。少数计划请求在发送窗口结束前未能发出，已从实际发送分母中分开列出。

3,000 条/秒时，各五秒区间基本保持该速率，没有持续下滑。4,500 条/秒时，前 25 秒约为 4,464～4,501 条/秒，最后五秒降至 **3,986 和 3,891 条/秒**。因此 4,400 左右是本次 30 秒的平均表现，尚不是长时间稳定的容量。两次结束时七副本堆内存合计约 5.35 GB；历史保留和后台工作成本也需要计入持续服务表现。

### 入口不同，饱和点不同

以下均为 15 秒短测、W=200 ms、Tick=5 ms，每组合一次。每格是 **吞吐（条/秒）；执行回复比例**。

| 输入速率（条/秒） | 全部交给同一个副本 | 均衡分给七副本 | 随机分给七副本 |
|---|---:|---:|---:|
| 1,500 | 1,499.7；100% | 1,499.4；100% | 1,499.5；100% |
| 3,000 | 2,682.6；96.304% | 2,998.3；99.978% | 2,998.9；99.998% |
| 6,000 | 986.9；21.001% | 5,641.3；98.561% | 5,566.4；97.760% |

单点入口在高负载下严重退化：输入从 3,000 提到 6,000，执行回复反而下降到约 987 条/秒。均衡和随机入口能分散初始协调与客户端处理成本，但输入 6,000 时仍分别拒绝 1,295 和 2,012 条请求。个别短测还有 1～4 次 HTTP EOF/连接重置，已计入未取得执行回复的数量，没有算成共识安全性失败。

单点入口另以 2,000 条/秒持续 30 秒，两次吞吐为 1,872 和 1,976 条/秒，分别拒绝 1,475 和 707 条请求。它的持续承载能力明显低于多入口。

## 3. 吞吐限制具体在哪里？

### 执行进度依赖定时轮询

`learn()` 保存决定后只把对应键标为 dirty；应用执行由 `Pulse → tickClass → execute` 推进。Pulse 每次最多调度 **64 个键类**，Tick 默认取 W/5。独立键负载因此受到调度预算限制：40 ms 周期每秒最多提供 1,600 次键类调度，20 ms 为 3,200 次，5 ms 为 12,800 次；其中还有检查和清理工作，不能把这个上界直接当作实际吞吐。

**同为 W=200 ms、输入 1,500 条/秒、发送 15 秒、每请求最多等待 20 秒，只改变 Tick：**

| Tick | 发送期吞吐（条/秒） | 全量平均延迟（毫秒） | 最终执行回复 |
|---|---:|---:|---|
| 40 ms，两次 | 1,134.4～1,326.9 | 1,402～2,261 | 全部 |
| 5 ms，一次 | 1,499.5 | 4.81 | 全部 |

40 ms 两次测试的七副本 CPU 合计只用约 **3.2 个核**，采样中大量实例已经决定但没有执行，说明这个瓶颈出现在执行推进机制，不能归因于 CPU 全部用满。

交付 server 的默认 W=100 ms，因此默认 Tick=20 ms。该配置输入 1,500 条/秒、持续 30 秒的两次测试全部回复，平均延迟 13.30～13.78 ms；输入 3,000 条/秒的 15 秒测试吞吐约 2,835 条/秒，最终全部回复，但平均延迟已经达到 990 ms。**本次没有改代码修复这一机制，5 ms 是候选已有配置能力的对照。**

### 接纳与协议处理争用同一组许可，短暂忙碌也会拒绝

`Submit()` 与协议 worker、Pulse 共用容量为 worker 数的 `parallel` 通道。Submit 获取不到许可就立即拒绝，不等待已有工作释放。它还使用键级 `TryLock`，遇到竞争也可拒绝；本次独立键负载实际记录的主要原因是前一种。

这解释了为什么随机入口 2,000～3,000 条/秒时，整体 CPU 尚未耗尽、请求大多很快完成，却仍有零星拒绝。`worker=4` 在这里是本地同时处理工作的许可数，**不是最多只能存在四个共识实例**。高负载下继续提交只会增加解析、检查和拒绝成本，尤其容易拖慢单点入口。

### 网络与后台传播仍有较大成本

这版已使用持久 TLS/TCP，去掉了旧实现的逐条协议 HTTP 请求，也不再携带 K/carry。剖析未再出现旧版本中 carry 组装或共享缺失前驱重复递归占据大部分 CPU 的现象。

但每条协议消息仍单独 JSON 编码，并分别写出长度头和消息体，产生两次 TLS Write。随机入口输入 6,000 条/秒的独立剖析中，副本 0 的系统调用约占 **26.9% CPU**，JSON 解码累计约 **20.4%**，TLS Write 累计约 **19.3%**；后两类与系统调用存在调用关系，不能相加。单点入口剖析中，协调副本自身已接近一个 CPU 的容量，系统调用约占 35.1%。

后台传播也没有变得很轻：每个副本登记实例或学习决定后，仍会为各 peer 排队完整 `Data`，等待 `DataAck`。七副本、800 条/秒的短测中，平均每个执行回复对应约 **100.5 条远端协议消息**。高负载时这一比值下降，部分原因是每 peer 每轮只处理八个后台条目，传播工作延后，不能解释成每条请求的全部成本自动减少。

## 4. 与之前的吞吐诊断相比

[此前四份实现的诊断](throughput-1117.md)中，两份 baseline 在七副本输入 1,500 条/秒时都明显过载；1111 v000 能跟上 1,500 条/秒，但输入 3,000 后也退化。本次 baseline 在 Tick=5 ms 的持续测量中已能维持接近 3,000 条/秒，多入口短测达到约 5,600 条/秒，表现确实提高了。

这次同时改变了协议材料、传输实现、数据管理和调度方式，旧测试发送时长也不同，因此这些数据说明实现表现的变化，不能把增益全部归给某一句提示词或单独归给删除 K。

另测了三副本、每副本两个虚拟 CPU、随机入口：输入 6,000 条/秒时完成约 **5,862 条/秒**，回复比例 98.198%；输入 10,000 时约 **6,057 条/秒**，回复比例降至 68.485%。这说明目前仍是数千量级，而没有测到数万条/秒；减少副本并增加每副本 CPU，也没有消除接纳和运行时成本。

**本次最明确的改进方向是：让已经决定、可执行的工作及时获得调度，避免把执行吞吐绑定到固定的周期预算；合理处理短暂的接纳竞争；减少逐消息系统调用和冗余后台传播。**这些属于实现选择。它们不要求扩大 K，也不要求先引入共识 batch。

## 6. 对照 EPaxos 作者实现：成本具体差在哪里？

**本次负载全部是独立键 Put，没有 Get，也没有同键读写或重复写。**`load.go` 为第 i 条请求生成 `load/%09d` 的新键；单点、均衡、随机只改变请求交给哪个副本，不改变键的独立性。因此，数千条/秒的瓶颈不能归因于热点冲突或复杂依赖环。三副本输入 6,000 条/秒时，记录的决定也全部来自快速路径。

对照来源为[作者仓库 efficient/epaxos](https://github.com/efficient/epaxos/tree/791b115669fca472d3136f6a2eda46c00b3f8251)，固定到提交 `791b115`。这是包含论文发表后修正的公开代码；其中默认 `MAX_BATCH=1000`，不能直接把默认运行结果当作论文的无 batch 实验。本节完成了源码对照和编解码微测，未重跑作者的整套集群吞吐实验。

论文 §7.3 的普通吞吐测试同样使用 Put，并在执行后回复；客户端在持久连接上成批发送请求，副本间消息不合批。它采用三或五副本、每副本两个虚拟核，且使用 thrifty，仅向所需投票副本发送 PreAccept/Accept。我们的主要测量是七副本、每副本一个虚拟核，命令包含字符串客户端身份、键和值；“value 为 16 字节”不等于论文整个小命令为 16 字节。[论文 §6.2、§7.1、§7.3](https://istc-cc.cmu.edu/publications/papers/2013/epaxos-sosp2013.pdf)

### 消息数量：正常共识之外又做了一轮全互联传播

作者实现的无冲突快速路径，在 thrifty 下，三副本远端消息为 `1 PreAccept + 1 回复 + 2 Commit = 4`，五副本为 `2 + 2 + 4 = 8`，不计客户端和独立探测流量。决定由协调者发给其他副本，普通学习路径没有再逐副本执行同样的全互联数据确认。[广播实现](https://github.com/efficient/epaxos/blob/791b115669fca472d3136f6a2eda46c00b3f8251/src/epaxos/epaxos.go#L547)

我们的协议要求广播给全体成员；七副本的一轮正常快速流程本身约为 `6 PreAccept + 6 回复 + 6 Learn = 18` 条远端消息。baseline 又在 `register()` 和 `learn()` 中调用 `queueGossip()`：每个副本向所有 peer 发送完整 Data，并等待 DataAck。仅“一份数据在七副本间逐对发送并确认”就对应 `7×6×2=84` 条消息；实际还受初始/决定两种 revision、合并和重传影响，不能把 84 当作精确固定增量。实测低负载、Tick=5 ms 时约 **100.5 条远端消息/执行回复**，与这种放大相符。三副本输入 3,000 条/秒也达到约 10.5 条/回复。

这里应区分两种差异：全体广播是当前协议要求，不能直接照搬 thrifty；为每个实例持续排队完整 Data/Ack 则是候选的传播实现选择。协议要求决定最终传播和缺失数据可获取，并不要求所有副本无条件互传完整内容。减少重复传输仍须保留协调者中途崩溃后的传播能力。

### 每条消息：更大的内容、更贵的编码、更多写调用

作者实现使用固定布局二进制，快路径未改变属性时只回复实例编号 `PreAcceptOK`，给已持有命令的副本发送 `CommitShort`；它们仍通过实例和连接上下文关联正确状态。baseline 使用统一 JSON Message，PreReply 附带完整 Init，Learn 同时附带 Init 和 V，其中又各有一份命令。[消息编码](https://github.com/efficient/epaxos/blob/791b115669fca472d3136f6a2eda46c00b3f8251/src/epaxosproto/epaxosprotomarsh.go)

直接调用两边实际编码函数，取单条独立 Put 的代表性消息，结果如下。字节数包含各自应用帧头，未计 TCP/IP 和 baseline 的 TLS；原实现固定五项依赖、整数键值，baseline 七项依赖、字符串身份与 16 字节 value，因此这是实际消息形式对比，而非保持字段不变的编码格式对比。

| 消息用途 | EPaxos 作者实现（字节） | baseline（字节） |
|---|---:|---:|
| PreAccept | 59 | 331 |
| 无冲突快速回复 | 5 | 380 |
| 决定通知 | 41，CommitShort | 450，Learn |

同机、同一 Go 1.25.8、单 CPU 的 PreAccept 微测，每项重复三次取中位数：

| 编解码对象 | 编码（微秒/条） | 解码（微秒/条） |
|---|---:|---:|
| 作者原始结构与二进制编码 | 0.152 | 0.198 |
| 同一作者结构改用 JSON，仅作格式对照 | 0.858 | 6.242 |
| baseline 实际结构与 JSON | 2.156 | 12.353 |

同字段 JSON 对照说明，差异不全来自 baseline 字段更多；编码方式本身也增加明显成本。微测不含网络、TLS、队列或共识状态处理，不能把解码耗时倍数当作系统吞吐倍数。原实现的字段范围和解码检查也更简单。

作者的 `SendMsg()` 将 RPC 类型和消息体写入 bufio 后 Flush 一次；baseline 分别将四字节长度头和 JSON 消息体直接写入 TLS，形成两次 Write。客户端也不同：作者在每副本一条二进制连接上流水发送，约每 100 次请求刷新；我们的负载器复用 HTTP 连接，但每个并发请求仍经过 HTTP 请求/响应处理。这些都没有要求把多条命令合为一个共识实例。[副本发送](https://github.com/efficient/epaxos/blob/791b115669fca472d3136f6a2eda46c00b3f8251/src/genericsmr/genericsmr.go#L324)、[客户端发送](https://github.com/efficient/epaxos/blob/791b115669fca472d3136f6a2eda46c00b3f8251/src/client/client.go#L150)

### 本地推进：作者实现没有“每 Tick 最多执行调度 64 个键”的限制

作者 `executeCommands()` 在独立 goroutine 中连续扫描尚未执行的实例，只在一轮没有执行任何命令时休眠 1 ms；有现成工作时继续推进。baseline 的决定先标记 dirty，再等待 Pulse 的固定 64 键预算。前述 Tick 对照已直接验证后者造成吞吐和排队延迟，而不只是源码上的猜测。[执行循环](https://github.com/efficient/epaxos/blob/791b115669fca472d3136f6a2eda46c00b3f8251/src/epaxos/epaxos.go#L429)

作者客户端接入先进入容量较大的 ProposeChan；baseline 与协议处理共享四个许可，瞬时争用就拒绝。两者的过载策略不同。此外，作者 SCC 遍历复用实例中的 Index/Lowlink 和栈；baseline 每个键的执行检查新建图、索引和分量 map，即使该键只有一条独立命令。后一点已从源码确认，尚未单独测量其吞吐贡献，优先级低于已有直接证据的调度、消息放大和传输成本。

**结论：当前差距主要体现为每完成一条独立命令付出了更多工作，并且执行推进受固定周期预算限制。**协议的广播与投票要求、成员数和 CPU 配置确有差异，但不能解释掉上述实现开销。优先验证执行调度、后台重复传播、消息编码与写入合并，再判断剩余协议成本；不需要先用共识 batch 掩盖这些成本，也不能根据本节直接推算优化后一定达到论文吞吐。
