候选提交 `1d23b52`，使用 `gpt-6.2-sol/high`，生成耗时 57 分 50 秒。15 个 Go 功能文件共 3,643 行，扣除空行和仅含行注释的行后为 3,386 行；baseline 04 同口径为 2,970 行。Forge 首轮审计运行约 9 分 45 秒后被内容审查中止，未提交正式报告，控制器结束本次流程。以下区分生成者自测、审计已执行的负载及对原始 v000 的独立复测。[候选设计](../../../../experiments/20261118T062134Z-sol62-high-forge-1118-01-46is0eo4/candidates/v000/DESIGN.md) · [审计状态](../../../../experiments/20261118T062134Z-sol62-high-forge-1118-01-46is0eo4/audits/000/runs/2026-11-18_15-19-27-consensus_system-audit/run.json)

## 1. 实现与生成过程

- **副本间通信。** v000 每个目标副本有一个持久 TCP/TLS writer，按配置的成员公钥认证对端。writer 从三类队列取已就绪的消息，最多 16 条同帧，每条连接复用 Gob 编解码器；发送下一帧无需等待逐帧应用层回复。客户端使用 HTTP/JSON。baseline 04 也用 Gob，但每个副本间 HTTP POST 重新创建编解码器，同一条发送队列要等 HTTP 回复。两版都按键分配协议 worker，同键串行，不同键可以在同一协议阶段并行。[v000 传输](../../../../experiments/20261118T062134Z-sol62-high-forge-1118-01-46is0eo4/candidates/v000/transport/tcp.go) · [baseline 04](../1118-baseline-04/README.md)
- **普通票与恢复。** 首次观察只在建议依赖和序号不同于初始值时附带建议，快票不回传命令或完整初始值。协调者按副本去重，达到 Collect 门槛后，只要初始任务仍有效就继续接收快票；慢路径合并不匹配回复。受控测试覆盖小门槛两阶段收集、循环依赖、恢复继承和部分 Learn 广播后的决定传播。七进程冒烟测试中，跨入口读写、已执行请求重试和停三个副本后的新操作均通过。我对归档源码副本重跑了普通 Go 测试和 race 测试，均通过。这些检查覆盖了具体路径，未独立裁定协议的全部性质。[协议代码](../../../../experiments/20261118T062134Z-sol62-high-forge-1118-01-46is0eo4/candidates/v000/consensus/protocol.go) · [测试](../../../../experiments/20261118T062134Z-sol62-high-forge-1118-01-46is0eo4/candidates/v000/tests/node_test.go)
- **agent 确实用测量做了选择。** 它保留了两条失败的受控测试记录，分别修正了冻结虚拟时间时等待新读请求、以及假定只有初始协调者能决定的测试前提。它还做了 CPU、堆剖析和通告策略对照。索引布局调整后，入口副本堆从约 148.3 MiB/44,244 个已完成实例降至 83.5 MiB/49,361 个实例。把主动传完整数据改为发可用性通告后，一个 32 客户端短测的编码量从 2.98 降至 2.82 kB/请求，完成数同时从约 7.67 万降至 7.12 万。设计记录给出的保留理由是减少重复数据和暂存副本。[自测数据与取舍](../../../../experiments/20261118T062134Z-sol62-high-forge-1118-01-46is0eo4/candidates/v000/tests/RESULTS.md)

## 2. 客户端吞吐

生成者的测试为七进程、单入口、独立键、约 75% Put 和 25% Get。使用 32 个闭环客户端，负载持续 6 秒。入口有两个 Go P，配置 1 / 2 个 worker 时分别完成 13,295 / 13,797 条/秒；另一次相同设置两者几乎持平。Go trace 中两个不同 Go P 上的 PreReply 处理有 5,275 段重叠，合计 3.36 ms。这是普通协议阶段确实并行的证据，尚未显示可重复的扩 worker 吞吐收益。[测试明细](../../../../experiments/20261118T062134Z-sol62-high-forge-1118-01-46is0eo4/candidates/v000/tests/RESULTS.md) · [重叠区间](../../../../experiments/20261118T062134Z-sol62-high-forge-1118-01-46is0eo4/candidates/v000/tests/results/trace/overlap.json)

独立复测使用 baseline 04 的固定速率驱动，适配请求字段和 OK 返回语义。每轮重启七个进程，向随机入口发送独立键、16 B 值的 Put，持续 30 秒，不重试。每副本绑定一个 vCPU、一个 Go P、四个 worker，驱动占第八个 vCPU。n=7、f=4、s=1、e=1、W=200 ms。v000 各 worker 的接纳与等待上限均取 1,024，每副本 HTTP 入口总上限 4,096，出站队列容量 4,096。两版的分片限额、队列职责与默认维护定时器并不完全相同。吞吐按发送窗口内客户端实际收到的正确执行回复计算。

单看 4,500 档，v000 两次共发出 270,000 条请求，全部得到正确执行回复，七个副本的执行计数都对上；全量平均延迟为 1.40 / 1.55 ms，P99 为 14.75 / 15.89 ms。baseline 04 在同档已出现严重积压，驱动达到在途上限，两次实际发出 171,620 条，最终仅 114,727 条收到执行回复。7,000 档 v000 两次发出的请求也都最终完成，但 P99 已升至 274 / 425 ms，第二次最后五秒只完成 6,584 条/秒。在收尾快照中，两次最慢副本分别比本次实发数少执行 219 和 569 条；该快照只等到各初始协调者执行完，不代表其他副本最终不会执行。另试 10,000 条/秒时，首轮因整机可用内存低于 1,100 MiB 触发测试驱动的保护，未取得完整窗口数据，未进行第二轮。[复测汇总](jobs-summary.csv) · [五秒窗口](jobs-windows.csv)

## 3. 客户端已完成，后台通告仍有积压

每个副本在登记实例和学习决定时各产生一条可用性通告。健康副本通常已经从直接 PreAccept/Learn 收到所需数据，因此通告可以落后而不拖住当次客户端回复。在本次配置中，后台 tick 为 10 ms，每个 worker 每次对每个目标最多取 12 条通告。四个 worker 即使每次都取满，向一个目标的上限也只有约 4,800 条通告/秒；以每条新命令产生两条通告计算，相当于约 2,400 条命令/秒。该上限只针对后台通告流。[通告调度](../../../../experiments/20261118T062134Z-sol62-high-forge-1118-01-46is0eo4/candidates/v000/consensus/gossip.go) · [入队点](../../../../experiments/20261118T062134Z-sol62-high-forge-1118-01-46is0eo4/candidates/v000/consensus/data.go) · [决定通知](../../../../experiments/20261118T062134Z-sol62-high-forge-1118-01-46is0eo4/candidates/v000/consensus/protocol.go)

另跑一次 4,500 条/秒、30 秒的诊断，仅给每个 worker 增加通告序号与确认进度之差的观察计数。实际发出的 134,999 条请求全部收到正确回复，七个副本均已执行 134,999 条。停止输入约 0.4 秒时，每个副本到固定下一成员的未确认通告仍有 **178,138～179,554 条**；停止输入约 **61 秒后**，首次采到所有 worker 对所有远端成员均已追平。这里积压的是登记和决定的可用性通告，不是同样数量的未决定、未执行命令。若持续以超过该通告速率接纳请求，后台记录会继续积累，慢副本也可能更晚获知此前未见的实例。后一个影响还需要单独的延迟副本场景验证。[通告时间序列](gossip-observation.csv)

因此，这次 Forge 初次交付在独立键普通路径上优于 baseline 04，也留下了由剖析推动实现调整的证据。最值得继续审阅的是客户端完成率和后台追赶能力的分离：六秒自测足以观察协议阶段并行，未揭示后台通告的生产速率已超过发送速率。两版各来自一次独立生成，性能差异体现这两个实现的实际行为，尚不能单独归因于提示词。
