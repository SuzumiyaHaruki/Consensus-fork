# 11 月 18 日 baseline 的网络实现与吞吐量

`gpt-6.2-sol/high` 在 42 分 11 秒内正常交付。七副本固定速率测试中，2,500 条/秒的两次 30 秒运行均完成全部 75,000 条独立键 Put。3,000 条/秒开始出现明显的运行间波动，4,500 条/秒下两次都出现后段吞吐下降。交付含 3,339 行 Go 功能代码和 814 行 Go 测试及负载工具代码（物理行）。在最终源码副本上重新运行 `go test ./... -count=1` 通过。

## 网络连接和编码

| 通信路径 | 最终实现 |
|---|---|
| 客户端到入口副本 | HTTP POST，命令和应用结果均使用 JSON。每个服务进程默认最多同时处理 512 个请求，超出时在接纳前返回 REJECTED。 |
| 副本到副本 | 每个副本为其他六个成员各设一个 writer，按需建立可复用的 TCP 连接。TLS 1.3 双向验证成员证书。每个方向独立发送，同一方向按顺序写帧，发下一帧无需等上一帧的应用层确认。协议投票和库存确认仍分别处理。 |
| 副本消息编码 | 帧头是 4 字节大端长度，消息体是标准库 JSON。发送端将两部分合并后调用一次 TLS Write。一般协议消息各占一帧，后台传播可把最多 128 条实例通告装入一条库存消息。每个共识实例仍只有一条客户端请求。 |

用交付版的 Message 类型构造一条 16 字节值的独立键 Put。在给定的示例编号和七维依赖向量下，PreAccept 为 **337 B**，PreReply 为 **221 B**，Learn 为 **500 B**（含帧头，不含 TLS）。Learn 同时编码初始值和决定值，示例中同一命令出现两次。这里是按真实类型编码的样例，各类消息在实际流量中的占比未单独采集。[传输实现](../../../../baseline/experiments/20261118T012229Z-sol62-high-baseline-1118-02-2o7gdavh/workspace/transport/tcp.go)、[编码样例](wire-size.txt)

生成 agent 实际比较了两种后台传播方式。其 8 秒闭环记录中，1 worker、48 客户端下，5 ms 周期主动重发完整值的版本发送 53.3 KB/完成请求，20 ms 周期发送紧凑库存、按需 Fetch 的版本降至 21.3 KB，发送窗口内的执行回复从 23,826 增至 39,174。对照同时改变了传播内容和周期。交付材料中没有 JSON 与二进制编码的同条件对照。[生成阶段的原始分析](../../../../baseline/experiments/20261118T012229Z-sol62-high-baseline-1118-02-2o7gdavh/workspace/VALIDATION.md)

## 最终版本的固定速率测试

本机 8 个 vCPU，Go 1.25.8，七个副本各占一个 vCPU、GOMAXPROCS=1，负载器占第八个。私有回环网络，n=7、f=4、s=1、e=1、W=200 ms，worker=4、tick=5 ms、每入口 queue 和 inflight 均为 4,096。每次重启集群并待服务就绪，从空 KV 开始，不注入故障。按固定速率随机选择入口发独立键 Put，值为 16 字节，无客户端重试。每档两次、每次发送 30 秒，每请求等待上限 15 秒。

| 输入（条/秒） | 30 秒窗口执行回复（条/秒，两次范围） | 最后 5 秒执行回复（条/秒） | 最终收到执行回复 / 实际发出（两次合计） | 接纳前拒绝 | 客户端超时 |
|---:|---:|---:|---:|---:|---:|
| 1,500 | 1,499.9～1,500.0 | 1,500 | 89,999 / 89,999 | 0 | 0 |
| 2,500 | 2,499.8～2,499.9 | 2,499.4～2,499.8 | 150,000 / 150,000 | 0 | 0 |
| 3,000 | 2,800.5～2,999.6 | 1,937.0～3,023.8 | 177,824 / 179,999 | 2,175 | 0 |
| 4,500 | 2,170.8～2,263.2 | 1,087.6～1,223.6 | 137,843 / 270,000 | 125,614 | 6,543 |

窗口吞吐按客户端在发送期收到且校验了返回值的 APPLIED 回复计算。最终回复计数包括收尾期。1,500 和 3,000 档各有一条计划请求未发出。2,500 档全量客户端平均延迟为 2.16～2.25 ms，P99 为 16.79～17.17 ms。3,000 档的 2,175 次拒绝全部来自同一次运行，另一次实际发出的请求全部完成，但 P99 已达 163 ms。

4,500 档两次的前 5 秒仍有 4,480.6～4,495.0 条/秒。随后入口等待执行回复的 HTTP 请求达到上限，全部 125,614 次拒绝都报告 `HTTP request limit`。其余 144,386 条请求均被接纳，收尾时七个副本分别执行了各次运行的全部已接纳请求，其中 6,543 条在客户端 15 秒的等待期内没有返回执行结果。负载器完成全部计划发送，但高负载时发送调度延误的 P99 达 82～109 ms，局部输入存在抖动。

按“开始发压前至收尾采样的全群发出量 / 接纳数”计算，2,500 档约 **83 帧、24.25 KB/条**，4,500 档升至 **195～237 帧、73.82～87.24 KB/条**，包含重试、取数和后台传播，不含 HTTP 和 TLS 开销。高负载两次各记录约 62～64 万次 Fetch 广播，以及约 1,149～1,661 万次本地或传输队列投递失败。源码中缺失初始值或已获通告但缺少决定时会广播 Fetch，缺失持续时会重试。计数说明过载时每条已接纳命令引起的通信工作显著增多。触发积压的各项因素和 JSON 自身的 CPU 占比尚未单独测量。[逐次统计](summary.csv)、`baseline-throughput-1118`

## 原生混合读写负载及与上次实验的区别

另用最终二进制，将 agent 自带的七进程闭环测试从 8 秒延长到 30 秒，一次运行。48 个客户端收到回复后再发下一条，在 2,048 个键中混合 Put/Get/Delete，各副本 2 workers、GOMAXPROCS=2，全群与负载器共享 8 个 vCPU。前 15 秒为 **4,295 条/秒**，后 15 秒为 **3,560 条/秒**，全程约 **3,928 条/秒**。发送期间完成 117,829 条，收尾再完成 48 条，零拒绝、零超时。生成阶段报告的约 4,980 条/秒对应较早代码的 8 秒样本。闭环遇到延迟会自然降低输入，这与上表持续发压是不同的测量。[最终代码 30 秒复测](native-30s.jsonl)

11 月 17 日 baseline 也采用持久 TLS/TCP 和 JSON，当时分两次写帧头与消息体，本次合并为一次写入。在相近的七副本随机入口独立键测试中，上次 1,500 档平均延迟为 4.79～4.82 ms，本次为 1.37～1.71 ms。上次 4,500 档发送期吞吐达 4,387～4,403 条/秒，显著高于本次。两次使用了不同的模型、协议与生成材料，预热和实现内部限额也有差异。这是两份实际交付的比较，无法单独归因于模型、提示词或编码方式。[11 月 17 日测量](../1117-baseline/README.md)
