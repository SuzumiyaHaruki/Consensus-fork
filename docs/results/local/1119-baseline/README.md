## 交付与自测

这次材料要求提供七成员配置示例，允许按 CPU 和合法协议参数选择压测规模。agent 提供了七成员配置，用三、七个真实进程分别验证了服务操作和停止 0 号副本后的恢复，两组存活副本最后各执行 19 个实例。受控测试检查了两阶段收集、迟到 NACK、恢复继承已接受值、跨入口重试和冲突环；其中一个测试用 72 个写请求、5 个键检查同一实例的决定是否一致，以及每对已决定冲突实例之间是否至少有一个方向的依赖。生成期间还调整了心跳序号记录和初始数据未齐时的消息处理，随后通过普通测试、重复运行、race 检查和 vet。此次在独立源码副本上重跑 `go test -count=1 ./...` 通过。[受控测试](../../../../baseline/experiments/20261119T044618Z-sol62-high-baseline-1119-01-hul25vbo/workspace/tests/node_test.go) · [真实进程测试](../../../../baseline/experiments/20261119T044618Z-sol62-high-baseline-1119-01-hul25vbo/workspace/tests/local.py)

agent 的性能自测用三个副本，每副本 `GOMAXPROCS=2`，驱动和副本共享 8 个 vCPU。均衡入口、256 个可重复选取的键、32 B 值、24 个闭环客户端，每段 4 秒。1 worker 两段完成 2,892、2,788 条/秒，4 workers 完成 2,690、2,801 条/秒，各段均排空。四个 worker 时观测到两个不同分片的 PreAccept 处理区间重叠；计数器记录了处理函数的进入和退出，不能据此算出两个核心同时计算了多久。单一热点键的两次测量只有 532、536 条/秒，约八成请求被接纳前拒绝；这组同时把每副本在途上限从 512 降到 12，也改变了客户端数和等待阈值，因此不足以单独量出冲突成本。[agent 的完整测量](../../../../baseline/experiments/20261119T044618Z-sol62-high-baseline-1119-01-hul25vbo/workspace/PERFORMANCE.md)

## 固定速率复测

每个档位从全新集群开始，预热 70 条。每个客户端请求是不同键的 Put，值 16 B，无重试，客户端等待执行回复。三副本均衡轮流接入，参数为 `f=1,s=0,e=0,W=80ms`，每副本固定两个 vCPU，驱动固定其余两个。七副本随机接入，参数为 `f=4,s=1,e=1,W=200ms`，每副本固定一个 vCPU，驱动使用第八个。三副本的快路径需三票，七副本需六票。各档均用四个协议 worker、每入口最多 512 个已接纳未执行实例。表中吞吐仅计发送窗口内收到的正确执行回复；P95 使用实际发起至收到结果的时间，过载档只覆盖有执行结果的请求。客户端不重试 `INCOMPLETE`。每次停止新请求后等所有已发请求返回或超时，并额外观察各副本执行计数至追平或约 3 秒到期。

**同一速率延长到一分钟，会改变结论。** 三副本 2,500 档的长测前 45 秒基本跟上，到最后 5 秒只有 1,563 条/秒。各副本最终执行了全部 141,018 条已接纳请求，其中 76 条在服务器等待期限内未给客户端返回执行结果。七副本 1,500 档的长测实际发了 90,000 条，接纳 69,229 条；收尾时各副本执行了 64,246～65,621 条。这里观察到过载期间的拒绝、等待和积压；要认定某个已接纳实例永久无法推进，还需要追踪该实例。驱动器在各档均未触及在途保护上限，个别测量有 2～6 条计划请求在发送窗口关闭前没有发出。[逐档汇总](jobs-summary.csv)

**与上次的七副本对照。** 在相同副本数、CPU 绑定、worker 数、协议参数、入口分布、负载和 30 秒时长下，上次 04 在 2,000 档两次完成 1,999、1,997 条/秒，当前候选一次为 1,666；2,500 档上次为 2,450、2,250，当前为 1,340、1,436。两代的 API、接纳策略和入口等待设置有差异。可以判断新实现的七副本端到端吞吐在这两个档位退化；三副本与七副本的数字不能单独衡量副本数的影响，因为每副本 CPU 预算、入口分布和协议参数也不同。[上次的原始汇总](../1118-baseline-04/jobs-summary.csv)

## 成本来自哪里

1. **短票被通用消息的编码成本放大。** 客户端使用 HTTP/JSON。副本间从上次的 HTTP/Gob 改为 UDP/Gob。每副本只有一个发送 goroutine 和一个接收 goroutine，各自负责所有对端；每条出站消息重新创建 Gob 编码器。用交付的真实消息类型编码一张 `FastOK`，正文为 682 B，加上自定义帧头为 694 B。诊断时用同一 Gob 流连续编码相同消息，第二条仅新增 44 B。这量出了类型说明的开销；独立 UDP 数据报若要引用共享编码状态，还得处理丢包、乱序等问题。[传输代码](../../../../baseline/experiments/20261119T044618Z-sol62-high-baseline-1119-01-hul25vbo/workspace/transport/udp.go) · [编码样例与测量](evidence.tar.gz)
2. **每个副本都会向其他副本重复传播已知数据。** 一个副本登记实例时将完整初始数据写入自己的传播日志，学到决定时再追加一条决定记录，后台向每个其他成员逐页发送并确认。全员追平时，仅这两种记录，每个实例在三副本部署对应 12 次记录投递，七副本对应 84 次。按页打包会减少包数；这里数的是记录副本。协议要求最终补齐数据，但当前实现也对已从前台消息取得相同数据的成员做这些工作。[写入初始数据与决定](../../../../baseline/experiments/20261119T044618Z-sol62-high-baseline-1119-01-hul25vbo/workspace/consensus/data.go) · [后台分页传播](../../../../baseline/experiments/20261119T044618Z-sol62-high-baseline-1119-01-hul25vbo/workspace/consensus/background.go)
3. **过载会增加每个已接纳请求的实际成本。** 三副本 2,500 档 20 秒共发送约 8.48 kB UDP 数据/已接纳请求，5,000 档两次为 17.43、22.48 kB，8,000 档为 37.75 kB，含收尾和重试。七副本 2,000 档，前 15 秒各副本合计约用 4.8～5.6 个 vCPU，末段约 6.9 个，同期传输丢弃计数单个采样间隔增加超过 220 万次。这个计数包括本地收发队列满等事件，不能换算为链路丢包数。三副本 5,000 档保持四个 worker 和相同绑核，只把每进程 Go P 从 2 降到 1，窗口吞吐降至 896。增加 P 对整机吞吐有实效，其中包含共识处理、传输和运行时工作。[计数、CPU 采样与压测脚本](evidence.tar.gz)

候选的冲突测试在所测调度下没有发现相互矛盾的决定。独立吞吐复测检查了 Put 回复和副本执行计数，没有逐一比对同一实例在各副本的完整决定值。已定位的工程问题是短测掩盖了持续输入下的退化、编码存在固定开销、后台传播重复，以及过载后单位请求流量上升。持续发送独立键还同时增加了键数和保留的实例数；没有单独替换编码或传播策略，也没有隔离历史和 GC 的影响，无法把吞吐下降按原因分摊。
