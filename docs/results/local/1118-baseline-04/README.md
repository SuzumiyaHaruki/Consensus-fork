## 统一口径复测

复用 03 的固定速率客户端，适配 04 的 48 字符会话 ID、`client_id` 字段和 `RESULT` 回复。每轮从空集群开始，在隔离回环网络中向随机入口发送独立键 Put，值为 16 B，不重试，持续 30 秒。七个真实副本各绑一个 vCPU、各用一个 Go P 和四个 worker；驱动独占第八个 vCPU。两版使用相同的两个入口随机种子和 n=7、f=4、s=1、e=1、W=200 ms。04 样例本来是 f=3、W=100 ms。04 的 HTTP 入口并发上限为每副本 4,096，03 的 Node 等待者上限为 512；两版的传输、调度和后台维护也不同。

| 目标输入（条/秒） | 03 窗口吞吐（条/秒） | 04 窗口吞吐（条/秒） | 04 最后五秒吞吐（条/秒） | 04 最终执行回复 / 实际发出，两次合计 |
|---:|---:|---:|---:|---:|
| 2,000 | 未测 | 1,999 / 1,997 | 2,000 / 1,990 | 119,999 / 119,999 |
| 2,500 | 2,500 / 2,500 | 2,450 / 2,250 | 2,238 / 1,015 | 144,779 / 150,000 |
| 3,000 | 3,000 / 3,000 | 2,203 / 2,089 | 185 / 160 | 136,564 / 161,530 |
| 4,500 | 4,356 / 4,300 | 1,805 / 1,928 | 255 / 318 | 114,727 / 171,620 |

窗口吞吐按发送期内收到的正确执行回复计算。2,000 档有一条计划请求未发出，两次所有实际请求都拿到正确结果，各副本的应用计数也与请求数一致。全量平均延迟分别为 13.69 和 14.24 ms，P99 为 71.38 和 80.32 ms。2,500 档前一次最终全部完成，后一次有 5,221 条请求在客户端等到 15 秒超时。两次 3,000 档在发送结束时分别有 16,383 和 16,384 个客户端请求等候回复，驱动达到在途上限，因此实际发出量低于计划量。客户端逐请求等 15 秒；观察结束时仍有本地已接纳实例未执行。有限的观察支持“过载且未排空”，不能据此判定永久不执行。**这组 30 秒测试中，04 能重复跟上约 2,000 条/秒，2,500 已进入退化区；03 能重复跟上 3,000。**

## 吞吐为何下降

**快票的内容变小，传输的固定成本变大。** 03 直接在持久 TLS/TCP 流上复用 Gob 编解码器。04 副本之间使用支持连接复用的 HTTP POST，以 HMAC 验证消息来源和内容。每个目标分三条发送队列，各自取最多 24 条组成一帧；同一队列等上一个 HTTP 回复后再发下一帧。每个 POST 都重新创建 Gob 编码器和解码器，重新传送类型信息。用双方实际 Go 类型构造同样数量的独立 Put 快票，得到下表。字节数为整帧 Gob 内容，未计 HTTP 头、HMAC 头或 TLS。[04 传输源码](../../../../baseline/experiments/20261118T051743Z-sol62-high-baseline-1118-04-xhwvhn4_/workspace/tcp/transport.go)

| 同帧快票数 | 03 常态，复用 Gob（B/帧） | 04 实际，每帧重建 Gob（B/帧） | 04 同一消息，假设复用 Gob（B/帧） |
|---:|---:|---:|---:|
| 1 | 177 | 741 | 54 |
| 8 | 1,375 | 1,086 | 399 |
| 24 | 4,111 | 1,870 | 1,183 |

在三个样本中，04 的新编码器都增加 687 B/帧。单独发送一张短票时，这笔成本超过了字段精简的收益；八张或更多同帧时，这组选定样本的 04 帧已经小于 03。实际流量里快票会和其他消息混合，以上数据解释了固定成本，不能直接换算为整机吞吐差额。

**过载后，大量工作花在重复取数和恢复上。** 04 的 2,000 档两次均没有 Fetch 发送和发送队列满，七进程合计已占用约 5.8 核。3,000 档两次分别成功排队约 164 万和 143 万条 Fetch，另有约 9,661 万和 1.02 亿次各类消息的发送入队失败。一次独立计数复测把失败按消息种类分开：`NeedRecover` 占 34.7%，`Prepare` 占 26.3%，`Fetch` 占 23.3%，三者合计 84.3%。这些是本地发送队列拒绝的尝试次数，不是同样数量的 TCP 包或失败的客户端命令。统计包含请求发送结束后的追赶期；这解释了退化后资源花在哪里，尚未单独量出 HTTP 等待、Gob 编解码和后台传播各自对首次饱和的贡献。

**收紧入口并发有帮助，但没有消除差距。** 保持队列容量和协议代码不变，仅在诊断副本中把 HTTP 入口上限从 4,096 改为 512。在同样的 3,000 档，两次窗口吞吐从 2,203 / 2,089 提高到 2,305 / 2,330 条/秒，客户端超时从 11,872 / 13,094 降到 1,122 / 1,803；代价是分别出现 17,259 和 16,526 次接纳前拒绝。两次已接纳请求在收尾时都已在各副本应用，末五秒吞吐仍只有 322 / 338 条/秒。03 的等待者限制在 Node 层，这个对照检验的是 04 对入口并发的敏感性。

这轮支持两个判断：新协议把首次投票写清楚后，04 给出了符合这项要求的简洁表示；整体性能仍取决于编码器的生命周期、发送并发和过载时对已有工作的处理。agent 的短测证明能完成请求，也观察到了真实并行，但没有测出随机多入口下的持续负载转折。两次独立生成同时改变了多项机制，无法把整机差距归因于某一条提示词。
