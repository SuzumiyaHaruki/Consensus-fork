# 四份初始实现的吞吐诊断（2026-11-17）

**这四份交付实现目前确实处在几百至几千条/秒的量级。主要原因已经定位到消息数量、HTTP/JSON 成本，以及过载时的数据处理放大，不是单纯缺少 batch 或 K 太小。**本机表现最好的是 1111 v000：三副本短测约 2,800 条/秒，另以 2,000 条/秒连续运行 30 秒，60,000 条请求全部执行并回复。

## 1. 对象与方法

对象是桌面 1111、1113 测试包中的两个 baseline 和两个 v000。1111 v000 为 `a49b2c8`，1113 v000 为 `10f4310`，详细来源见 [origins.json](origins.json)。这些都是删除 K/carry 前的交付代码；本次不测试 v003，不修改候选的共识或执行算法。

本机八个虚拟 CPU、约 12 GiB 内存，Go 1.25.8。四份实现使用相同负载器和资源分配：独立进程、随机入口、独立键 Put、16 字节 value、无 batch、无故障，K=64、W=200ms、worker=4、队列上限 4,096。客户端请求仍包含 key、rid 和 JSON 字段，并非完整命令只有 16 字节。每项重新启动集群、预热并等待各副本执行，再开始发压。

七副本各绑定一个虚拟 CPU、Go P=1，负载器使用剩余一个；三副本各绑定两个虚拟 CPU、Go P=2，负载器使用剩余两个。七副本参数 f=4/s=1/e=1；三副本为 f=1/s=0/e=0。成员使用不同回环 IP，保留 1113 baseline 的源 IP 身份检查；会话身份长度满足四份实现的要求。

共 61 项有效运行：七副本扫描 32 项、三副本扫描 12 项、单独剖析 8 项、关闭观测对照 4 项、持续负载 5 项。短测发送 8 秒、收尾最多再等 8 秒；持续负载发送 30 秒、收尾最多再等 10 秒。**吞吐是发送期间的执行回复数/发送时长；回复比例包含收尾等待，以实际发出的请求为分母。**少量漏发保留在 CSV 的 not_sent 字段，不把目标输入速率当作实际吞吐，也不把截止未回复直接认定为永久失活。

## 2. 四份实现到底有多快？

### 七副本、每副本一个虚拟 CPU

每格为 **吞吐（条/秒）；执行回复比例**，吞吐取两次中位数，比例按两次请求合计。

| 实现 | 输入 300 条/秒 | 输入 800 条/秒 | 输入 1,500 条/秒 | 输入 3,000 条/秒 |
|---|---:|---:|---:|---:|
| 1111 baseline | 299.8；100.0% | 799.2；100.0% | 97.5；6.9% | 74.9；2.7% |
| 1111 v000 | 300.0；100.0% | 800.0；100.0% | 1,499.9；100.0% | 939.1；59.9% |
| 1113 baseline | 299.7；100.0% | 440.4；55.7% | 49.9；3.9% | 34.1；1.5% |
| 1113 v000 | 299.0；100.0% | 427.6；53.5% | 28.7；1.9% | 6.6；0.2% |

这里存在明显的过载退化：提高输入后，完成速度反而下降。1111 v000 在 1,500 条/秒下两次均完成所有请求；1111 baseline 能跟上 800 条/秒；两份 1113 实现在 800 条/秒已经积压。因此不能把“输入 3,000 时只完成几十条/秒”解释成它在所有负载下都只能处理几十条。

### 三副本、每副本两个虚拟 CPU

每格含义相同，每组合一次。此组改变了成员数和每副本资源，用于检查减少消息量、增加每副本 CPU 后的表现。

| 实现 | 输入 800 条/秒 | 输入 3,000 条/秒 | 输入 8,000 条/秒 |
|---|---:|---:|---:|
| 1111 baseline | 799.4；100.0% | 178.0；8.5% | 244.9；4.0% |
| 1111 v000 | 800.0；100.0% | 2,778.2；100.0% | 2,707.8；53.0% |
| 1113 baseline | 798.6；100.0% | 58.0；2.6% | 53.8；0.9% |
| 1113 v000 | 798.1；100.0% | 8.6；0.3% | 7.5；0.1% |

减少副本并增加每副本资源，确实提高了可承受负载，但没有使任何一份实现达到数万条/秒。1111 v000 在输入 3,000 时，发送期完成约 2,778 条/秒，剩余请求在收尾完成；输入 8,000 后仍约 2,708 条/秒且出现积压，已经测到了该配置下的饱和区间。

### 连续运行会不会继续下降？

下面均为三副本、每副本两个虚拟 CPU。

| 实现 | 800 条/秒持续 30 秒：吞吐（条/秒） | 执行回复 / 已发出 |
|---|---:|---:|
| 1111 baseline | 799.8 | 24,000 / 24,000 |
| 1111 v000 | 800.0 | 24,000 / 24,000 |
| 1113 baseline | 407.8 | 12,409 / 24,000 |
| 1113 v000 | 798.9 | 24,000 / 24,000 |

1113 baseline 的每五秒吞吐依次为 **798.2、800.0、780.4、50.0、11.0、7.4 条/秒**：8 秒短测通过，并不代表持续运行能维持该速率。

1111 v000 另以 2,000 条/秒连续运行 30 秒，实际发送和完成均为 60,000 条，发送期吞吐 1,999.9 条/秒。每五秒吞吐约为 2,000，没有持续下滑；全量平均客户端延迟 2.81 ms，P99 为 34.66 ms。这是已测到的持续处理能力，2,778 条/秒则是短测发送窗口中的吞吐。

## 3. 低吞吐的具体原因

### 每条逻辑请求对应几十次 HTTP 请求

七副本、输入 300 条/秒且全部完成时，资源成本如下，取两次中位数。HTTP 数量只计协议请求，含心跳与重传，不含客户端请求、观测接口和 HTTP 响应；分配量是累计申请量，不是常驻内存。

| 实现 | 协议 HTTP 请求 / 执行回复 | 分配量（KiB / 执行回复） | 全组 CPU 占用（核） |
|---|---:|---:|---:|
| 1111 baseline | 64.6 | 1,010 | 2.67 |
| 1111 v000 | 56.1 | 678 | 2.41 |
| 1113 baseline | 86.0 | 1,277 | 3.53 |
| 1113 v000 | 49.9 | 965 | 2.83 |

这四份被测实现采用的协议版本要求副本首次获知决定后向全体广播。因此七个副本均学习后，仅 Learn 就有 `7×6=42` 次远端发送；再加 PreAccept、回复、Fetch 和后台消息，每条应用请求需要处理几十次 HTTP 请求。**这一广播模式来自当时的协议要求，不是四个 agent 各自偶然写出了同一个问题。**后续输入材料已改为决定协调者广播、接收副本通过后台摘要与 Fetch 补齐；本报告数据仍来自修改前的实现。

每条消息又经过 HTTP 头、JSON 编解码、对象分配、队列及身份校验。应用虽然只是写一个小值，复制它的工作远比一次本地 map 写入多。1111 v000 还对每个目标副本使用一个发送循环，逐条等待 HTTP 响应，限制了同一连接方向的流水化程度。

### 三份实现过载时，把大量工作花在附带数据上

以下是七副本、输入 1,500 条/秒的独立剖析。CPU 占比包含该函数的子调用，存在调用层次重叠，不能简单相加；剖析运行没有混入前面的普通测量。

| 实现 | 实际热点 | 原因 |
|---|---|---|
| 1111 baseline | JSON 解码约 30.4% CPU；advance 约 27.1%，其中 attach 约 14.5% | 旧实例、重传和 carry 附带数据反复组装、编码与解析；分配剖析中 attach/发送相关路径占主要部分 |
| 1113 baseline | attachLocked 约 66.1% CPU、91.7% 累计分配量 | 每次发送先组装 carry 和代表的数据，再尝试进入发送队列；队列满仍付出组装成本，过载后大量工作被丢弃 |
| 1113 v000 | completeLocked 约 91.1% CPU | 对缺失的初始数据递归检查；成功结果可以缓存，但未完成的共享前驱会在多条路径中反复访问，并长时间占用状态锁 |
| 1111 v000 | 系统调用约 25.2% CPU，JSON 解码约 14.7% | 此负载下工作仍有效推进，主要成本是大量网络消息、编码与运行时处理，没有前三者那样的严重退化 |

对应位置为 1111 baseline 的 `data.go:217`、1113 baseline 的 `data.go:158`/`data.go:219`、1113 v000 的 `consensus/storage.go:63`，以及 1111 v000 的 `transport/http.go`。剖析原始文件及函数列表保存在证据包中。

1113 v000 的递归检查只用 visiting 排除当前递归路径中的环；一条分支返回后会删除标记。carry 中多个后继共享一个缺失前驱时，这个前驱会被反复走到，工作量随路径数增长。CPU 忙于反复确认“数据还没齐”，却无法及时处理使数据齐全的消息。该结构与本次 completeLocked 热点相符。

历史增长也有额外成本：1113 v000 在每次执行调度中复制、排序全部 records，已经执行的历史也在其中；输入仅 300 条/秒时，sortedLocked 已占约 9.7% CPU。1113 baseline 的维护和执行同样遍历历史表。持续负载中的退化说明不能只评估一个小规模、刚启动的集群。

### K 与测试工具分别占什么作用？

1111 v000 七副本、1,500 条/秒的一次运行中，各协调者平均占槽 **0.24～0.32**，单副本峰值 **5～11**，没有满槽。此时 K=64 并未限制吞吐。过载后槽位填满、carry 变大，则会进一步放大上述成本；因此“扩大 K”不是通用提速办法。

关闭生命周期日志及事件轮询后，在七副本、输入 800 条/秒下得到：

| 实现 | 原观测开启，两次范围（条/秒） | 关闭生命周期记录和轮询（条/秒） |
|---|---:|---:|
| 1111 baseline | 799.2～799.2 | 799.0 |
| 1111 v000 | 800.0～800.0 | 799.9 |
| 1113 baseline | 401.8～479.0 | 494.5 |
| 1113 v000 | 398.2～457.0 | 431.4 |

结果落在原来的范围附近，观测开销不能解释数量级差距。持续 2,000 条/秒时，负载器只用约 0.34 个 CPU，也未达到自身 CPU 上限。七副本主扫描期间虚拟机没有新增 swap-out；虽然记录到其他页面换入，当前证据主要指向 CPU 工作和内存分配成本，而非 RAM 容量不足。

## 4. 与 EPaxos 数万吞吐的差距

论文的无协议 batch 测试也是 KV 写入、执行后回复，但客户端批量发送请求，使用专门生成的 RPC 编码，并采用 thrifty：PreAccept/Accept 优先只联系 quorum。实验是三或五副本，每个副本独立 EC2 实例、两个虚拟核，另有客户端实例；小命令为完整 16 B。当前是逐请求 HTTP、JSON 和全体传播，七副本还具有不同的容错与快速门槛。它们不能只因“都是 KV、都没做共识 batch”就视为同样工作量。[EPaxos §6–7](https://www.cs.cmu.edu/~dga/papers/epaxos-sosp2013.pdf#page=10)

这些差异解释了比较条件，但更直接的发现是：**当前实现存在可消除的大量重复工作。**删除 K/carry 会去掉独立键之间的人为数据依赖和相关附带成本，方向正确；它不会自动消除全体 Learn 广播、逐条 HTTP/JSON、历史扫描，也不能替代对真实依赖查询的缓存与去重。

下一轮应先看新生成实现是否消除了数据组装、缺失闭包重复遍历和历史扫描的放大，再定位正常路径的消息数与传输成本。若进一步修改决定传播，应保留故障后的传播与恢复能力；不能在性能测试副本中直接删掉协议要求的消息来制造提升。本次未修改这些算法行为。

## 复现命令

`run.py` 读取桌面 `consensus-server-evaluation-1111`、`consensus-server-evaluation-1113` 的交付源码，复制到桌面 `consensus-throughput-1117` 后构建。四份实现共用 1111 测试包当前的固定速率负载器、观测层和资源配置逻辑，各自保留原有 Node、网络处理、身份检查、共识及执行代码。1113 baseline 使用其已有适配器和三个生命周期观察点，修改差异保存在构建目录的 `candidate-observation.patch`。

```bash
cd /home/nitro/Desktop/consensus-forge-vft-epaxos
python3 docs/results/local/1117-four-implementations/run.py prepare
python3 docs/results/local/1117-four-implementations/run.py run --name main7 --n 7 --rates 300,800,1500,3000 --seconds 8 --drain 8 --repeats 2
python3 docs/results/local/1117-four-implementations/run.py run --name main3 --n 3 --rates 800,3000,8000 --seconds 8 --drain 8
python3 docs/results/local/1117-four-implementations/run.py run --name profile7 --n 7 --rates 300,1500 --seconds 8 --drain 8 --profile
python3 docs/results/local/1117-four-implementations/run.py run --name quiet7off --n 7 --rates 800 --seconds 8 --drain 8 --quiet
python3 docs/results/local/1117-four-implementations/run.py run --name sustained3 --n 3 --rates 800 --seconds 30 --drain 10
python3 docs/results/local/1117-four-implementations/run.py run --name sustained-best --n 3 --versions 1111-v000 --rates 2000 --seconds 30 --drain 10
python3 docs/results/local/1117-four-implementations/analyze.py
```

`--profile` 单独采集 CPU 和分配剖析，不混入普通测量的重复结果。`--quiet` 在预热后关闭生命周期记录和负载器的事件轮询；候选事件回调仍保留，用于检查观测开销。原始事件、逐请求结果、CPU 剖析、构建日志及来源保存在桌面诊断目录；仓库保留脚本和轻量分析材料。

`scan7` 是适配预检，包含无效源地址/会话配置以及未完成诊断收尾的任务，不纳入正式分析。`main7` 及后续任务使用统一的合法地址和会话配置。首次命名为 `quiet7` 的补测漏传了开关，实际仍是普通观测，排除出对照分析；正确关闭观测的任务为 `quiet7off`，分析脚本检查其配置及测量前后的事件序号。

本机 Go 1.25.8 工具链缺少 pprof 可执行文件，剖析使用本机已有的 `/usr/lib/go-1.18/pkg/tool/linux_amd64/pprof` 读取标准 profile 文件；候选程序仍由 Go 1.25.8 构建和执行。重现本机剖析时，在分析命令前设置 `PPROF_TOOL=/usr/lib/go-1.18/pkg/tool/linux_amd64/pprof`；完整 Go 工具链可以直接使用 `go tool pprof`。
