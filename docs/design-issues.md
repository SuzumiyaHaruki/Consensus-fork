# 协议与系统设计中需要继续考虑的问题

更新日期：2026-11-02。这份文档记录我们讨论过的设计问题，方便以后逐项处理。它不作为 agent 的输入，也不改变当前实验要求。这里区分已经明确的规则、当前讨论采用的假设和仍需论证的方案；线性一致性、执行活性和运行时计时的完整方案尚未确定。

本轮暂定每个逻辑命令只由客户端提交一次，不实现客户端重试、跨节点结果查询和未完成请求恢复。该范围与执行完成后回复、拒绝和结果未知等语义已同步到 [protocol.md](../inputs/protocol.md) 第 12、14 节与 [system.md](../inputs/system.md)。副本自主恢复、命令身份和执行去重仍然保留。这些输入材料供后续生成、审计和修复使用；已准备的实验仍保留各自的输入，不按新要求追溯判错。6Delta 的等待时间讨论、时间戳方案和完整的时间与一致性保证没有作为新的实验要求。

下面有 10 类事项，但不代表协议有 10 个错误。有些是原先没想清楚、后来已经补上的规则；有些仍需要讨论；还有些是当前明确不支持的能力。判断旧实验时，要看它当时拿到的材料，不能拿后来补上的要求追溯判错。

## 1. 客户端到底能得到什么一致性保证

**当前状态：已明确讨论范围，完整保证与证明仍待确定。**

例如，客户端写入 `x = 1`，收到成功后，再向另一个副本读取 x。在没有其他写入的情况下，是否必须读到 1？如果是另一个客户端来读，保证是否相同？同一个客户端连续写两次，最终顺序如何确定？这些都属于需要明确的服务语义，不能只讨论 Get。

“所有副本最后保存相同的数据”“冲突命令在各副本上按相同顺序执行”“客户端观察到的历史满足线性一致性”是不同的要求。前两个成立，不代表第三个已经得到证明。并发操作、返回值和超时后结果未知的操作，也都需要考虑。

线性一致性可以理解为：所有操作的结果都能放进某个合法的串行执行中，而且每个操作仿佛在调用到完成之间的某一刻生效。如果 A 已经完成，B 才开始，就必须保留 A 在 B 前面的关系，不区分两个操作是否来自同一客户端。并发操作可以有不同的合法顺序，不能只凭发送先后或命令编号判错。

除写后读之外，还要看连续读取不同副本时是否倒退、并发写的结果能否用同一个顺序解释、删除及其返回值是否正确，以及超时请求后来生效时怎样解释整个历史。以后如果提供原子加一、条件更新或跨键操作，再讨论这些接口对应的原子性要求；不能把未提供的接口当作当前缺陷。

EPaxos 原文区分每个对象的线性一致性与多对象操作的严格可串行化。后者可理解为把多对象操作作为整体，既满足合法串行顺序，也尊重已经完成的操作与后来操作之间的先后关系。作者提出 EPaxos-strict：等命令及整个依赖图中的实例都 commit 后，再通知客户端。输入材料已规定“执行完成后回复”，但仍需结合自己的依赖发现、恢复和执行规则论证，不能直接继承 EPaxos 的结论。依据：[EPaxos 技术报告第 7 节](https://www.pdl.cmu.edu/PDL-FTP/associated/CMU-PDL-13-111.pdf)。

客户端序号目前用于区分命令，不自动保证执行顺序。当前只有单键 KV 操作，没有跨键事务接口。单键操作分别线性一致，不等于两次单键调用自动合成一个原子事务。

## 2. 不同客户端怎样避免使用相同的命令编号

**当前状态：设计规则已补齐，不继续作为开放协议问题扩大讨论。**

如果客户端 A 和 B 都从编号 1 开始，服务器就可能把两个不同操作认成同一条命令。现在使用 `(ClientID, RequestSeq)`：前一部分区分客户端的编号分配会话，后一部分区分这个会话里的操作。

现有规则还说明了并发调用怎样分配编号，以及客户端重启后怎样创建新会话来发送新的操作；当前不恢复或重发旧的未完成请求。编号允许有空缺，请求也允许乱序到达；服务器不能一直等待某个从未发送的较小编号。独立客户端不能复制同一个分配器后各自发新命令。实验可以直接为各客户端配置不同的 ClientID。

正常客户端正确分配编号、命令内容保持不变后，编号冲突就被排除在正常模型之外。并发分配和编码是否正确，是普通实现审查与测试的责任，不必为每一种可能的编程错误另设计协议恢复机制。随机 ClientID 的唯一性是概率保证，ClientID 也不能代替身份认证；这些边界已说明，不作为持续扩展问题清单的理由。

## 3. 非法命令被拒绝后，会不会拖累正常命令

**当前状态：接纳前拒绝规则已明确；同编号对应不同内容被正常客户端规则排除。**

例如，同一个命令编号第一次对应 `Put(x, 1)`，后来却变成 `Put(x, 2)`。副本如果已经知道第一次的内容，就应该拒绝第二次提交，并保留第一次的内容和结果。在接纳前被检查拒绝的请求，不能进入依赖图，让其他命令等它执行。

当前只需把三条规则落实正确：不同逻辑操作使用不同编号，副本传递与恢复命令时保留完整原值，副本按身份识别同一命令并保留执行状态和结果。正常的网络延迟、乱序、重复投递或接管不会自己把一份请求变成两份不同内容。

如果不同副本已经接受同编号的不同内容，那违反了现有客户端前提。全局选择哪份内容、怎样恢复受影响的服务，目前没有设计，也不把它列为当前正常流程必须解决的事项。已有正确结果仍须保留，不能用异常处理把它覆盖、删除，或把尚未执行的命令擅自当作空操作。

一般的格式或参数检查仍然有必要。在接纳前被拒绝的请求不能进入依赖图，已有正常命令也不能被一次不一致输入破坏。

## 4. 我们允许客户端怎么发送请求

**当前状态：暂定每个逻辑命令只提交一次，已同步到输入。支持多客户端并发；超时、断连或崩溃后不重发旧命令。**

副本遵守 CFT 假设，表示它们按协议运行，可能崩溃，但不会任意伪造协议行为。客户端按规则分配编号，每条命令只选择一个副本提交一次，可以同时提交不同命令。客户端超时、断连或崩溃后不换节点重发，也不把结果未知的操作换一个编号再提交。客户端崩溃不占用副本最多 f 个故障的名额；重启后可以用新会话发起新的操作，但不恢复旧的未完成请求。

只提交一次，指客户端操作接口上的提交次数，不禁止传输层重传或副本内部的协议通信。副本仍可能通过重复投递、观察、恢复查询、决定转发等路径多次获知同一命令。它们必须关联已有命令，不能重新观察、重置已有 Watchdog 或在同一副本上再次执行。客户端不重试也不能成为删除这些机制的理由。

本轮客户端主要用于提交并发负载并观察正常路径的结果，不要求保存并加载请求记录、跨节点查询结果或恢复客户端状态。真实多进程、网络、后台计时和副本自主推进仍是系统要求。允许的负载范围和过载响应还需说明，不能要求正常客户端必须让服务器定期空闲。

已有定时器测试让 16 个调用循环在成功后继续提交同一个已完成操作，并在观察回调中加入约 1 毫秒的计算。这个触发流量不符合当前单次提交模型，因此不能直接用它证明当前支持的客户端流量会触发问题。代码中无限清空队列的缺陷仍值得检查，但并发新请求等合法流量能否在承诺负载内复现，需要另外实测。旧实验仍按当时材料解释，保留原始证据，不追溯改写实验结果。

## 5. 客户端收到成功、失败或超时，分别意味着什么

**当前状态：执行完成后回复；超时只报告结果未知，不重试。副本内部恢复与客户端是否继续等待分开处理。**

一条命令要经历接纳、决定命令及依赖、等依赖准备好、执行、回复客户端。决定完成，也就是这里的 commit，不等于已经执行，更不等于客户端已经收到结果。输入材料已规定执行完成并保留结果后才回复客户端成功；执行产生的应用错误也是需要保留的确定结果。

客户端超时、断连或取消等待，不会撤销已经接纳的命令；结果可能已经产生，只是客户端不知道。当前客户端结束等待后不重试，也不查询旧结果。如果命令的完整内容从未到达任何永久存活的正确副本，目前没有相应的最终决定保证。客户端不能只凭等待了多久，就断定命令已经消失。

接纳前拒绝、执行后返回应用错误、结果未知，需要分开处理。应用错误也是要保留的执行结果。想再读一次当前值，应创建一个新的 Get 操作。每个副本只执行一次，也不意味着对外部系统的副作用只发生一次。

| 客户端收到什么 | 应当怎样理解 |
| --- | --- |
| 执行成功 | 操作已完成，结束本次调用 |
| 明确的非法请求拒绝 | 输入不合法，本次结束，不自动重发 |
| 已执行的业务失败，例如条件不满足 | 是该逻辑操作的确定结果，本次结束 |
| 明确的临时拒绝，例如接纳前过载 | 本次结束，不自动重发；接口须说明是否保证尚未接纳 |
| 超时、断连或取消等待 | 没有确定结果时报告未知；命令可能尚未开始、正在恢复或已经执行 |

以客户端向 P0 提交命令为例，共识进度与客户端结果可能不同。

| 故障位置 | 当前要求 |
| --- | --- |
| P0 崩溃，完整命令从未到达任何永久存活的副本 | 不保证最终决定；客户端可能一直不知道结果 |
| 完整命令已到达永久存活的副本，随后 P0 崩溃 | 副本在协议前提下自主恢复并推进决定，不能等客户端重发；执行还需依赖准备好 |
| 命令已执行，P0 在回复前崩溃 | 允许客户端拿不到结果，不要求换节点找回；不能仅据此认定共识未推进 |

无故障且客户端仍连接等待时，正常路径仍须执行完成后返回结果。测试可以通过存活副本的决定和执行事件观察共识进度，这不要求额外实现客户端结果查询接口。

### 以后恢复客户端重试支持时再讨论

下面保留之前的重试设计讨论，暂不作为当前实现或审计的要求。若以后恢复这项能力，重试需要保留同一份完整请求；换一个接入节点不改变原始协调者，也不能绕过协议的接管资格。

| 重试节点的本地状态 | 应有行为 |
| --- | --- |
| 完全不知道该命令 | 注册同一份原始请求，查询当前候选协调者或按合法资格推动进度 |
| 已知道但尚未 commit | 将客户端等待关联到已有命令，不重建观察、不重置已有 Watchdog、不重复启动同一流程 |
| 已经 commit 但尚未执行 | 等待依赖并完成本地执行，再返回结果 |
| 已经执行 | 返回保留的原结果，不重新执行 |

按当前协议可以推出：命令一旦合法 commit，所有仍存活的副本都应至少知道它的原始内容。Fast 要求所有成员回复或被准确判死；Seal 要求完整发送并等够传播和保存时间。这依赖当前同步、准确判死、固定成员和 crash-stop 前提，不适用于未设计的重启或网络分区场景。知道原始内容，不等于知道最终决定或已经执行。

若以后恢复重试，重试节点完全不知道命令，主要对应原请求尚未完成传播。例如原协调者只发给 P1 就崩溃，P2 尚未见过；客户端重试到 P2 时，不能推断全体都不知道，也不需要先证明全体都不知道才能继续。那时需要明确 P2 怎样通过原请求身份和查询、接管规则与 P1 已有状态汇合。

去重是每个副本对同一逻辑命令执行一次。P1 已执行而 P2 尚未执行时，P2 后续执行一次属于正常复制。以后支持重试时，还需确定客户端重试是否立即触发进度查询，以免新接收节点又等待完整 Watchdog 周期；当前不增加这项接入规则。

## 6. 已经 commit 的命令，会不会一直等不到执行

**当前状态：只对有限、最终能准备好的依赖讨论执行进度；持续冲突输入下的更强保证还没有建立。**

例如 A 依赖 B，B 又依赖其他尚未决定的命令。A 虽然已经 commit，仍然不能执行。这里把 A 直接或间接依赖的全部命令称为它的“依赖闭包”。如果持续输入使需要等待的命令不断增加，就可能一直等不到整个闭包准备好。

用强连通分量（SCC）处理循环依赖，只解决一组互相依赖的命令按什么顺序执行，不自动保证需要等待的命令集合会停止扩大。

这和定时器问题要分开：依赖没准备好，是执行条件尚未满足；定时器已经到期，或者命令已经可以执行，却被后来工作一直挤到后面，是调度没有给它处理机会。不能用前一种限制解释后一种错误。

这里记录的是尚未建立的保证，不表示我们已经构造出当前协议在合法无限输入下永远不能执行的完整反例。

### 时间戳方向约束的候选方案

一个讨论方向是给命令排序，只允许较晚命令依赖较早命令。如果每个命令之前只有有限个命令，这有助于避免环和限制依赖范围。但不能直接删掉指向较晚命令的依赖：当前安全性论证依靠两个冲突命令之间至少保留一个方向，不保证保留的总是时间戳要求的方向。

之前“先看到 B 就执行 B，之后 A 才到”的简单描述没有交代 commit 条件，不能作为当前协议的完整反例。更具体的风险来自提前 Seal：某个副本先看到 A，它关于 B 依赖 A 的回复也可能在 B 选定候选后才到。

例如 5 个节点、f=2，C、A、B 都写同一个键，时间戳 C<A<B。假设新增规则是在观察时不记录对较晚命令的依赖，各节点首次看到的顺序如下。

| 节点 | 首次看到的顺序 |
| --- | --- |
| P1 | C → B → A |
| P2、P3、P4 | B → C → A |
| P5 | A → C → B |

B 的协调者先收到 P1 到 P4 的回复：只有 P1 的首次观察包含 C。此时 r=4、s(C)=1，满足 r-s(C)=3>f，可以提前 Seal 为 D(B)={C}。P5 关于 A 的迟到回复不能修改这个候选。应用新增过滤规则后，C 的依赖为空，A 只依赖 C，B 也只依赖 C，冲突的 A 与 B 失去了先后约束。

这可以安排为所有消息延迟都不超过 Delta 的推演：C、A、B 分别于 0、0.1Delta、0.2Delta 在 P1、P5、P2 开始；B 于 0.3Delta 完整发送 Seal，等到 1.3Delta 才决定；C 于 0.5Delta 决定并于 0.6Delta 被各节点获知；A 于 0.8Delta 决定并在 P5 执行，其决定直到 1.7Delta 才到 P2。P2 可以先执行 B 再执行 A，P5 则先执行 A 再执行 B。这个例子没有让命令跳过 commit 就执行。

上述例子针对新增的时间戳过滤规则，已经核算观察集合与 Fast/Seal 条件，但没有完成实际运行时复现。当前协议保留反方向依赖，不直接落入这个例子。后续研究时间戳方案时，需要同时解决候选关闭、迟到旧命令和冲突顺序的问题，不能只增加一条过滤规则。

## 7. 定时器怎样与普通请求一起处理

**当前状态：已发现的无限清空队列属于实现错误；完整的运行时调度规则仍需思考，暂不确定最终方案。**

### 这次具体错在哪里

旧代码把请求和定时器放在同一个 select 的平级分支中，但进入定时器分支后，先尝试清空收件箱，再真正处理超时。清空期间，新请求仍能进入队列。因此，“每个请求都处理得很快”并不意味着“整个队列最终会变空”。

已有要求是节点能够在后台自主推进。代码却额外要求“收件箱必须先变空”，这个条件没有出现在设计要求里。因此，这次具体缺陷归为实现问题；它本身没有证明 Fast、Seal 或接管算法错误。相关代码见 [旧版 Node](../experiments/20261101T041626Z-sol-high-subagents-01-wgoch47u/candidates/v000/node/node.go)。

### 为什么调度设计还需要继续想

把两个分支写在同一层，并不等于所有处理步骤都公平、都有时间上界。即使每次只处理一个事件，Go select 在多个分支就绪时也是伪随机选择，没有承诺某个分支最多等待多少次。因此还需要明确：定时器什么时候获得处理机会，一次最多处理多少工作，后来的请求能否不断插到它前面。依据：[Go 语言规范](https://go.dev/ref/spec#Select_statements)。

也不能简单规定所有定时器永远优先。例如，探测回复 ALIVE 已经按时到达，只是还在接收队列里；如果先做超时判断，就可能把活节点误判为死亡。

不同计时器的作用也不一样：

| 计时器 | 到期后做什么 | 处理错误主要影响什么 |
| --- | --- | --- |
| Watchdog，也就是恢复看门狗 | 发现命令迟迟没有完成，开始查询和探测 | 处理过晚会拖延恢复；它自己不直接授予接管资格 |
| Probe 探测计时器 | 检查是否及时收到了对应的 ALIVE，可能据此确认节点死亡 | 漏掉按时回复会误判死亡，影响接管安全；处理过晚会拖延恢复 |
| Seal 保存等待计时器 | 等待候选值按假设传播并保存后，再做决定 | 提前结束可能没有等够保存时间；处理过晚会增加延迟 |

这三个是讨论中的重点，不是全部计时点。OBSERVE 和正式恢复 READ_STATE 的回复期限也可能用于判死。Seal 的保存等待是完整发送 SEAL 后额外等待 Delta，不是快速路径收集观察的 2Delta；理想模型中的常规 Seal 路径因此最多为 3Delta。

Watchdog 应尽快得到处理，可以考虑优先于后来到达的普通请求，但不应打断尚未完成的原子状态更新。让有效 ALIVE 优先处理也能缓解排队问题，但仅靠它还不够：对端必须及时处理 PROBE，本端还要及时读取、解码并识别回复，其他用于判死的回复同样不能被漏掉。

如果用 delta 表示纯网络单程上界，用 p 表示对端收到 PROBE 后到发出 ALIVE 的排队与处理上界，用 q 表示本端收到 ALIVE 后到完成协议处理的上界，那么整个确认过程需要覆盖 2delta+p+q。只计对端处理 t 时，就是讨论中的 2delta+t。网络单程 10 毫秒、对端处理 5 毫秒、本端处理 3 毫秒时，20 毫秒判死就可能早于 28 毫秒的合法处理完成时刻。

可以显式计算网络与处理时间，也可以把指定处理阶段纳入有效 Delta；边界必须说清楚。现有 protocol.md 已注明理想计算忽略本地处理、真实执行应包含其成本，但运行时怎样满足这个要求还未完整设计。Seal 保存时间以后若包含 WAL 写入，也必须相应处理，不能只等网络传输。

客户端超时只表示等待预算用完，协议判死超时则用于授予接管资格，两者不能混用。我们的接管安全依赖准确判死，误判可能让两个存活节点都认为自己有权推进同一命令。因此后续应先明确每个计时点的起点、及时回复的接收边界和处理上界，再决定优先级与事件循环。

### 当前修复做到哪一步

当前 [v002 Node](../experiments/20261101T041626Z-sol-high-subagents-01-wgoch47u/candidates/v002/node/node.go)发现有计时器到期时，记录当前时间和队列中已有多少个事件，处理这一批之后推进本轮已经到期的计时器。期间新来的事件不会继续加进这一批；在处理过程中才到期的其他计时器，留到下一轮重新检查消息。

这个方案消除了本次“清空过程被新请求无限延长”的问题，可以作为工程候选。但实际要等多久，仍取决于这一批事件、处理函数、回调和系统调度的耗时。修复这个循环，不代表整个运行时的时间保证已经设计完整。

## 8. 换一种应用后，哪些命令算冲突

**当前状态：当前单键 KV 有明确解释，可复用范围需要注意。**

当前 KV 是内存映射，只支持 Put、Get 和 Delete，每次操作一个键。Put 返回写入值，Get 返回读到的值，Delete 返回删除前的值，并区分键是否存在。它用于承载共识实验，不需要马上扩展成事务数据库。

单键操作例如修改 Alice 的余额；跨键操作例如同时减少 Alice 的余额并增加 Bob 的余额，而且承诺两者作为整体生效。分别发送两个 Put 仍是两个单键操作，不会自动成为原子转账。当前没有跨键操作接口。

当前实现把同键读写视为冲突，两个 Get 不冲突，不同键的操作通常也不冲突。判断依据应包括操作返回值和状态变化。例如先读后写与先写后读，最终保存的值可能相同，但读出的结果不同，所以仍然冲突。

如果以后把应用换成跨键操作，不能继续照用现在按键判断冲突的规则。还需要考虑应用是否确定性地返回结果、错误结果怎样保留、应用回调会不会长时间阻塞，以及是否会调用外部系统。当前没有为任意应用提供这些保证。

## 9. 系统一直运行，历史数据怎样处理

**当前状态：保留必要历史，安全删除的方法尚未设计。**

现在需要保留命令、观察记录、依赖、决定和执行结果。运行时间越长，这些数据越多，不只占内存，还会增加消息大小和处理时间。即使请求速率没变，长期运行后的成本也可能不同。

不能因为命令已经执行就直接删掉它。后续命令可能需要观察它，副本恢复可能需要查询它，重复消息也需要按已有状态处理。即使客户端不重试，这些需求仍然存在。什么时候可以删除、删除后怎样处理协议消息，以及是否需要快照，都要单独设计。当前每个存活副本保留自己的结果，并没有提供副本重启后的持久化结果保证。

WAL 主要用于保留崩溃后恢复需要的记录；快照主要用于压缩历史、加快恢复或状态传输。只保存 KV 值不一定够，还要考虑观察、Seal、决定和去重结果。当前 crash-stop 模型不支持副本重启，可以暂不实现恢复，但长期运行的历史增长问题仍然存在。

## 10. 客户端最坏要等多久，测试又证明了多少

**当前状态：客户端可以设置等待超时，但不重试。6Delta 是之前讨论的条件性等待预算，未规定为当前默认值或完成保证。**

Fast 的 2Delta、Seal 的 3Delta 从相关广播完整发送后开始计算，不是从客户端发请求开始。客户端还可能等待发送、故障发现、按固定副本顺序接管、依赖恢复、执行和结果返回。不能把 commit 的时间界直接当作一次客户端调用的时间界。

假设客户端与节点之间的单程延迟也不超过 Delta，客户端直接联系原始协调者，广播启动等本地协议处理按理想模型计算，则请求到达需要 Delta，正常 commit 最多需要 3Delta，回复需要 Delta，再加执行前后的等待 E，得到 5Delta+E。如果依赖准备、执行排队和应用执行合起来能控制在 Delta 内，6Delta 就能覆盖这条路径。若经过其他接入副本转发和返回，还需按实际路径计算通信。

协调者正常不代表依赖都已准备好。例如 A 依赖正在恢复的 B，A 的协调者一直正常，客户端仍可能超过 6Delta 才收到回复。有限依赖也不自动提供统一的执行时间界：还要考虑依赖数量和处理成本。

之前讨论过用 6Delta 作为初始重试阈值；当前已暂缓客户端重试，只保留上述时间分析。实现可以选择并说明等待预算，超时后报告结果未知并结束等待，不联系其他节点重发，不宣布原命令失效，也不直接判定原协调者死亡。正式的最坏完成时间仍需单独论证。

消息条数少，也不代表传输字节少；依赖和历史可能让单条消息越来越大。已有恢复结论是保守估计，更紧的最坏延迟界和完整正确性证明仍有待研究。

98,304 个图枚举用例检查的是给定依赖图后的执行行为，没有检查完整客户端读写历史。它们是有价值的局部测试，但用例数量不能代替对验证范围的说明。

## 当前明确不支持的能力

下面这些是范围限制，不是这次发现的新错误。以后如果要长期持续服务，就需要另行设计。

| 能力 | 当前限制及以后需要考虑的事情 |
| --- | --- |
| 客户端重试与结果找回 | 每个逻辑命令只提交一次；不要求保存并加载请求、跨节点查询或恢复未完成请求。以后支持时再明确重试接入与结果交付规则；副本内部恢复继续属于当前要求。 |
| 副本重启和重新加入 | 当前副本一旦崩溃就不再回来。以后需要设计数据落盘、恢复身份和追赶状态；客户端换新会话重启不等于副本可以重启。 |
| 成员添加、移除和替换 | 当前成员固定，最多 f 个崩溃是累计限制。以后需要处理新旧成员如何共同确认决定、未完成命令怎么办，以及不同配置怎样区分。 |
| 网络分区后的恢复 | 当前不承诺任意分区。活节点因超界延迟被判死后，原来的“准确死亡判断”前提已经不成立，不能未经设计就撤销死亡记录或让旧节点继续参与。 |
| 快照和历史回收 | 当前没有快照安装或安全删除历史的规则，见第 9 项。 |
