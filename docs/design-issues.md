# 系统与协议的待讨论问题

本文件记录研究者尚需作出的选择，不作为 agent 的额外要求。当前设计以 [protocol.md](../inputs/protocol.md) 和 [system.md](../inputs/system.md) 为准，一次实验内固定；列出疑问不授权 agent 修改保证。具体实现案例见 [11 月 10 日探索性评测](exploratory-1110.md)、[11 月 13 日生成结果比较](comparison-20261113.md)和[11 月 11 日实现的服务器评测](server-evaluation-1115.md)。

## 1. 会话复用

当前生成、每轮修复、每轮发现审计和每次独立复核各自新建 Codex 会话；同一审计或复核内部的后续回合复用该阶段会话。新会话不等于更换模型，也不保证消除共同理解偏差。

| 可比较的组织方式 | 可能收益 | 需要观察的代价 |
| --- | --- | --- |
| 各阶段新建会话，当前方式 | 审计能重新选择方向，修复与复核不直接继承旧判断 | 重新理解实现，依赖文档交接，可能重复调查 |
| 生成与修复复用 | 熟悉架构和选择理由，减少理解成本 | 延续原误解，多轮积累过时上下文 |
| 发现审计复用 | 继续线索，记住已排除场景 | 调查方向固化，需要明确当前候选与旧观察的区别 |
| 原审计者承担修复复核 | 熟悉原反例，核查更快 | 更容易接受自己的解释，独立程度下降 |

这些选择可以分开比较，优先考虑生成与修复复用，同时保留新会话复核。比较重新理解与重复调查的成本、真实发现、有效修复和回归；无论复用与否，版本和原始证据仍应独立保存。

## 2. 外部中断后的证据使用

已实现的处理是：发现审计遇到 external_error，或回合超时且未交付完整报告时，从归档保留可用问题与证据，标注中断原因，再由修复与独立复核核查。没有可用问题时保留未完成状态，不解释成零缺陷。具体支持的续跑、人工交接和分支入口见 [workflow.md](workflow.md)。

待分析的是材料质量：中断时正文和索引可能不同步，执行记录也未必支持原解释。需要检查哪些发现仍有效、哪些应收窄、哪些尚未完成调查，不能把残留条目直接算成确认缺陷。

安全拒绝、网络断开、本地沙箱限制和预算截止按实际事件分别记录，不互相推断。已有材料的保存和核查不应变成反复换会话绕过拒绝；外部中断的成本与调查进度单列分析。

## 3. STATIC 与 TIMED 的研究范围

当前输入采用依赖 W/s 的 Collect 规则，没有 STATIC 功能或模式开关要求。此前讨论的 STATIC 是仅收齐 L 个合格正响应才完成 Collect；TIMED 允许在窗口前提成立时进入较小集合分支。两者影响响应人数、时间假设和故障后的可用性。

是否另行研究 STATIC 仍是范围选择。它可以减少小集合路径对窗口论证的依赖，却会失去部分高故障情况下的进度。例如 n=7、q=3、L=5 时，只剩三个副本便不能收齐 L；若仍要与合法 q 输出共存，也不能直接把 L 换成普通多数四票，因为两个集合可能不相交。

继续采用当前规则，就需要认真分析真实运行成本与 W/s 的关系；本地耗时检查无法证明所有远端窗口都满足前提。若将来增加模式切换，应由设计侧规定切换条件与证据兼容性，不能靠切换撤销此前已形成的决定，也不能由实现 agent 静默删除小集合路径。

## 4. 设计材料的详细程度

协议正文与事件伪代码已合入 protocol.md。明确的状态、原子动作、消息义务和选值规则属于设计依据；锁、队列、线程和数据结构通常由实现端选择。需要检查材料是否把某一种代码组织方式误写成唯一合法实现，以及正文和伪代码是否重复表达后发生偏差。

详细伪代码能减少遗漏，也承担了部分状态拆分和边界分析工作。当前 baseline 与 Forge 接收相同材料，比较回答的是给定这些设计后的实现效果。若要研究更简略的协议输入，应另设输入条件并同时提供给双方，不通过只删 baseline 的关键信息制造差异。

## 5. 与设计 agent 的衔接

当前没有接入设计 agent。两份设计文档提供协议规则和系统目标，通用实现、审计与交接方法放在角色提示和控制器中。未规定的合法工程选择由实现端决定；偏离明确规则由修复端处理；真实缺口、矛盾或忠实实现仍会触发的合法反例，通过 needs_specification 保留，具体状态处理见 [workflow.md](workflow.md)。

将来的交流适合在具体阻碍出现时进行。问题应带材料版本、相关规则、场景或代码位置、已有证据及哪些工作依赖答复；设计端说明是在澄清含义还是改变规则。实现端继续不受影响的工作，依赖新设计的部分明确等待，不能后台静默换掉正在使用的材料。

改变语义时用普通 Git 提交或版本号记录，重新判断旧反例和代码是否仍适用，baseline 同步采用对应输入。设计 agent 的答复仍需理由与反例检验，不能自行充当正确性证明。交流时机、分歧处理与变更传播方式尚待设计。

## 6. 协议仍需完整论证的范围

以下是证明与分析任务，不是已经确认的缺陷：

| 范围 | 需要连接起来的论证 |
| --- | --- |
| 选值与证据 | Cover、Selection、NoFast、继承和跨实例引用如何共同保持决定一致及冲突可见性 |
| 恢复与后台进度 | HELP、并发 ballot、任务替换、证据取回和 Omega 稳定后如何共同推进 |
| 依赖向量与 carry | 代表编号、初始序号、较小编号数据和依赖展开如何覆盖必要冲突并保持执行进度 |
| 请求与实例 | 跨入口重试产生多个实例时，执行、rid 去重和客户端回复如何共同保持服务语义 |

有限测试可以寻找反例，不能替代完整组合论证。发现问题时区分实现偏离与设计反例；本文件不重复维护协议摘要，也不把当前未要求的检查点、跨 epoch 或崩溃重启纳入实现任务。
