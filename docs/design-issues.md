# 系统与协议的待讨论问题

本文件供研究者讨论，不作为实验 agent 的额外提示词。当前设计以两份混合 EPaxos PDF 为基础，并已纳入依赖前沿和检查点方案；具体要求以 [protocol.md](../inputs/protocol.md)、[pseudocode.md](../inputs/pseudocode.md) 和 [system.md](../inputs/system.md) 为准。下面区分当前做法、它带来的取舍和后续值得验证的问题。列为待讨论不代表已经发现错误，也不授权 agent 在实验过程中修改给定设计。

## 1. 每个阶段新建 agent，还是复用已有会话

当前生成、每轮修复、每轮发现审计和每次独立复核都启动新的 Codex 会话。同一次审计内部继续调查，或者同一次复核补充交付时，会复用该阶段的会话。因此，并不是每次模型回复都换一个 agent。“新 agent”在这里主要指新会话和新上下文，并不表示换了模型。

| 组织方式 | 可能的好处 | 需要注意的代价 |
| --- | --- | --- |
| 每个阶段都新建会话，沿用当前做法 | 新审计可以重新选择调查方向；修复和复核不直接继承前一会话的全部判断 | 需要重新理解实现，部分设计理由和未完成线索只能靠文档交接；可能重复调查 |
| 生成与后续修复复用同一会话 | 熟悉架构、改动理由和已有测试，可能减少修复前的理解成本 | 可能延续生成时的误解、维护原方案；多轮后会积累过时上下文 |
| 所有发现审计复用一个会话 | 能继续未完成线索、记住排除过的假设，减少从头读代码 | 可能持续围绕原来的怀疑，遗漏新方向；必须区分旧版本观察和当前版本事实 |
| 同一审计者还负责修复复核 | 熟悉原始缺陷及其复现，检查改动可能更快 | 更容易认可自己的原始解释；这种复核与另外新建会话的复核，独立程度不同 |

这些选择需要分别比较，不能把“全部复用”作为一个不可拆分的方案。例如，可以让生成与修复复用，让发现审计持续调查，同时仍让修复复核使用新会话。新会话也可能因采用同一模型和材料而重复相同误解，不能把会话隔离理解为判断必然独立。

后续可以先比较“生成与修复复用”和当前方式，再单独比较发现审计是否复用。记录重新理解代码的时间、重复调查、有效发现、修复效果、回归和实际 token 开销，而不是只看完成得更快。无论采用哪种方式，候选版本、原始证据、修复说明和独立可读的交接材料仍需保留，不能只依赖会话记忆。

## 2. 审计可能被 OpenAI 的安全审查中断

审计阶段可能遇到 OpenAI/Codex 的安全拒绝或网安审查拦截，导致模型无法完成当前回合。它与本地沙箱不允许某条命令、普通网络断开、额度不足和阶段超时是不同原因。应依据实际返回事件和错误说明记录，不根据“某个测试执行失败”就推断触发了网安审查，也不凭拒绝结果推断候选实现存在安全缺陷。

当前代码保留原始回合、命令、输出和已有文件；失败阶段中尚未正式交付的报告会列为待查看材料，不自动变成正式问题。安全拒绝不会被当成普通可恢复超时继续收尾。这样保留了失败原因，但也可能使已经写出有效复现的调查无法进入修复阶段。

需要进一步讨论的是如何利用中断之前已经完成的工作：已有正式交付的问题是否可以继续处理；仅写到一半的报告中，哪些观察有可定位的候选版本和执行证据；哪些只是尚未核实的怀疑。完整交付与未完成材料应分别呈现，不能因为会话中断就忽略全部证据，也不能把残留 JSON 中的每个条目直接当成可信缺陷。

后续处理应围绕保存、核查和合法复用已有材料，不把换会话反复重试作为绕过安全拒绝的办法。实验分析也应单独记录这类外部中断、已投入的资源和中断时的调查进展；它既不是“未发现问题”，也不能直接用于评价审计模型的找错能力。

## 3. STATIC 与 TIMED 模式如何定位

桌面的 `mixed_epaxos_frontier_v2.md` 提出过两种 Collect 策略。STATIC 只在收齐 L 个合格正响应时成功，不使用依赖窗口的小集合分支；TIMED 允许在真实 W/s 前提成立时，按两阶段规则使用较小集合。两种策略影响所需响应人数、时间假设和故障后的可用性。

当前共同输入保留了依赖 W/s 的 Collect 规则，没有要求实现 STATIC 模式或模式开关；从上述分类看，它使用的是 TIMED 路径。不能因为外部方案曾建议默认 STATIC，就要求当前生成结果实现一个材料中没有规定的功能。

STATIC 的好处是 Collect 成功集合的相交可以依靠人数关系，不使用小集合所需的窗口论证；代价是需要更多成员回复。以当前示例 n=7、q=3、L=5 为例，四个成员崩溃后只剩三个成员，STATIC 就不能继续完成 Collect。它也不意味着整个协议从此不需要任何时序或进度前提，Omega 等其他部分仍有自己的要求。如果还要与既有合法 q 输出共存，也不能直接把 L 改成普通多数四票，因为 4+3=7，两个集合可能不相交。

TIMED 保留了较多成员崩溃时继续推进的目标，但编码、排队、验证、证据取回和检查点传输等实际成本必须计入给定窗口。收到 q 个回复并等到本地超时，不足以证明所有相关远端都满足 W/s；发现本地耗时超标也只是发现一部分违约，不能证明其他窗口都没有违约。事后切换 STATIC 不能撤销已经在假设失效时形成的错误决定。

后续需要决定的是研究对象：继续研究给定 W/s 假设下的协议实现，还是把 STATIC 作为另外一种运行配置，并明确它牺牲的可用性；若允许切换，还要规定切换前后的有效证据和保证。本项属于设计范围选择，不能由实现 agent 静默删除小集合路径来换取更容易通过的测试。

## 4. 关闭旧 epoch 与开放新 epoch 存在串行阶段

当前检查点方案要求先封住旧 epoch，确定必须完成的实例清单，完成清单内实例的决定与执行，形成并存储合法检查点，再安装新基座、开放下一 epoch。已经进入 Seal 的副本暂停新实例准入；客户端请求可以排队，但不能提前当作新 epoch 的实例执行。旧实例恢复、执行和已有结果返回仍可继续。

因此，旧 epoch 中必须完成的工作与基于新检查点的新请求处理之间存在串行阶段。若一个清单内实例恢复缓慢，或检查点准备、验证、传输成本较大，暂停准入的时间就可能变长。检查点频繁时，即使普通请求路径很快，客户端也可能周期性遇到排队和延迟上升。这是当前保守协议设计的代价，不应仅因实现忠实遵循该顺序就报告为实现缺陷。

这里的“不能并行”需要限定范围：尚未合法关闭旧工作时，不能提前开放依赖新基座的新实例；但合法安装之后，清理已经失去引用的物理对象可以按实现条件放到后台。某些副本进入新 epoch 时，仍存活的落后副本也可能正在同步检查点。增量准备、共享不可变数据和分块传输可以优化实际成本，但仍须满足安装、可取回性和证据保留规则。

如果希望在旧清单尚未处理完时就接纳新 epoch 实例，需要重新回答：新请求基于哪份应用状态执行，怎样表示对未完成旧实例的依赖，跨 epoch 的顺序如何保证，何时允许删除旧证据，以及崩溃接管后如何保留这些关系。这已经超出增加几个后台线程的实现选择，需要设计侧给出新规则。

后续先测量不同 J、检查点触发频率和负载下的暂停准入时间、请求排队、尾延迟、检查点成本及长期吞吐。区分协议必须等待的时间与实现重复扫描、复制、校验带来的额外成本，再决定是否值得扩展成真正重叠推进的跨 epoch 方案。

## 5. 近 500 行伪代码是否提供得过细

当前 `inputs/pseudocode.md` 共 693 行，其中代码块占 520 行，扣除代码块中的空行后为 472 行；这个数字仍包含数据结构声明和行内说明，不等于 472 行核心算法。伪代码除了普通命令路径，还覆盖证据验证、恢复、HELP、后台调度和检查点控制，复杂度并非全来自代码写法。

详细伪代码可以减少规则遗漏和解释分歧，也让审计有更具体的依据。但它已经替实现 agent 完成了不少状态拆分、事件组织和边界分析，可能使任务更接近把操作规格翻译成程序；同时，协议说明和伪代码重复表达相同规则，会增加维护不一致的风险。文件越详细，也越需要区分必需语义与示例组织方式，避免把示例函数边界误当成唯一合法架构。

对当前比较而言，baseline 和 Forge 得到相同伪代码，额外方法是否有效仍可比较；但结论应限定为“给定这些设计材料后”的实现与审计效果，不能直接推广成仅凭一篇简略协议论文也能获得同样提升。生成耗时变短是否来自伪代码更详细，需要在相同协议范围、模型与资源条件下比较，不能只凭不同协议的两次实验判断。

后续可以检查哪些内容属于设计必须明确的状态与规则，哪些是可由实现端自行组织的调度和数据结构示例，以及哪些只是两份文档之间的重复。精简应保留关键语义、失败路径和解释依据，不以减少行数为唯一目标，也不只删除 baseline 的关键信息来制造差距。如果要比较较简略和较详细的设计输入，应明确作为不同输入条件分别运行。

## 6. 与设计 agent 的衔接

当前设计作为给定输入，一次实验中不修改，也没有接入设计 agent；真实规格缺口通过报告和 `needs_specification` 记录。协议规则、操作展开和目标系统要求集中在三份设计文档；可复用的实现、审计和交接方法放在角色提示与控制器中。将来设计端应提供这三类信息，但是否必须生成当前规模的伪代码，需要结合上一项单独评估。

需要区分三种反馈。第一种是材料允许的工程选择，例如使用哪种队列或证据索引，由实现 agent 自行决定。第二种是实现偏离已明确规则，由修复端处理。第三种是缺失、矛盾的设计要求，或忠实实现也会触发的合法反例，需要设计侧解释或修订。不能把实现端一时没有想清楚都升级为设计问题，也不能要求实现端靠偷偷加强假设来消除真实设计缺口。

将来的沟通更适合在发现具体阻碍时进行，而不是一定等完整生成或审计结束。提问至少应带上当前材料版本、相关规则、具体场景或代码位置、已有证据、缺失的决定，以及哪些工作真的依赖这个答复。设计端需要说明答复只是澄清已有含义，还是改变规则、假设或目标；实现端可以继续不受影响的工作，依赖该答复的部分则保留明确状态。

“可以及时交流”不等于设计端可以在后台随时改掉正在使用的材料。若答复改变语义，应保留旧材料和旧证据，用普通 Git 提交或版本号标明变更，再明确后续代码、审计和复核采用哪个版本。旧反例可能因此变得不适用，也可能仍揭示实现问题，需要重新判断，不能直接删除或沿用旧结论。baseline 比较同样要对应相同的设计输入。

另一个待讨论点是设计端、实现端和审计端意见不一致时如何处理：理由与反例需要保留，设计 agent 的答复本身不能充当正确性证明。涉及保证变化、故障范围或 STATIC/TIMED 选择时，不能默认为普通实现细节。

## 协议本身仍需完整论证的部分

前六项主要讨论系统组织、实验输入和协议扩展的取舍。另有一些问题属于协议正确性论证：原始混合 EPaxos 材料保留了未完成的组合证明，后来加入的依赖前沿和检查点又增加了新的组合关系。现有材料给出了规则和部分论证，但还需要把这些部分连起来确认，不能仅因原始核心成立就认定扩展也成立。

| 范围 | 需要进一步确认的内容 |
| --- | --- |
| 原始核心的选值与证据 | Cover、Selection、NoFast 的组合是否始终支持合法选值，继承和跨实例引用是否保持同实例决定一致及冲突可见性 |
| 恢复和后台进度 | HELP、并发 ballot、任务替换、证据取回与 Omega 稳定后的恢复是否能共同推进，而不只是各条路径单独可运行 |
| 依赖前沿压缩 | 压缩后的依赖是否持续覆盖必要冲突，是否保留执行顺序及序号语义；普通扫描的压缩是否与 Validate 的完整冲突义务正确衔接 |
| 检查点和跨 epoch | START、ADD、CLOSE 的并发与恢复是否遵守最高 accepted 继承，最终清单是否覆盖所有合法旧决定；检查点存储、安装、证据退休和落后副本同步是否共同保持状态与证据可用 |
| 客户端历史与请求延续 | 实例决定、依赖执行、请求去重、跨 epoch 重排队和结果保留组合后，是否满足目标客户端历史语义，并避免请求在反复切换 epoch 时一直被推迟 |

这些是尚待完整论证的范围，不是已经确认的缺陷。实验可以针对具体疑点寻找合法反例；若发现问题，需要区分实现偏离了规则，还是遵守规则仍会失败，再按第 6 节交给相应一侧处理。已明确的参数、消息规则和可选实现机制直接以三份设计材料为准，本文件不再重复维护一份协议摘要。
