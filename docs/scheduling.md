# 实际事件调度与重放

`runtime/schedule.py` 是一个可选的标准库工具。它在已有 `isolated_exec` 内启动候选适配器，从适配器报告的待处理动作中选择下一步，并保存实际返回的事件和观察。Python 不计算依赖集、判断换主或补发协议消息；这些仍由候选实现完成。工具也不决定哪些场景应该测，场景和性质判断仍由 agent 负责。

生成和修复阶段得到 `inputs/schedule.py` 副本，可从 workspace 查看 `python3 -I ../inputs/schedule.py --help`。审计和复核得到只读 `tools/schedule.py`，绝对路径在 run brief 中；交接包保留当时工具。新实验不注入旧逐消息时间检查器。

## 三部分各自做什么

| 部分 | 职责 | 需要审阅的边界 |
| --- | --- | --- |
| 调度计划 | 提交输入、选择消息、安排崩溃、推进时间、检查观察 | 外部动作是否满足当前协议假设，断言是否表达真正要检查的性质 |
| 候选适配器 | 调用真实接口，报告可用动作和实际观察 | 是否绕过相关运行时，事件是否符合实际实现及协议义务，是否偷偷补了协议逻辑 |
| 公共调度器 | 按计划选择动作，限制执行步数和时间，记录与比较 | 完成一次运行不等于性质正确，重复得到相同记录也不等于记录可信 |

适配器通常可以写成候选语言中的小程序，使用标准输入和标准输出交换 JSON 行。候选无需采用框架规定的包结构或公开接口。如果现有接口不能控制某个关键边界，应说明覆盖限制；诊断插桩要保留并解释，不能把绕过真实路径的实验说成生产路径复现。

协议中的发送、窗口和故障规则见 [protocol.md](../inputs/protocol.md)。适配器沿用候选真实事件含义，不能在驱动中补全实际未完成的广播、响应或状态转换。W 从广播开始计时，包含实际收回响应的工作；每个窗口允许 s 个仍存活成员尚未回复，不能把它当作逐消息期限或准确判死。时间推进与回调执行可以是不同事件，记录必须说明所控制的实际边界。故障注入永久停止崩溃副本；正确节点通信和后台工作应符合源模型的公平性。公共调度器不独立验证这些前提。

## 最小接口与计划

第一次请求是 `{"op":"init","setup":{...}}`。每次响应必须有非负且不倒退的整数 `now_ns` 和 `pending` 列表，可附增量 `events` 和自定义 `observations`。首次响应还需要 `scope`，说明实际调用哪些实现、绕过哪些部分。标准输出只能写响应 JSON；诊断信息写标准错误。

一个待处理项可以是：

```json
{"id":"a:17","actions":["deliver","complete"],"src":"a","dst":"b","command":"x","message_kind":"OBSERVE"}
```

`id` 标识本次可操作项，不是命令的全局身份。其他字段由适配器选择。调度器只按这些字段匹配，不能独立验证这个动作是否真的存在于候选内部。对一次发送的开始、接收和完成回调，应根据真实接口分别建模；崩溃不应凭空删除已发出且仍有交付义务的消息。

计划示例：

```json
{
  "setup": {"members": ["a", "b", "c"]},
  "steps": [
    {"do": "submit", "args": {"node": "a", "command": {"id": "x"}}},
    {"do": "deliver", "select": {"src": "a", "dst": "b", "command": "x"}},
    {"expect": {"observations": {"executed": {"b": 1}}}}
  ]
}
```

这里只演示格式；命令是否合法、何时可以执行由候选和所检查性质决定。`select` 要匹配一个允许该操作的待处理项；零个匹配报告 `not_reached`，多个报告 `ambiguous`。对象按给出的字段匹配，列表和标量要求完整一致。调度器向适配器发送 `{"op":"deliver","id":"a:17"}`，不会生成消息内容。没有 `select` 的动作直接传递 `args`，适合提交请求或崩溃等外部输入，合法性由适配器和审阅者确认。

需要自动推进一个有限后缀时，可用 `drive`：

```json
{"drive":{"choices":[{"do":"deliver","select":{}},{"do":"fire","select":{}}],"until":{"observations":{"done":true}},"limit":100}}
```

它按 `choices` 的顺序选择第一个有匹配项的操作，再按适配器报告顺序选择一个待处理项。最多执行 `limit` 个动作，不会自动补消息或推进时间。这个顺序是一种明确的测试调度策略，不是实现具有公平性的证据。定时器到期和回调执行能否分别控制，取决于适配器实际连接的接口；只调用核心 `Advance` 不能验证真实 Node 的队列优先级。

## 执行、重放和反馈

下面的命令在一次 `isolated_exec` 内执行；`ADAPTER` 是同次调用内编译好的适配器程序，`HELPER` 是该阶段提供的工具绝对路径。调度器默认有 30 秒墙钟预算，可用 `--timeout` 调整；构建、调度和清理仍受外层执行预算约束。

```sh
python3 -I HELPER --plan tests/scenario.json -- ADAPTER
python3 -I HELPER --replay tests/previous.jsonl -- ADAPTER
```

标准输出依次记录计划、发出的请求、实际响应和总结，并逐行刷新。既有执行服务会保留完整 `executions/<id>/stdout.txt`，即使超时或临时源码副本被删除，已有输出仍在。使用 `source="candidate"` 或 `source="before"` 时，把计划、适配器和检查代码作为 `overlays` 提供；需要重放时，将原 stdout 复制为工作区中的输入文件并一并提供。执行记录关联原始 Git commit、命令和实际覆盖文件，不需要再加文件哈希或新的版本约定。

若适配器另写文件，可通过 `isolated_exec` 的 `outputs` 参数选择工作区相对路径，在副本清理前归档，例如 `"outputs": ["results/history.json"]`。保存位置和未保留原因在执行结果的 `artifacts` 中；不要依赖调用结束后仍能访问临时副本。相关限制见 [workflow.md](workflow.md)。

`--replay` 要求原记录包含完整的请求/响应和可重放的终止状态。它重新运行原计划，对比每次请求、响应及终止状态；不会自动执行原日志里的可执行文件路径。相同版本也可能因未控制的线程、时间戳或容器枚举顺序发生差异，应定位差异而不是删除观察字段来制造一致。跨版本修复通常用相同 `--plan` 检查因果场景和最终性质，不要求 token 或所有内部观察逐字一致。接口适配需要解释并保留原材料；事件消失或编译失败不能说明问题已修复。

| 总结状态 | 含义 |
| --- | --- |
| `completed` | 计划和显式观察检查完成；检查可能本来就在寻找缺陷，因此不等于共识正确 |
| `expectation_failed` | 实际观察不满足计划断言 |
| `not_reached` / `ambiguous` | 无法唯一确定所要求动作；需要判断场景变化、适配问题还是实现问题 |
| `step_limit` | 有限推进步数用完，不能直接宣称无限不活跃 |
| `replay_diverged` | 实际请求、响应或终止结果与原记录不同 |
| `adapter_error` / `timed_out` / `interrupted` / `invalid_input` | 工具、输入或适配执行未正常完成，保留已有记录供分析 |

退出码 0 对应 `completed`，1 对应观察、选择、步数或重放差异，2 对应输入或执行错误。审计报告还应说明断言极性：一次成功运行可能恰好证明了错误行为可复现。修复和独立复核都要检查实际观察与性质，不能只比较退出码。

增量 `events` 和额外适配器字段保留在实际响应记录中，不自动套用协议时间模型。适配器的 `trace_model` 等附加字段仅作为记录保留，总结不生成 `trace_check`。需要解释广播、窗口、阶段与慢成员条件时，由调查者结合真实观察和协议规则给出依据；普通 JSONL 记录直接作为 `evidence` 引用。

## 工具检查

`tests/test_schedule.py` 检查动作选择、严格重放、输入错误、超时和中断清理等行为。真实隔离环境的检查统一放在已有的 `tests/check_local_execution.py`：复用小型队列适配器，通过 MCP 执行调度，再从保留的 stdout 严格重放，确认源版本、覆盖文件和日志保留。这部分验证工具接入，不是共识测试。两者均不调用模型。

```sh
.venv/bin/python tests/check_local_execution.py
```
