# Consensus Forge: Engineering Consensus Systems with Coding Agents

## Abstract

Strong coding agents create an opportunity to turn new consensus designs into runnable concurrent systems. The challenge is to preserve protocol requirements as agents make engineering choices, construct tests, and revise shared runtime mechanisms. An implementation and its tests can share a mistaken interpretation, while a repair can remove one failure yet violate another obligation or impose substantial costs. We present Consensus Forge, a method and framework that organizes generation, independent auditing, repair, and review around explicit links between protocol requirements, implementation mechanisms, and execution evidence. Forge guides agents to explain consequential choices alongside code. Independent auditors investigate reachable executions, distinguish implementation defects from specification gaps, and retain reproducible evidence. Repair and review carry this evidence across versions to check the original failure and affected behavior. A lightweight controller manages artifacts and revisions while leaving engineering and investigation strategies to the agents. We study Forge through Mixed EPaxos, generating Go replicated key-value services with real networking, concurrent consensus instances, and multicore processing. Audit and review records identify recovery lifecycle and progress defects and document targeted repairs. Comparisons with direct autonomous generation show substantial gains in ordinary request performance and selected progress scenarios, alongside remaining defects and repair-induced performance regressions. Forge provides a practical approach to engineering consensus implementations with coding agents, with protocol conformance, correctness, and performance evaluated separately and evidence retained throughout iterative development.

## 1. Introduction

Coding agents make it practical to attempt a demanding systems task: implementing a new consensus design as a complete concurrent service. In our experiments, direct autonomous generation already produces runnable Go systems with replica processes, network transports, client interfaces, and tests, and can diagnose and revise its own code. Researchers can ask agents to undertake substantial engineering work. The research challenge is how to organize that capability so that the system remains faithful to its protocol, behaves correctly under failures and concurrency, and provides useful performance.

The distance between a protocol description and an executable system is substantial. Experience with Paxos has long illustrated that implementing a concise consensus algorithm requires additional mechanisms, engineering decisions, and validation beyond the algorithm itself. [Paxos Made Live: An Engineering Perspective](https://static.googleusercontent.com/media/research.google.com/en//archive/paxos_made_live.pdf) documents this transition in a production system. For an agent implementing a new protocol, the description establishes obligations but leaves many mechanisms open: how replicas share state across workers, when a protocol timer begins, how messages enter and leave queues, and how recovery and application execution coexist with new requests. These choices determine whether abstract protocol steps retain their intended meaning in the running system.

Three difficulties arise when agents carry out this work. First, **engineering freedom must remain connected to protocol obligations**. A protocol need not prescribe every lock or worker, yet implementation choices can change its behavior. For example, collecting enough replies to select a candidate need not end every message obligation for that request. Conflating these events can produce a system that completes requests while bypassing a required protocol path. Guidance must make obligations inspectable while preserving implementation freedom; prescribing every detail would shift the engineering task back to the researcher.

Second, **self-consistency between code and tests is insufficient**. The same interpretation can shape both an implementation and the tests written to validate it. An auditor faces a related problem: a plausible failure scenario may violate the protocol's assumptions, a test adapter may bypass the runtime mechanism under investigation, or an assertion may establish less than the accompanying explanation claims. Existing work on testing LLM-generated distributed protocol implementations demonstrates the value of fault injection and examination of debugging behavior. [Testing LLM-Generated Distributed Protocol Code](https://pldi26.sigplan.org/details/page-2026-papers/5/Testing-LLM-Generated-Distributed-Protocol-Code) studies these issues for distributed protocols. Our focus is how findings and their supporting executions can guide the continued construction of a complete system, including the runtime behavior that a protocol simulation may not exercise.

Third, **repair changes a system, not just a failing test**. Consensus implementations share synchronization, queues, timers, retry logic, and dependency tracking across normal operation and recovery. Modifying one of these mechanisms can fix a witnessed failure while introducing a protocol deviation elsewhere. Even when a change preserves correctness, it can increase ordinary-path cost or slow unrelated work. A useful repair process must therefore retain what justified the original finding, examine the behavior affected by the change, and keep earlier evidence available for later revisions. Passing the original reproduction alone does not answer these questions.

We present **Consensus Forge**, or **Forge**, to address these difficulties. Its organizing principle is to maintain a connection between a protocol requirement, the runtime mechanism intended to satisfy it, and observations that support or challenge that implementation choice. Generation establishes these connections, auditing challenges them with concrete scenarios, and repair and review reassess them after changes. Protocol conformance, correctness, and performance are distinct evaluation dimensions: following the supplied design, satisfying the required observable behavior, and using resources effectively. This separation makes it possible to identify an implementation that departs from the design even when a generic success check passes, or to recognize a valid repair whose performance cost still warrants investigation.

On the generation side, Forge supplies a fixed protocol design and system goals, with guidance for building complete execution paths and explaining consequential choices. The agent develops its design document alongside the implementation, connecting requirements to code and stating what its checks establish. It chooses module boundaries, synchronization, scheduling, and tests. Unspecified mechanisms remain implementation decisions; genuine contradictions or missing requirements are recorded explicitly. These practices make decisions reviewable without forcing every candidate into a common architecture.

On the auditing side, a fresh agent context examines the candidate using source inspection, native tests, and additional executions through real replica code. Findings connect expected behavior to a reachable scenario, an observation, and an explanation. The auditor must examine which runtime events timing assumptions cover, whether message and crash schedules are allowed, and whether observations exercise the mechanisms implicated by a claim. Supported findings, unresolved hypotheses, and ruled-out interpretations are recorded separately. A finite timeout can establish poor progress within an observation interval without proving permanent loss of liveness.

At the handoff between auditing and repair, Forge preserves reproductions, execution records, assumptions, and the revision to which they apply. The repair agent evaluates this evidence before selecting a change. An independent review examines the original obligation and affected behavior, retaining useful checks for subsequent iterations. Reports use a lightweight structure to make these relationships easy to locate. The controller manages revisions, artifacts, and execution associations; agents and subsequent evaluation assess their semantic meaning. This division preserves investigative freedom while making clear what was tested, what changed, and why an issue was considered resolved.

We investigate Forge using **Mixed EPaxos**, a protocol with explicit timing assumptions, multiple coordination paths, dependency-based execution, and recovery under a fixed-membership crash-stop model. The implementation target is a replicated key-value service with autonomous replicas, real networking and timers, concurrent consensus instances, and multicore processing within a replica. Our comparison distinguishes direct autonomous generation, the initial implementation produced with Forge's generation guidance, and later versions produced through auditing and repair. The direct baseline retains the ability to design, test, debug, and decide when to deliver; it is not restricted to a single code-generation attempt. Runtime measurements use separate replica processes and explicit CPU allocations, with fixed input rates and observation of work that remains after request submission ends.

The case study exposes defects beyond basic service functionality. Audits produce executable findings involving recovery tasks that remain active after losing eligibility, higher-ballot responses discarded by stale-message filtering, and background work that fails to revisit old pending instances. Subsequent repair reviews exercise the corresponding changes. These findings connect abstract protocol obligations to concrete lifecycle and scheduling mechanisms; their review outcomes apply to the tested revisions and scenarios. The [audit and repair record](../experiments/20261111T051255Z-sol-high-protocol-parallel-forge-1111-02-mhu_ai6o/issues.json) preserves these associations.

Performance measurements also show substantial improvements, with distinct effects from generation and repair. In a seven-replica deployment with two physical cores and four hardware threads per replica, independent-key writes submitted across replicas at 800 requests per second have mean latency of 7.35 ms for direct generation, 1.24 ms for Forge's initial implementation, and 1.32 ms after repair. Repairs improve completion in selected conflict workloads and reduce interference from pending work, but also introduce substantial regressions in some resource and message-delay configurations. These results make repair cost an engineering question alongside repair effectiveness, rather than an assumed necessary price of correctness. [Ordinary requests](server-A-evaluation.md), [conflict workloads](server-B-evaluation.md), [message delays](server-C-evaluation.md), and [pending work](server-D-evaluation.md) are evaluated separately.

This work makes three contributions:

- **A method for constructing consensus systems with coding agents.** Forge organizes implementation freedom around explicit relationships between protocol requirements, runtime mechanisms, and evidence, addressing the transition from an abstract design to a concurrent service.
- **An evidence-preserving audit and repair framework.** Independent investigation, reproducible findings, revision-aware handoffs, and repair review connect defect discovery to subsequent implementation changes while retaining material needed to examine regressions.
- **An empirical case study of complete generated consensus services.** Comparisons across direct generation, guided generation, and repair identify improvements in runtime behavior, expose failures of interpretation and verification, and characterize the performance consequences of correction.

The central lesson is that stronger coding capability makes the organization of engineering work more consequential. Forge supports this shift by connecting autonomous implementation choices to protocol obligations and carrying executable evidence through successive revisions.
