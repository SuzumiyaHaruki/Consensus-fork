三者提供的 protocol.md 内容相同。本次 baseline 与 Forge 的 system.md 相同；相对上一次 Forge，系统材料加强了独立副本资源配置、结果分布和收尾观测等说明。基线实现、两个 Forge 实现的架构不同，结果不能只归因于提示词长度或某一次修复。

原第三轮的审计因连接错误提前结束，留下执行图问题并完成修复。新开第三轮完整审计发现了三个不同问题，但没有带回旧第三轮的修复。因此将旧修复直接整合到新分支 v003，再用本地测试验证并替换原第三轮。没有增加正式的第四轮修复或复核；误启动的追加模型流程已停止，其部分输出未用于本次整合。原第三轮、新分支原始记录及整合前候选仍然保留。

## 新第三轮发现与遗漏

| 问题 | 影响及已取得的证据 |
| --- | --- |
| Observe/Validate 的 promise 更新与首次观察登记分离 | 更高 promise 已对外生效时，冲突命令还未进入观察集合；真实六 Node 场景可到达该状态。复核检查了原触发和 Validate 变体；这是协议原子性偏离，尚未构造决定分歧 |
| 低位未执行命令之后的已执行区间重复扫描 | 新执行索引跳过已执行位置。复核的 30,001 条历史场景约 199.5→381.3 OK/s，p95 156.6→72.7 ms；额外索引增加内存 |
| 每次读请求扫描该键全部历史写 | 改用精确的冲突摘要。复核的 15,001 次历史写场景约 591.8→739.8 OK/s，p95 59.0→44.7 ms；独立键写控制约下降 1.1% |
| 多个未执行根重复展开重叠依赖闭包 | 新分支仍有旧第三轮已经修复的问题；直接整合旧修复，并验证其与新执行索引的组合 |

上述性能数字来自各自的独立复核场景，不能与下表不同配置直接比较。前三项在新第三轮 v003 上被复核关闭；最后一项有旧第三轮独立复核证据；整合后的验证由本次直接运行的测试给出，不能把旧复核改记成对新提交的独立复核。

## 共同测试条件

本机八个共享 vCPU；七个独立副本进程，各自 GOMAXPROCS=2，使用真实 Node、原生网络与认证方式；无独占 CPU。配置 n=7、f=4、s=1、e=1、K=64、W=200 ms，普通性能项 worker=4。目标 N 是已接纳但尚未首次决定的全局实例上限，不是客户端等待数；请求首次决定后允许补充新请求，客户端回复仍可继续等待。

每个性能配置测量 8 秒，独立重启集群，轮换版本顺序重复三次。表中分别取三次吞吐和 p95 的中位数，原始逐次值保留；吞吐仅计测量窗口内 OK 回复，p95 计本轮包含收尾的 OK 回复。停止提交后继续收集回复和生命周期事件，检查未完成工作。它是本机短测对照，不替代长时间服务器实验。

测试使用候选源码副本。baseline 没有暴露接纳/决定/执行事件，因此仅在其副本对应位置增加三处只读事件通知；适配器不生成票、决定或依赖。旧 Forge 对同键读读也判冲突，新实现允许读读交换，有限历史检查遵从各自实际冲突分类。认证和传输设计仍保留各自实现差异。

## 如何解释这些差异

最终 v003 在独立键和大载荷场景明显快于最新 baseline，空闲历史成本也更小；但热点写吞吐更低。相对上一次 Forge，单点协调及 N=64 均匀协调吞吐更高，N=16 均匀/随机协调和大载荷吞吐较低。共享执行图消除了原复现中的大幅延迟，普通路径也有小幅得失，不能概括为所有指标都提高。

源码层面，上一次 Forge 使用实例级锁和共享登记锁；本次 baseline 主要使用全局读写锁，本次 Forge 在共享互斥锁之外计算观察/执行图。三者的网络请求组织、调度和索引也不同，因此单凭吞吐表不能把差异全部归因于锁，或宣称已证明副本内多核扩展效果。新第三轮修复才补上本次 Forge 的精确冲突摘要，而最新 baseline 初始实现已有类似摘要，这是 baseline 的实际优势之一。

这次记录体现了独立审计能补足生成阶段自查，也暴露了调查覆盖的不稳定：新一轮发现原审计未发现的原子性与历史成本问题，却漏掉了旧执行图问题。复用历史反例使这个遗漏在替换前被发现，已有修复得以直接整合并重新验证。收益需要分别看协议符合、有效修复、回归和普通路径成本，不能用问题数量或单一吞吐概括。

共同测试没有覆盖所有恢复分支、网络调度和长时间运行；性能任务的状态统计也不等于完整安全性检验。此次未重新进行三份候选原生测试套件的等量审计，独立复核的关闭结论只对应其实际执行版本和证据。
