# 历史推导：旧同步协议的本地剪枝

本文件仅适用于旧同步协议的完整收集与准确判死前提，不是混合 EPaxos 的规范或证明。新协议明确要求执行过的实例继续参与冲突扫描；当前输入不引用这份推导。下文保留历史内容，其中“当前”“本轮”均指原版本。

结论：在固定成员、准确判死、crash-stop、不可变首次观察和正确的依赖闭包执行这些前提下，取消提前 Seal，要求所有新候选源于完整收集，就可以在本地实际执行完成并保留结果后，让命令退出本地未来的冲突观察。其他副本不必先执行，不需要执行报告。这里给出协议层面的纸面证明；有限测试检查具体路径，不承担证明的角色。

## 1. 修改的确切范围

正常路径只有在 OBSERVE 已完整发送、且 `R ∪ F = Pi` 后才选择候选。每个依赖的支持数都达到 `r-f` 时 Fast，否则把完整观察并集送入 Seal。低支持度依赖不会被删除，也不会使完整收集后的流程无限等待。

正式恢复读取同样覆盖全部尚未确认死亡的成员。发现合法最终决定就直接学习；没有决定但有合法 Seal 就按原规则继承；都没有时，才把完整读取中的首次观察取并集。继承的值不能根据后继自己的执行进度重新剪枝。

本地执行完成并保留结果后，命令退出未来首次观察使用的冲突索引。先前保存的观察、Seal、决定、执行标记和结果不变。旧查询返回旧观察，不能把“现在已执行”用于重算“当时观察到了什么”。退出索引也不能让未完成的 SCC 改变原定执行顺序。

## 2. 先证明同一命令的决定仍然唯一

剪枝只影响新命令首次形成的观察，不改变已经形成的观察。因此需要检查的是：正常决定之后，恢复是否仍然能保留它，而不是要求各节点的新观察相同。

### 隐藏 Fast 决定

设原协调者从 R 得到 Fast 决定，`|R|=r`。因为当时覆盖已经完整，R 之外的 `n-r` 个成员已经崩溃。总共至多 f 个崩溃，所以 R 内之后最多再崩溃：

```text
f - (n-r) = r-f-1
```

Fast 要求每条依赖至少有 `r-f` 份首次观察支持，因此即使上述成员全部崩溃，每条依赖仍有至少一个存活的观察者。后续完整读取一定能读到它的原始观察。依赖本身已经在这个观察者上执行，并不允许把它从旧观察中删除。

另一方面，后续能回复的成员都在原来的 R 内；R 之外的成员已经 crash-stop，不可能重新出现。因此，新读取的观察并集既不会丢失原依赖，也不会增加原并集没有的依赖，正好重建原 Fast 决定。

这说明 Fast 的支持数门槛仍然必要。完整收集不能替代它；本次只取消覆盖不完整时的提前 Seal，没有取消 Fast 的支持门槛。

### Seal 及其继承

协调者真正决定一个 Seal 值之前，必须完成向全部目标的发送并等待规定的保存时间，所以当时仍存活的副本都已保存它。接管只能在前面的候选准确确认崩溃后发生，合法后继的完整读取会保留这个值。更高代的 Seal 继续继承，不能改写已经决定的值。

如果协调者只发出一部分 Seal 就崩溃，后继可能继承收到的候选；这个候选本身已源于一次完整观察收集。如果所有持有这个部分候选的副本都崩溃，后继可能重新取并集；但这种情况下旧候选不可能已经合法决定，否则每个仍存活副本都会保存它。

因此，原有的决定保持机制继续成立。它依赖准确死亡事实、完整保存等待、唯一合法协调者以及旧状态不可变；本地退出观察不改变这些前提。

## 3. 每个最终值都有一次完整收集作为来源

沿最终决定的形成和继承过程往前追，依赖集合一定来自一次完整观察并集：正常路径的完整收集，或者没有找到 Seal 的完整恢复读取。被继承的候选保留这个来源；隐藏 Fast 的重建按上一节保留其原值。

把这次来源收集选出候选的事件记为 `T(c)`。把节点 i 首次观察 c 的事件记为 `H_i(c)`，实际执行完成记为 `A_i(c)`。这些记号只用于推理，不要求实现保存全局时间戳、增加消息或比较节点时钟。并发事件可以取一个尊重因果顺序的排列。

有两个事实：

1. 任何副本执行 c 之前，`T(c)` 必须已经发生。
2. 对于 `T(c)` 时仍存活的每个节点 i，`H_i(c)` 已经发生，而且 `Obs_i(c)` 包含的每条依赖都属于最终 `D(c)`。

第二点正是取消提前 Seal 后获得的条件。完整覆盖时，一个仍存活的节点不能被准确死亡集合排除；既然它必须回复，它的首次观察就必须进入并集。crash-stop 又保证后来仍存活的节点在更早时也存活，没有重新加入的成员。

## 4. 有依赖关系的冲突命令怎样执行

各副本取得的是同一份最终依赖图。如果两个命令位于不同 SCC，依赖所指向的 SCC 先执行。如果位于同一 SCC，所有副本按同一命令身份顺序执行。

这里不能把“本地完成后退出冲突索引”误写成“从历史执行图中删除顶点”。尤其是逐条执行 SCC 时，必须保留已经确定的内部顺序。例如原 SCC 的顺序是 A、B、C，执行 A 后不能删除 A、重新划分剩余图，再把 C 排到 B 前面。实现可以一次执行整个 SCC，也可以保存其未完成顺序后继续；不要求整个 SCC 期间禁止观察其他命令。

要求完整已决定闭包也很关键。一个 SCC 开始执行前，它能沿依赖到达的命令都已决定，相关出边不会再改变。将来新命令只有指向它的入边，不能凭这一条入边把它重新变成更大的 SCC；若存在形成新环所需的出向路径，这条路径本来就应在开始执行前被解析完整。

所以，本地剪枝不改变有依赖关系的命令的执行规则。真正需要新增证明的是：剪枝后，两个冲突命令完全没有互相记录依赖时，是否仍会执行一致。

## 5. 没有互相记录依赖时，也不可能逆序执行

考虑冲突的 x、y，并假设 `x 不属于 D(y)` 且 `y 不属于 D(x)`。不妨设 `T(x) ≤ T(y)`；另一个方向完全对称。

取任意一个在 `T(y)` 时仍存活的节点 i。由于 crash-stop，它在更早的 `T(x)` 时也存活。因此，它关于 x、y 的两份首次观察都已经进入相应最终依赖值。

**先排除“i 先知道 y，再知道 x”。** 如果是这个顺序，i 观察 x 时已经知道 y。两条命令冲突，但最终 `D(x)` 没有 y，所以 `Obs_i(x)` 也没有 y。按本地剪枝规则，这只有在 i 已实际执行 y 时才可能发生。于是得到：

```text
A_i(y) < H_i(x) ≤ T(x) ≤ T(y)
```

但 y 只能在它自己的来源候选选出之后执行，即 `T(y) < A_i(y)`。前后矛盾。所以 i 不可能先知道 y 再知道 x。

**因此 i 一定先知道 x，再知道 y。** i 观察 y 时已经知道 x；最终 `D(y)` 没有 x，说明它的观察也省略了 x。这要求 i 已实际执行 x：

```text
A_i(x) < H_i(y) ≤ T(y)
```

节点 i 是任意选的，所以在 `T(y)` 时仍存活的所有节点都已经执行 x。而任何 y 的执行都必须在 `T(y)` 之后。由此得到：**所有执行 y 的副本，都先执行 x。** 其他副本若在 `T(y)` 之前就崩溃，则不可能随后再执行 y，同样不会产生相反顺序。

这比只比较两个永久存活副本更强：它也覆盖先执行一些命令、随后才崩溃的副本。证明没有假设各副本的执行速度相同，也没有假设客户端串行发送，更没有要求先前命令在新命令接纳前全局完成。

## 6. 为什么可以得到一致的执行结果

对任意冲突命令对，有依赖关系时使用固定图和 SCC 规则；没有直接依赖时，上一节给出统一的先后顺序。因而本地剪枝不会让两个副本把同一对冲突命令执行成相反顺序。

在相同初始状态、确定性应用和正确冲突分类下，非冲突操作可以交换顺序而不改变状态和各自返回值。因此，上述冲突顺序保证保留副本的执行结果一致性。冲突分类必须考虑返回值，例如同键 Get 与 Put 不能被当成不冲突。

这里证明的是这项修改在规定模型下保持决定与执行安全性，不是证明所有命令都能在固定时间内执行。无限冲突输入的闭包增长、历史删除、快照、成员变更、crash-restart 和完整客户端线性一致性仍按各自范围处理。

## 7. 与旧反例和实际检查的对应

旧七副本反例中，r6 的 x 还没执行，它关于 y 的观察包含 x。提前 Seal 可以跳过这份观察；完整收集不能跳过，所以最终 `D(y)` 保留 x。它不是要求其他五个副本继续报告自己已经执行的 x，而是让仍需要 x 的副本把这条约束放进候选。

检查记录在 [完整收集与本地剪枝实验](../experiments/20261103T084943Z-full-collection-local-pruning-check/README.md)。使用候选实际 Core 的隔离副本，分别检查旧反例、依赖已在见证者上执行后的隐藏 Fast 重建、部分 Seal 继承、连续两次崩溃接管和 SCC 执行。该实验不覆盖真实 Node 的 goroutine、TCP 或物理时间上界，也不把通过的有限场景当作以上证明的替代。
