# Server D：旧请求的开销与落后副本的补齐

对象是 **11 月 11 日的 baseline、Forge v000（a49b2c8）和 v003（84a6445）**。

## 1. 测试项目与数据范围

服务器为 Xeon Gold 6148，20 个物理核、40 个硬件线程，约 62 GiB 内存，Go 1.25.8。七个独立副本各自绑核，负载器另占两个物理核。三档为 1核1线程/Go P=1、2核2线程/Go P=2、2核4线程/Go P=4。

默认 n=7、f=4、s=1、e=1、K=64、W=200 ms、64 B 值。缺少旧命令数据的测试使用 W=1 秒；旧命令缺少决定的测试使用 W=10 秒。

| 测试项目                     | 怎么做                                                  | 已有结果 / 计划任务 | 当前状态                                       |
| ---------------------------- | ------------------------------------------------------- | ------------------: | ---------------------------------------------- |
| 校准                         | 100 条/秒，10 秒，两核两线程                            |                 3/3 | 全部完成                                       |
| 旧请求执行完后，停止发送     | H=0/1,000/10,000，七副本执行完后空闲 30 秒              |             135/135 | 全部取得资源测量                               |
| 旧请求执行完后，继续发送     | 上述三档 H，向各副本均衡发送新请求，100 条/秒持续 30 秒 |             135/135 | 405,000 条新请求全部返回执行结果               |
| G 缺少旧命令数据             | H=100/1,000/5,000，解除限制后向 G 发起一次读取          |             135/135 | 105 次完成，baseline 另 30 次在 300 秒内未完成 |
| G 的 1,000 条旧命令缺少决定  | 保持旧决定阻断，向 G 发送不相关新请求                   |               45/45 | 新请求全部返回执行结果                         |
| G 的 10,000 条旧命令缺少决定 | 同上，修正准备方法后补测                                |               45/45 | 40 次整批完成，baseline 单核 5 次仍缺回复      |

补测 45 次全部形成目标场景，状态为 40 measured、5 incomplete_batch，没有准备失败或执行工具错误。共发送 135,000 条新请求，收到 128,746 条执行回复，另 6,254 条在观察结束时未收到回复，均来自 baseline 单核。实际发送速率均为 100 条/秒，无漏发、窗口后补发、拒绝或传输错误；发送延误 P99 为 1.15～1.29 ms。

以下数字为各次指标的中位数，整批平均延迟与 P99 只在全部请求完成时给出，包含发送结束后的回复；中位数 P99 不是合并请求后重算的 P99。

## 2. 旧请求都执行完后，再处理新请求有多快？

先提交 H 条写入，等待七个副本全部执行完；随后向各副本均衡发送访问新键的写入，每秒 100 条，持续 30 秒，共 3,000 条。这里测的是：**保留了很多旧记录之后，处理新请求会不会变慢？**

三版发送期吞吐与整批吞吐都约为 100 条/秒，已经跟上给定输入；这一负载主要比较延迟。每格为 **整批平均延迟 / P99（毫秒）**：

| 旧请求数量与每副本 CPU |     baseline |        v000 |        v003 |
| ---------------------- | -----------: | ----------: | ----------: |
| H=0，1核1线程          | 8.25 / 17.07 | 2.26 / 4.37 | 2.39 / 5.50 |
| H=0，2核2线程          | 7.19 / 13.67 | 2.11 / 3.18 | 2.19 / 3.56 |
| H=0，2核4线程          | 8.11 / 13.82 | 2.13 / 3.04 | 2.21 / 3.34 |
| H=1,000，1核1线程      | 8.91 / 17.07 | 2.26 / 4.03 | 2.38 / 5.33 |
| H=1,000，2核2线程      | 8.51 / 14.03 | 2.11 / 3.08 | 2.19 / 3.75 |
| H=1,000，2核4线程      | 8.87 / 13.63 | 2.13 / 3.07 | 2.21 / 3.31 |
| H=10,000，1核1线程     | 8.35 / 22.11 | 2.25 / 3.94 | 2.35 / 4.81 |
| H=10,000，2核2线程     | 8.64 / 17.60 | 2.10 / 2.97 | 2.18 / 3.45 |
| H=10,000，2核4线程     | 8.76 / 14.32 | 2.13 / 2.70 | 2.19 / 2.99 |

两版 Forge 的平均延迟约 2.1～2.4 ms，baseline 约 7.2～8.9 ms。H 从 0 增至 10,000 后，两版 Forge 的延迟基本稳定；v003 在这组轻负载下通常比 v000 稍慢。

## 3. 旧请求都执行完后，系统闲时消耗多少资源？

先等七个副本都执行完预热和 H 条旧请求，然后不再发送请求，观察 30 秒。程序仍可能定期扫描记录、检查定时器或分配内存；这里测的是：**处理过的请求越多，系统闲着时是否也越来越消耗资源？**

以下为 **七副本每秒分配的内存合计（MiB/秒）**。它表示不断申请内存的工作量，其中一些内存随后会被回收，不等于每秒永久多占用这么多内存。

| 旧请求数量与每副本 CPU | baseline | v000 |  v003 |
| ---------------------- | -------: | ---: | ----: |
| H=0，1核1线程          |     6.15 | 6.77 | 10.66 |
| H=0，2核2线程          |     6.15 | 6.81 | 10.67 |
| H=0，2核4线程          |     6.17 | 6.77 | 10.68 |
| H=1,000，1核1线程      |    18.02 | 6.75 | 10.66 |
| H=1,000，2核2线程      |    18.03 | 6.75 | 10.66 |
| H=1,000，2核4线程      |    18.05 | 6.76 | 10.67 |
| H=10,000，1核1线程     |   114.54 | 6.69 | 10.67 |
| H=10,000，2核2线程     |   114.71 | 6.69 | 10.66 |
| H=10,000，2核4线程     |   114.76 | 6.71 | 10.68 |

baseline 的空闲分配从约 6 增至 115 MiB/秒；两版 Forge 分别稳定在约 6.7 和 10.7 MiB/秒。baseline 的 allRecords 为活跃记录准备列表时按全部历史数量分配容量，与这一增长现象一致。v003 的固定分配开销高于 v000，修复并未使所有成本都下降。

## 4. G 没收到旧命令，需要多久才能补齐并正确读取？

这组任务在文件中叫 `cold-h…`。具体过程是：

1. 连续对同一个键写入 H 次不同的值，测试工具暂时阻止这些旧命令的数据到达 G；其他六个副本正常执行完所有写入。
2. 解除消息限制，向 G 提交一次读取该键的请求。G 需要取得缺失的信息、完成相关旧命令的执行，才能返回正确结果。例如，依次写入 1、2……1,000 后，这次读取应返回 1,000。
3. 从读取请求发出开始计时，观察多久收到正确回复，并检查七个副本最终都执行了预热、H 条旧写入和这次读取，共 70+H+1 条命令。

这里测的是**缺少旧命令数据的副本补齐信息并完成读取的速度**。读取本身也经过共识。下面为 **读取延迟中位数（秒）；300 秒内完成次数/5**：

| 旧请求数量与每副本 CPU |  baseline |      v000 |      v003 |
| ---------------------- | --------: | --------: | --------: |
| H=100，1核1线程        | 6.70；5/5 | 1.17；5/5 | 1.18；5/5 |
| H=100，2核2线程        | 4.57；5/5 | 1.16；5/5 | 1.16；5/5 |
| H=100，2核4线程        | 4.99；5/5 | 1.15；5/5 | 1.15；5/5 |
| H=1,000，1核1线程      | >300；0/5 | 1.07；5/5 | 1.25；5/5 |
| H=1,000，2核2线程      | >300；0/5 | 1.19；5/5 | 1.07；5/5 |
| H=1,000，2核4线程      | >300；0/5 | 1.07；5/5 | 1.06；5/5 |
| H=5,000，1核1线程      | >300；0/5 | 4.16；5/5 | 4.01；5/5 |
| H=5,000，2核2线程      | >300；0/5 | 3.96；5/5 | 3.92；5/5 |
| H=5,000，2核4线程      | >300；0/5 | 4.19；5/5 | 4.13；5/5 |

两版 Forge 的 90 次读取全部返回正确的最终值，且七个副本都执行完上述命令：H≤1,000 时约 1.1～1.2 秒，H=5,000 时约 4 秒。两者差异较小。

baseline 的 H=1,000/5,000 共 30 次读取到 300 秒仍未完成，状态均为 OBSERVATION_ENDED。观察结束时，其他六个副本已执行旧写入和新读取，G 仍只执行了 70 条预热请求。这说明五分钟内没有完成补齐。

## 5. G 积压了未决定的旧命令，会不会拖慢新请求？

这组任务在文件中叫 `pending-h…`，只比较新请求延迟。G 已收到 H 条访问不同键的旧命令，但测试工具阻止这些旧命令的决定到达 G，其他六个副本已执行完旧命令。保持这一限制，向 G 发送访问其他新键的写入，每秒 100 条，持续 30 秒，共 3,000 条；等待这批请求全部返回执行结果，再计算平均延迟和 P99。

这里测的是：**积压旧实例的后台处理，会不会影响无关新请求的响应速度？** 新请求不依赖旧命令完成，旧命令在测量期间保持未决定。

每格为 **新请求平均延迟 / P99（毫秒）**，均为五次中位数。H=1,000 保留原实验；H=10,000 全部采用本次补测，不与旧准备方法的数据混合。除 baseline 单核 H=10,000 外，其余每格五次均收到全部 3,000 条执行回复。

| 旧请求数量与每副本 CPU |        baseline |        v000 |        v003 |
| ---------------------- | --------------: | ----------: | ----------: |
| H=1,000，1核1线程      |   10.98 / 20.03 | 2.60 / 4.77 | 2.47 / 4.74 |
| H=1,000，2核2线程      |    9.11 / 14.39 | 2.47 / 4.25 | 2.17 / 3.73 |
| H=1,000，2核4线程      |   10.67 / 14.77 | 2.37 / 3.47 | 2.17 / 3.07 |
| H=10,000，1核1线程     | 部分请求 >300 s | 4.46 / 8.64 | 2.52 / 4.94 |
| H=10,000，2核2线程     |   30.36 / 69.97 | 4.54 / 7.83 | 2.19 / 4.17 |
| H=10,000，2核4线程     |   21.92 / 49.13 | 4.94 / 8.58 | 2.18 / 3.07 |

H=10,000 时，两核配置下 baseline 的平均延迟约 22～30 ms，v000 约 4.5～4.9 ms，v003 约 2.2～2.5 ms。三个 CPU 配置下，v003 相比 v000 的平均延迟均降低约 44%～56%。两版 Forge 的 30 次负载全部完成，发送期吞吐均为 100 条/秒，最后一条执行回复均在 30 秒发送窗口内收到。

baseline 单核的“部分请求 >300 s”表示仍未回复请求的等待时间下界，不是整批平均延迟或 P99。五次运行中，每次 30 秒发送期内收到 97～149 条执行回复，发送结束后再等 300 秒，累计收到 1,699～1,825 条，仍缺 1,175～1,301 条。因此不给出整批平均延迟或 P99，也不使用已完成子集代替。发送期 G 的 CPU 占用约为一个核的 95.3%～96.6%，而负载器仍按计划发完全部请求；这组结果反映的是积压状态下新请求处理明显变慢，不能仅凭超时判定永久无法完成或返回了错误结果。

## 6. 结论

- **生成阶段已有收益：**旧请求数量增加后，v000 的资源开销较稳定，新请求延迟较低；副本漏收旧命令时，也能很快补齐并完成读取。这些不是最终修复才带来的。
- **修复收益有具体范围：**G 积压 10,000 条未决定旧命令时，v003 相比 v000 将新请求平均延迟降低约 44%～56%；轻负载延迟和固定资源成本则通常略高于 v000。
- **baseline 的历史成本更明显：**旧记录增加会推高空闲资源开销；G 缺少大量旧命令数据时，五分钟仍未完成读取，详细记录与本机诊断定位到反复检查依赖链的高成本。
- **积压状态下的资源差异已经显现：**baseline 单核在 10,000 条未决定旧命令下不能及时完成 100 条/秒的新负载，两版 Forge 在三档 CPU 下均及时完成。本报告评价给定负载下的响应、资源开销与数据补齐，不把未完成批次直接判为协议安全性错误。

原完整实验与本次补测均已结束，第 5 节已补齐三档 CPU 的有效场景。普通请求、热点、延迟与崩溃后的表现分别见 [A](server-A-evaluation.md)、[B](server-B-evaluation.md)、[C](server-C-evaluation.md) 报告。
