# 混合同步 EPaxos 材料整理

本分支使用 2026-11-06 提供的 `混合epaxos_完整.pdf`（17 页）与 `混合epaxos_伪代码.pdf`（38 页）。工作目录为 `consensus-forge-vft-epaxos`，分支为 `vft-epaxos`。旧同步协议及其已保存实验不因本次迁移而改变。

`inputs/protocol.md` 整理规范、模型、协议目标和论证边界；`inputs/pseudocode.md` 用英文整理事件处理、状态、验证条件和后台流程。它们共同定义实验协议，不要求候选采用伪代码同名函数或相同线程结构。`inputs/system.md` 定义 Go KV、真实 Node、客户端与可控执行的交付目标，并引导实现解释自己的选择。四类角色提示只引用这些共同规则，不重复展开整个算法。

## 与旧分支的主要差异

新模型是完整广播窗口 W 与慢回复人数 s，不是逐消息 Delta 或准确判死。正常路径使用 PreAccept 与正式 Accept；恢复使用 ballot、Prepare、Validate/Rebuild、HELP 和 Omega。客户端请求号与协议实例号分离，允许相同请求号及载荷跨入口重试。实例执行后仍参与冲突观察；K 个私有准入槽在原协调者本地执行后释放，但不回收实例、证据和结果。

旧版 `docs/local-pruning-safety.md` 只保留为历史推导，不是新协议依据。`comparison/` 绑定旧候选与旧模型，不能直接作为新候选的比较脚本。新的输入不会加载这些研究者文档或历史实验。

## 主流程与 baseline

双方的 `protocol.md` 与 `pseudocode.md` 内容相同，任务范围同为可运行 Go KV、真实 Node、多进程、并发客户端、重试与去重、真实时间和可控执行。baseline 自行组织设计、实现、自测；主流程额外使用 `system.md` 的设计指导及独立审计、证据修复和复核。伪代码是共同协议输入，不是主流程专享的参考答案。两个输入目录独立维护，运行不会自动改写对方；离线测试核对当前共同材料与交付副本。

材料继续平铺在 `inputs/`，通过固定输入清单分发。`pseudocode.md` 随候选源码交付审计，也进入修复和复核的对应版本。协议逻辑没有搬进 Python 控制器。

## 工具与未决事项

`schedule.py` 继续记录、控制和重放适配器交互，不判断 W/s 或共识性质。旧 `tracecheck.py` 只保留为逐消息有界交付模型的独立历史工具；新实验不注入它，也不在证据导入或调度结束时自动调用它。历史 `trace_files` 引用仍能保留与导航，但不重新生成旧时间模型的判定。

本轮已确定每次干净集群运行最多 10,000 条新逻辑请求，规则放在双方共同的 `protocol.md` 实验范围一节；这是研究者确定的实验范围，不是 PDF 新增的协议规则，也不是服务器的历史容量上限。达到上限后停止新增请求，继续在执行预算内处理已有工作。每次运行的 W 固定，实际窗口前提仍需观察。

已确定的范围和剩余证明义务见 [design-issues.md](design-issues.md)。尚未完成的形式论证不阻塞按现有规则生成实现；发现合法反例时再区分协议问题和实现偏离，不把工程选择重新变成人工审批事项。
