# 混合同步 EPaxos 材料整理

本分支使用 2026-11-06 提供的 `混合epaxos_完整.pdf`（17 页）与 `混合epaxos_伪代码.pdf`（38 页）。工作目录为 `consensus-forge-vft-epaxos`，分支为 `vft-epaxos`。旧同步协议及其已保存实验不因本次迁移而改变。

`inputs/protocol.md` 整理规范、模型、协议目标和论证边界；`inputs/pseudocode.md` 用英文整理事件处理、状态、验证条件和后台流程。它们共同定义实验协议，不要求候选采用伪代码同名函数或相同线程结构。`inputs/system.md` 定义 Go KV、真实 Node、客户端、可控执行、服务语义与交付范围。三份文档集中承载协议及目标系统的具体要求。通用工程方法放在 `AGENTS.md`，生成、审计、修复和复核提示只引用给定规则，不内置 W/s、恢复路径或其他协议特有要求。

## 与旧分支的主要差异

新模型是完整广播窗口 W 与慢回复人数 s，不是逐消息 Delta 或准确判死。正常路径使用 PreAccept 与正式 Accept；恢复使用 ballot、Prepare、Validate/Rebuild、HELP 和 Omega。客户端请求号与协议实例号分离，允许相同请求号及载荷跨入口重试。实例执行后仍参与冲突观察；K 个私有准入槽在原协调者本地执行后释放，但不回收实例、证据和结果。

旧版 `docs/local-pruning-safety.md` 只保留为历史推导，不是新协议依据。后续共同材料已加入依赖前沿和检查点替换；仍须区分执行后的槽位释放与经合法检查点安装后的证据回收。新的输入不会加载这些研究者文档或历史实验。

## 主流程与 baseline

双方的 `protocol.md`、`pseudocode.md` 和 `system.md` 内容相同，协议信息与交付目标一致。baseline 自行组织设计、实现、自测；主流程在角色提示中提供工程、调查与证据方法，再安排独立审计、修复和复核。两组默认生成阶段均不设固定截止时间，单次隔离命令仍受限。伪代码是共同协议输入，不是主流程专享的参考答案。两个输入目录独立维护，运行不会自动改写对方；离线测试核对三份共同材料及其交付副本。

材料继续平铺在 `inputs/`，通过固定输入清单分发。三份设计材料随候选源码交付审计，也进入修复和复核的对应版本。替换协议或目标系统时修改这三份材料；角色提示与控制器不解释具体协议。当前执行环境仍是 Go，候选模块名从其 `go.mod` 读取，不再在 Python 中指定混合 EPaxos 的模块名。

设计在一次实验内给定且不修改，但不因此认定它正确。实现可选择未规定的机制；审计需区分实现偏离、合法设计反例和未完成调查。真正阻碍合规修复的缺失或矛盾规则通过既有问题记录与 `needs_specification` 处理，继续不受影响的工作。本次不接入设计 agent，也不增加运行内的设计协商流程。

## 工具与未决事项

`schedule.py` 记录、控制和重放适配器交互，不判断 W/s 或共识性质。历史 `trace_files` 引用仍能保留与导航，但不解析为协议时间模型，也不重新生成时间判定。

已有检查点替换机制后，取消此前为有限历史实验设置的固定请求总数上限。J 仍是每个 origin 在单个 epoch 内的分配上限；后续 epoch 可以继续接纳请求。具体负载规模由实验选择，窗口前提和结果保留义务仍须满足。旧实验保存的输入与结果不改写。

已确定的范围和剩余证明义务见 [design-issues.md](design-issues.md)。尚未完成的形式论证不阻塞按现有规则生成实现；发现合法反例时再区分协议问题和实现偏离，不把工程选择重新变成人工审批事项。
